# 4. Central semantic philosophy

The following principles are already established and should be treated as architectural constraints unless current canonical specs explicitly supersede them.

## 4.1 Checker authority

When the semantic checker can formally establish a fact, that fact is authoritative.

Example:

```text
checker proves CellNum
developer annotates Int
```

The annotation is wrong.

Do not reconcile this by trusting both equally.

Developer annotations become assumptive evidence only when the checker cannot independently establish the proposition and the unknown reason permits a contract assumption.

---

## 4.2 Epistemic states

Phalcom distinguishes:

```text
Established
Assumed
Unknown(reason)
Dynamic(reason)
```

These states are semantically meaningful.

A concrete `TypeId` is not sufficient to describe semantic knowledge.

Never silently perform:

```text
Assumed -> Established
Unknown -> Known
Dynamic -> Known
```

without a valid proof rule.

---

## 4.3 Causal invalidity is orthogonal to type knowledge

The analyzer may correctly publish:

```text
Established(Int)
+
Invalid(C1)
```

or:

```text
Established(Int)
+
Ready
+
non-clean upstream causal invalidity
```

depending on whether the current proposition itself was refuted.

Do not collapse type knowledge and validity into one axis.

---

## 4.4 Required-premise completeness

A conclusion may only be formally established when every premise required to establish that proposition has been accounted for.

Do not use patterns such as:

```rust
if let Some(ty) = child.knowledge.ty() {
    inputs.push(ty);
}
```

when a missing child is a required premise.

---

## 4.5 Identity preservation

Semantic identity should eventually be explicit and canonical.

Do not reconstruct identity from lossy tuples such as:

```text
(name, source range, owner)
```

if canonical IDs already exist or can be propagated.

---

## 4.6 Authority monotonicity

Information from a weaker authority source must not become stronger merely by flowing through another semantic operation.

Examples:

```text
Assumed callable
→ must not produce Established fixed return

Assumed receiver
→ must not establish target-dependent fixed result
```

unless there is a separate independent proof.

---

## 4.7 Atomic publication

A semantic product should not be partially committed and then repaired piecemeal.

This applies both to expression products and later to:

```text
workspace state
semantic session state
published snapshots
incremental products
```

# 5. Correctness versus completeness

This distinction is critical.

The **Semantic Correctness Program** is not intended to make the analyzer understand every valid Phalcom program.

It is intended to guarantee:

> Whenever the analyzer publishes a semantic claim, that claim obeys the formal semantic laws of the language.

Correctness work therefore prefers:

```text
Unknown
Dynamic
Blocked
Suppressed
```

over an unjustified precise answer.

Examples of correctness bugs:

```text
[1, unresolved] -> Established List<Int>

1 + "hello" -> Ready Int without checking RHS

list["wrong"] -> Ready element type without checking index

Assumed callable -> Established return

workspace update fails after mutating committed internal state

advisory lookup bypasses export visibility
```

The **Semantic Completeness Program** begins after correctness closure.

Completeness asks:

> Which programs that the language semantics make statically knowable are still reported as Unknown, Dynamic, Blocked, unresolved, or unsupported?

Completeness work may include:

- deeper callable-pack analysis;
- complete rest/spread parameter binding;
- richer iterable/cursor protocol inference;
- recursive/fixpoint inference;
- more advanced generic inference;
- higher-kinded inference coverage;
- GADT/ADT reasoning;
- exhaustiveness;
- pattern refinements;
- refined types;
- stronger branch narrowing;
- richer structural relations;
- more complete public-signature inference;
- additional protocol/trait reasoning;
- improved LSP query completeness.

Do not solve completeness by weakening correctness invariants.

Correctness is the foundation on which completeness is built.

# 9. Likely next architectural slice: generic inference and proof integrity

Unless the canonical ledger says otherwise, the next technical slice should concern generic inference proof integrity.

Repository archaeology should investigate, at minimum:

```text

```

Known issues requiring fresh verification include:

### Unknown generic premise omission

Current/previously observed shape:

```text
if argument has TypeId:
    add inference constraint
else:
    contribute nothing
```

This can make:

```phalcom
first<T>(1, unresolved)
```

solve `T = Int` and publish an unjustifiably strong result.

The correct model must distinguish:

```text
substitution solvable
```

from:

```text
call proposition fully proven
```

### Generic result authority

Generic result authority must depend on all premises actually used to establish the substitution/result proposition.

Likely authority relationship:

```text
result authority
=
meet(
    receiver/callee authority,
    callable contract authority,
    substitution support,
    result-contract authority,
    all required generic premises
)
```

Do not ratify this formula without fresh repository and spec verification.

### Expected-result constraints

Expected context may constrain inference.

Expected context must not become evidence that the runtime value actually has that type unless the semantic proof rules permit it.

### Generic solver outcome

Preserve structured states:

```text
solved
underconstrained
conflicting
blocked
dynamic
cancelled
budget exceeded
internal failure
```

Do not reduce generic proof state to `Option<TypeId>`.

