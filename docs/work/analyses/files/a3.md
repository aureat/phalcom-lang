Next is to turn the design decisions into the actual Resource implementation package. The dependency order should be:

## 1. Freeze the Resource contract (spec amendment)

Before implementation, produce the replacement `resource-implementation-spec.md`.

It should supersede the current spec, not patch it. The new spec should include:

- Handle encoding:

    - 21-bit slot index
    - 32-bit generation
    - exact `f64` range proof
    - retired-slot policy
- Resource table model:

    - `Vacant`
    - `Open`
    - `Closed`
    - `Retired`
- Primitive surface:


```
Resource.attach_(_)
Resource.close_
Resource.isClosed_
Resource.ensureOpen_

System.leakReport_
System.strictResources_(_)
```

- Error model:

```
UseAfterCloseError
```

with:

```
kind
open_site
close_site
attempt_site
reason = closed | stale | malformed
```

- Diagnostic attribution:

    - first user frame rule
- Leak semantics:

    - stderr
    - strict mode
    - deterministic ordering
- Shutdown boundary:

    - Resource defines only table teardown
    - Reactor owns pending-work coordination later
- Test gates.


This becomes the authoritative document.

## 2. Write a dedicated test specification

Before Rust changes, define the tests. Resource is a lifecycle primitive; implementation mistakes here will infect BytesReader, Files, sockets, etc.

The test matrix should be:

### Rust unit tests

`resource.rs`

Handle encoding:

```
pack(0,0)
pack(max_slot, max_generation)
reject(index >= 2^21)
reject(values > 2^53-1)
reject fractional Number
reject NaN/infinity
```

Generation:

```
open slot 1 generation 7
close
close again succeeds
reuse slot
generation becomes 8
old handle is stale
```

State machine:

```
Vacant -> Open
Open -> Closed
Closed -> Closed
Closed -> Open(next generation)
Retired -> never reusable
```

Table behavior:

```
open
resolve
close
leaks
drain
```

---

### VM golden tests

Positive:

```
r = TestResource.new()
assertFalse(r.isClosed)
assert(r.close.ok)
assert(r.close.ok)
assert(r.isClosed)
```

Use-after-close:

```
r = TestResource.new()
r.close
r.read
```

Expected:

```
UseAfterCloseError
kind: TestResource
open site: user.ph:line
close site: user.ph:line
```

Stale handle:

Create a resource, force slot reuse, attempt old handle.

Expected:

```
UseAfterCloseError(reason=stale)
```

---

### Leak tests

Normal:

```
strictResources(false)
leak resource
exit 0
stderr contains leak
```

Strict:

```
strictResources(true)
leak resource
exit non-zero
```

Ordering:

```
allocate A
allocate B
allocate C
```

Report order must be:

```
A
B
C
```

---

### Constructor safety tests

This is the Lua-inspired one.

Verify:

```
constructor fails before attach
```

does not leave a table row.

Verify:

```
attach succeeds
```

is the final fallible step.

## 3. Amend dependent specs

Three downstream edits are required.

### Streams

Replace:

```
_handle = Resource.register_("BytesReader")
```

with:

```
self.attach_("BytesReader")
```

and replace:

```
if self.isClosed
```

with:

```
self.ensureOpen_
```

Also update dirty-buffer leak wording because Resource now supports richer leak metadata.

---

### FS

Add a new concept:

```
Resource.adoptExternal_()
```

or equivalent.

Do not use `attach_` for file descriptors.

Reason:

`attach_` means "the object owns and creates the resource row".

FS needs:

```
worker produced fd
↓
VM receives completion
↓
resource row created
↓
File object receives ownership
```

That is adoption, not attachment.

---

### Reactor

Before FS implementation, Reactor must specify:

```
what happens to pending jobs when close happens?
```

Resource cannot solve this.

Possible policies:

1. close waits for pending jobs;
2. close cancels pending jobs;
3. close marks closing and final close happens after drain.

I would pick (3):

```
Open
 |
close requested
 |
Closing
 |
all jobs complete
 |
native close
 |
Closed
```

That matches Node's practical behavior better than immediate descriptor destruction.
