The cross-language evidence strengthens the basic direction, but it changes several details. The constrained single-`Number` handle remains the right representation.

## Lessons worth importing

Python, Java, Lua, and Node converge on one lesson: deterministic cleanup must be explicit and scope-oriented. Python’s context managers close resources even when a block exits through an error; Java’s try-with-resources does the same; Lua 5.4 added to-be-closed variables that run on normal exit, return, jumps, and errors. [Python documentation](https://docs.python.org/3/library/contextlib.html)

They also demonstrate why GC cleanup must not carry correctness. Node explicitly describes garbage-collection closure of `FileHandle` as unreliable and deprecated. Java’s `Cleaner` makes no guarantee that actions run during `System.exit`, and exceptions from cleaning actions are ignored. Python has `ResourceWarning`, but release builds ignore that warning category by default. [Node.js](https://nodejs.org/api/fs.html)

That validates Phalcom’s no-finalizer rule, but it also means the leak reporter must not become a quiet equivalent of Python’s ignored warning.

A second major lesson comes from Java’s `Closeable`: repeated close should have no effect, and an implementation should mark the resource closed and relinquish ownership before reporting a close failure. This avoids dangerous retries against an underlying handle that may already have been consumed. [Oracle Docs](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/io/Closeable.html?utm_source=chatgpt.com)

A third comes from Node’s asynchronous file API. Node warns that promise-based filesystem operations are not synchronized, says closing a raw descriptor while another operation uses it can produce undefined behavior, and makes `FileHandle.close()` wait for pending operations. [Node.js](https://nodejs.org/api/fs.html)

This confirms that U-FS cannot merely copy an fd into jobs and synchronously close the table row. That remains a downstream blocker. U-RESOURCE should define the lifecycle boundary clearly without pretending to solve reactor ownership.

Lua contributes two particularly useful implementation lessons. Its file implementation constructs a handle in a closed state before opening the underlying file, preserving consistency if allocation or opening fails. Its structured cleanup closes multiple resources in reverse declaration order and continues closing remaining resources after one close operation fails. Lua also documents that resources held by abandoned suspended coroutines may never receive scope cleanup, reinforcing the need for a VM-global leak table. [Lua](https://www.lua.org/source/5.4/liolib.c.html)

Java adds the error-composition rule: when both the body and cleanup fail, the body’s error remains primary and cleanup errors are retained as suppressed failures rather than replacing it. [Oracle Docs](https://docs.oracle.com/javase/tutorial/essential/exceptions/tryResourceClose.html?source=post_page---------------------------&utm_source=chatgpt.com)

## Refined Resource design

### Handle encoding

Retain one inherited slot containing either `None` or an exact integer-valued `Number`.

```
INDEX_BITS      = 21
GENERATION_BITS = 32
MAX_SLOTS       = 2^21
MAX_HANDLE      = 2^53 - 1

packed = index × 2^32 + generation
```

Validation rejects:

- non-Number values;
- NaN and infinity;
- fractional values;
- negative values;
- values greater than `2^53 − 1`;
- decoded indices outside the table;
- impossible generations or malformed encodings.

A slot whose generation reaches `u32::MAX` is retired rather than wrapped. This prevents an ancient handle from becoming valid again.

### Table state

The old `closed: bool` representation should be replaced with an explicit state machine:

```
enum ResourceSlotState {
    Vacant,
    Open {
        kind: ResourceKind,
        open_site: SourceRange,
        serial: u64,
    },
    Closed {
        kind_name: String,
        open_site: SourceRange,
        close_site: SourceRange,
    },
    Retired,
}
```

The slot stores its current generation outside the state.

The transitions are:

```
Vacant(g)  --open-->   Open(g)
Open(g)    --close-->  Closed(g)
Closed(g)  --close-->  Closed(g), success and no effect
Closed(g)  --reuse-->  Open(g + 1)
Closed(MAX)            Retired
```

Generation changes on reuse, not close. That is what makes both idempotent close and stale-handle detection possible.

Each allocation also gets a monotonically increasing internal `serial`. Leak reports sort by this serial, giving deterministic allocation order even when table slots are reused.

### Close transition

Close must logically consume the native resource exactly once:

1. Resolve and validate the handle.
2. Move the native `ResourceKind` out of the `Open` state.
3. Install the `Closed` tombstone, including `close_site`.
4. Invoke the kind-specific native close operation.
5. Return its failure, when any, without restoring the `Open` state.

This follows the safer Java posture: an OS close failure does not imply the handle remains safely retryable. A second `close` returns success and does not call the native close operation again. [Oracle Docs](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/io/Closeable.html?utm_source=chatgpt.com)

For this Resource unit, managed in-memory resource kinds are infallible. The return channel must nevertheless be specified now so File can extend it later:

```
close_ returns:
    None           native close succeeded or resource was already closed
    Error instance native close was attempted once and failed

close_ raises:
    UseAfterCloseError only for a stale/reused or malformed handle
```

The `.ph` wrapper converts the bare return value:

```
close {
  const failure = self.close_
  if failure == None {
    return Ok.new(None)
  }
  return Err.new(failure)
}
```

### Replace `register_` with atomic attachment

I recommend replacing the two-step primitive:

```
_handle = Resource.register_("BytesReader")
```

with an instance primitive:

```
self.attach_("BytesReader")
```

`attach_` atomically:

1. verifies that the receiver is a `Resource`;
2. verifies slot zero is `None`;
3. validates the diagnostic kind name;
4. allocates the table entry;
5. packs the handle;
6. writes it directly into inherited slot zero.

This removes a partially registered state where a table row exists but the returned handle was never installed in the object.

`attach_` must be the final potentially failing operation in a managed-resource constructor. No code follows it except an implicit or explicit return. This imports Lua’s “closed/inert before acquisition” lesson without adding finalization. [Lua](https://www.lua.org/source/5.4/liolib.c.html)

The primitive is internal-by-contract rather than a public capability. Calling it manually grants no filesystem or network authority because U-RESOURCE supports only:

```
ResourceKind::Managed { name: String }
ResourceKind::Test(...)
```

The name should be bounded, for example to 128 UTF-8 bytes, and must not contain line breaks or control characters because it appears in diagnostics.

External resources such as `File` will need a separate atomic adoption seam in U-FS. U-FS must not reuse `attach_` to fabricate an fd-backed row.

### Object states

The inherited handle slot begins as `None`.

Its semantics are:

|Object/table condition|`isClosed`|`close`|guarded operation|
|---|---|---|---|
|handle is `None`|`true`|`Ok(None)`|raises use-after-close|
|matching open row|`false`|closes once|proceeds|
|matching closed row|`true`|`Ok(None)`|raises with close site|
|stale generation|`true`|raises|raises|
|malformed handle|`true`|raises|raises|

Treating an unattached object as closed keeps partially constructed objects inert.

### `ensureOpen_`

The Boolean `isClosed` is insufficient for operational guards because it discards diagnostic context. Add:

```
Resource#ensureOpen_
```

It returns `None` for a matching open entry and raises `UseAfterCloseError` otherwise.

Managed stream methods therefore begin with:

```
self.ensureOpen_
```

rather than:

```
if self.isClosed { ... }
```

For a matching closed tombstone, the diagnostic includes:

- resource kind;
- open site;
- close site;
- attempted operation site.

For a stale handle whose slot has been reused, the runtime cannot retain unbounded historical diagnostics. The contract should therefore distinguish:

```
reason: closed
    kind, open site, close site available

reason: stale
    slot and generation information available;
    historical open/close sites are best-effort
```

Both remain represented by `UseAfterCloseError` until a richer error-kind carrier lands.

### Call-site attribution

`attach_`, `close_`, and `ensureOpen_` are reached through `core.ph`, so the immediate primitive frame is not the correct diagnostic location.

Add one shared VM helper:

```
fn first_user_source_range(&self) -> SourceRange
```

It walks outward to the first frame not originating in the installed core module. The same rule must be used for:

- open site;
- close site;
- attempted-use site.

Leak and use-after-close tests must assert user program lines rather than `core.ph` lines.

### Leak policy

The default behavior should be:

- leaks are rendered to `stderr`;
- diagnostics are visible by default;
- the process retains its otherwise successful exit status;
- every open entry is reported once at orderly VM shutdown.

`System.strictResources(true)` changes only the exit status: any leak causes a nonzero exit.

`System.leakReport` returns a stable snapshot and has no side effects:

- it does not close resources;
- it does not mark them reported;
- it does not mutate strict mode;
- it returns rows in allocation-serial order.

This avoids Python’s mistake of making resource warnings invisible by default while preserving a non-strict development mode. [Python documentation](https://docs.python.org/3/library/warnings.html)

The existing Resource test plan’s “exact stdout” expectation should become exact `stderr`.

### Shutdown order

U-RESOURCE can define only its own side of shutdown:

1. all registered external producers must already have stopped;
2. capture the leak snapshot;
3. render leaks;
4. drain all remaining open table entries exactly once;
5. determine success versus strict-resource failure;
6. destroy the heap and VM.

U-RESOURCE must not claim it can safely drain resources still referenced by reactor jobs. U-REACTOR and U-FS must guarantee step 1 before they add external resource kinds.

### Structured cleanup compatibility

No `using` syntax or scope-management feature should be added in this unit. The Resource contract should nevertheless record future requirements learned from Python, Java, and Lua:

- cleanup runs on normal and exceptional scope exit;
- resources close in reverse acquisition order;
- every close is attempted even after one fails;
- an existing body error remains primary;
- close failures are retained as secondary errors;
- abandoned fibers remain detectable by the global leak table;
- no scope feature weakens explicit-close or leak-report behavior.

That keeps the Resource protocol compatible with future deterministic cleanup without prematurely choosing syntax. [Python documentation](https://docs.python.org/3/library/contextlib.html)

## Revised primitive delta

U-RESOURCE should install six primitives:

```
Resource#attach_(_)
Resource#close_
Resource#isClosed_
Resource#ensureOpen_
System.leakReport_
System.strictResources_(_)
```

This corrects the existing census omission of `register_` and accounts for the new operational guard. The current spec’s declared floor delta is therefore inconsistent and must be replaced. resource-implementation-spec.mdMD

## Downstream consequences

U-STREAMS constructors should replace `_handle = Resource.register_(...)` with `self.attach_(...)` as their final action. Every can-operate method should call `ensureOpen_`. streams-implementation-spec.mdMD

U-FS needs a separate atomic adoption path for handles returned by worker completions. It must also resolve operation ordering and close-while-pending behavior before implementation. Node’s experience makes the current “copy `RawFd` into a job and synchronously close it” design unacceptable. fs-implementation-spec.mdMD [Node.js](https://nodejs.org/api/fs.html)
