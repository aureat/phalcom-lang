# 0. Amendment contract

Spec 02 is no longer a design draft. Its revised architecture has entered implementation and has already produced concrete schema/export/runtime-typing code. Therefore this specification uses a different rule from an ordinary revision:

> **Spec 02 remains the historical design authority for the implementation already landed. Spec 02.5 changes only what later decisions or implementation evidence now require.**

A 02.5 implementation must begin from the repository, not from an imagined clean implementation of Spec 02. If the live implementation has made a sound, equivalent choice that differs from old pseudocode, 02.5 adopts the implementation unless a later semantic law requires a migration.

The purpose of 02.5 is to close five classes of gap discovered only after Spec 02 implementation began:

1. restore an explicit runtime-validation boundary doctrine that the earlier compact Spec 02 stated more clearly than its revision;
2. extend the durable model for the now-ratified `RecordRow` semantic domain without rewriting the working closed-record representation unnecessarily;
3. decouple light advanced semantic summaries from heavy proof retention;
4. preserve explicit provenance and foreign/native-boundary extension points that were compressed during the Spec 02 rewrite;
5. put schema evolution on a deliberate compatibility footing before the first post-v1 semantic extension is emitted.

This specification **does not** reopen the following implemented decisions:

- compiler/static semantics are authoritative;
- durable metadata is store-independent and does not serialize raw `TypeId`, `KindId`, `InferVarId`, `ObjRef`, or `ClassId`;
- generic constraints are signature-owned;
- generic parameter identity is owner/index, not spelling;
- type lambdas use scoped/alpha-normalized metadata;
- `Self` is owner-relative;
- nominal type forms reify to existing runtime class objects;
- synthetic type forms are lazily reified;
- descriptors are weakly cached;
- weak cache liveness uses `Heap::try_get`, never panicking `Heap::get`;
- a descriptor roots its typing context, but the descriptor cache does not root descriptors;
- immutable metadata pools are VM-owned and read without a broad arena lock;
- runtime overlays are separate from immutable base metadata;
- `MethodObject` does not grow a full static semantic signature;
- runtime method-to-semantic mapping is a side table;
- `Value` does not gain a type/kind metadata tag;
- generic type applications do not create specialized runtime classes/metaclasses or per-instance generic tokens;
- semantic type metadata does not alter selector identity, method dictionary keys, layout, allocation, or ordinary dispatch.

If an implementation agent proposes any of those changes while implementing 02.5, stop and require a new architectural decision rather than treating it as an amendment detail.

# 3. Non-negotiable preservation laws

Every 02.5 change must preserve these laws.

## 3.1 Runtime erasure law

For ordinary values:

```text
value.class
layout
allocation
selector lookup
inline-cache key
method table
GC layout
```

are unchanged by static generic or row information.

No successful `validate(value, as: T)` call installs a permanent generic or row token on `value`.

## 3.2 Explicit-validation law

No ordinary runtime operation performs deep semantic validation merely because metadata exists.

Specifically, these paths must not implicitly call deep typing validation:

- ordinary assignment;
- ordinary field write;
- list/map/set mutation;
- object allocation;
- method dispatch;
- return from an ordinary method;
- closure invocation;
- selector lookup;
- inline-cache population;
- GC tracing;
- class lookup.

Deep validation occurs only because an explicit boundary requested it.

## 3.3 No false higher-order evidence

Runtime class membership in `Function`, `Closure`, `BoundMethod`, or another callable class does not by itself prove a structural callable type such as:

```text
(Int, String) -> Bool
```

Sound higher-order success requires an authoritative callable contract/signature witness whose relation to the requested callable form can be checked. Absent such a witness, the result is a dynamic boundary or blocked/unavailable state according to Spec 03—not success.

## 3.4 Row-domain separation

`RecordRow` is not `Type`.

A parameter `R: RecordRow`:

- may appear as a record tail;
- may be reflected as a generic parameter whose `.kind` is `RecordRow`;
- must not be emitted as `TypeNode::Parameter(R)`;
- must not be used where a proper type is required.

`RecordRowVarId` is never serialized.

## 3.5 Closed-record compatibility law

A closed record already representable in schema v1 remains representable by the existing v1 `TypeNode::Record` variant.

Adding open records must not force every closed record to acquire a new wire shape or new structural fingerprint.

## 3.6 Extension trust law

Parsing an extension section establishes only that bytes were decoded according to a known version. It does not establish:

- proof trust;
- purity;
- totality;
- effect freedom;
- callable validity;
- FFI safety.

Each owning semantic subsystem decides the meaning/trust of its payload.

# 6. Schema evolution foundation

Record rows are the first post-v1 semantic extension that affects the core kind/type graph. Before emitting them, schema version behavior must become explicit.

## 6.1 Current problem

The current validator conceptually expects:

```text
header.schema_version == TYPE_METADATA_SCHEMA_VERSION
```

This is appropriate while there is only one schema. It is insufficient once a v2 producer exists, because a v2 runtime should have an intentional answer to a v1 artifact rather than treating every older schema as malformed.

The current JSON decoder can remain structurally simple **provided v2 is additive**. New Rust enum variants do not prevent the new decoder from deserializing old JSON containing only old variants. This is why 02.5 forbids reshaping the v1 closed-record payload.

## 6.2 Version constants

Modify `phalcom-type-meta/src/header.rs`.

Introduce explicit minimum/current constants:

```rust
pub const MIN_SUPPORTED_TYPE_METADATA_SCHEMA_VERSION: u32 = 1;
pub const TYPE_METADATA_SCHEMA_VERSION: u32 = 1; // remains 1 until A3 enables row schema v2

#[inline]
pub const fn supports_type_metadata_schema(version: u32) -> bool {
    version >= MIN_SUPPORTED_TYPE_METADATA_SCHEMA_VERSION
        && version <= TYPE_METADATA_SCHEMA_VERSION
}
```

When the row-aware schema is enabled in A3, change only:

```rust
pub const TYPE_METADATA_SCHEMA_VERSION: u32 = 2;
```

Do not bump `SEMANTIC_MODEL_VERSION` merely because the wire schema gains a representation for an already-ratified semantic domain. Bump the semantic-model version only if the meaning of an existing canonical form/relation changes incompatibly.

## 6.3 Version-aware validator

Modify `phalcom-type-meta/src/validate.rs`.

Replace exact current-version acceptance with:

```rust
if !supports_type_metadata_schema(bundle.header.schema_version) {
    return Err(MetadataValidationError::UnsupportedSchemaVersion {
        found: bundle.header.schema_version,
        minimum: MIN_SUPPORTED_TYPE_METADATA_SCHEMA_VERSION,
        maximum: TYPE_METADATA_SCHEMA_VERSION,
    });
}
```

Then apply schema-specific legality checks:

```rust
match bundle.header.schema_version {
    1 => validate_schema_v1_feature_floor(bundle)?,
    2 => validate_schema_v2_feature_floor(bundle)?,
    _ => unreachable!("version range checked above"),
}
```

For schema v1:

- `features.record_rows` must be false;
- no `KindNode::RecordRow` may occur;
- no open-record global/scoped node may occur;
- existing closed `TypeNode::Record` remains legal;
- all other existing v1 invariants remain unchanged.

For schema v2:

- v1 nodes remain legal;
- `RecordRow` and open-record nodes are legal only when `features.record_rows == true`;
- a bundle setting `record_rows=true` but containing no row-aware construct is legal but should be avoided by the exporter; deterministic producer tests require minimal feature bits;
- an open-record node with `record_rows=false` is malformed.

## 6.4 Decoder compatibility

Modify `phalcom-type-meta/src/encode.rs` only as necessary to improve error classification. Because the v1 variant shapes remain unchanged, the current direct deserialization can continue to read v1 after the Rust enums gain additive v2 variants.

Required behavior:

```text
v1 JSON + v2 decoder  -> deserialize -> v1 validation -> success
v2 JSON + v2 decoder  -> deserialize -> v2 validation -> success
v2 JSON + v1 decoder  -> unsupported by definition; old runtime must reject/rebuild
future v3 + v2 decoder -> explicit UnsupportedSchemaVersion when the envelope remains structurally readable
```

If a future schema must reshape a required existing field such that direct deserialization cannot inspect the old header first, **then** introduce a header-probe/versioned decoder envelope. Do not pre-build duplicate v1/v2 struct trees now while additive evolution is sufficient.

## 6.5 Golden v1 fixture

After Step 3 completes, generate and check in a stable v1 fixture under a new test-fixture location, for example:

```text
phalcom-type-meta/tests/fixtures/schema-v1/
  basic.json
  generic-lambda.json
  closed-record.json
```

The fixture must contain:

- at least one nominal;
- one generic application;
- one signature-owned constraint;
- one type lambda;
- one closed record;
- one callable signature;
- one runtime root.

Once checked in, those files become compatibility evidence. 02.5 implementation must not regenerate them using schema v2 and overwrite history.

# 7. Record-row metadata extension: schema v2

## 7.1 Design choice: preserve closed records, add open records

Do **not** replace:

```rust
TypeNode::Record(Box<[RecordFieldRef]>)
```

with a different payload in place.

That variant becomes the durable representation of a closed record in both v1 and v2.

Add a separate row-aware case for a record with a stable tail parameter.

This has four advantages:

1. old v1 artifacts deserialize in a v2 decoder without a duplicate legacy type tree;
2. existing closed-record structural fingerprints can remain stable;
3. open rows are visibly feature-gated rather than ambiguously changing old record semantics;
4. the metadata representation does not have to mirror the exact internal `RecordRowId` storage chosen by Spec 05.

## 7.2 Global wire shape

Modify `phalcom-type-meta/src/kind.rs`:

```rust
pub enum KindNode {
    Type,
    RecordRow,
    Arrow {
        parameters: Box<[KindNodeId]>,
        result: KindNodeId,
    },
}
```

Modify `phalcom-type-meta/src/type_node.rs`.

Add:

```rust
#[derive(Clone, Debug, Eq, Hash, PartialEq, Deserialize, Serialize)]
pub struct OpenRecordTypeRef {
    pub fields: Box<[RecordFieldRef]>,
    pub tail: StableTypeParameterRef,
}
```

and:

```rust
pub enum TypeNode {
    // v1 forms remain unchanged
    Never,
    Unit,
    Nominal { declaration: StableDeclarationRef },
    Applied { origin: TypeNodeId, arguments: Box<[TypeNodeId]> },
    Union(Box<[TypeNodeId]>),
    Tuple(Box<[TupleElementRef]>),
    Record(Box<[RecordFieldRef]>),
    Callable(CallableTypeRef),
    Parameter(StableTypeParameterRef),
    SelfType(SelfTypeRef),
    TypeLambda(TypeLambdaRef),

    // schema v2, feature = record_rows
    OpenRecord(OpenRecordTypeRef),
}
```

Semantic interpretation:

```text
TypeNode::Record(fields)
    == closed record #{ fields... }

TypeNode::OpenRecord { fields, tail: R }
    == open record #{ fields..., | R }
```

The `OpenRecord` node itself has kind `Type`. Its `tail` parameter must have kind `RecordRow`.

There is intentionally no `TypeNode::RecordRowParameter`. A row-kinded binder is represented by `TypeParameterRecord` plus its `KindNode::RecordRow` kind and is referenced from the open-record tail.

## 7.3 Why no core `RecordRowNodeId` in v2

Revised Spec 05 may use `RecordRowId` internally because the compiler needs canonical row terms and solver results. Durable metadata does not yet need a standalone first-class reflected row value.

For v2, the artifact needs to transport exactly these public facts:

- a generic parameter is row-kinded;
- a record is closed or has a stable row-parameter tail;
- known fields and their proper types;
- deterministic semantic identity.

Encoding the row inline in `OpenRecordTypeRef` is sufficient and avoids a second graph/table that has no independent public consumer yet.

If a later feature requires durable standalone row terms—for example proof artifacts containing solved row expressions or public row-value reflection—add a separately versioned `RecordRowNode` table or `advanced.record_rows.vN` extension. Do not turn a speculative future need into v2 core complexity.

## 7.4 Scoped type-lambda wire shape

A type lambda may eventually bind a row-kinded parameter:

```phalcom
<R: RecordRow> =>> #{ name: String, | R }
```

The scoped metadata graph therefore needs an open-record representation that can point either to a lambda-bound row binder or a stable free row parameter.

Modify `phalcom-type-meta/src/scoped_type.rs`.

Add:

```rust
#[derive(Clone, Debug, Eq, Hash, PartialEq, Deserialize, Serialize)]
pub enum ScopedRecordTailRef {
    Bound {
        depth: u32,
        index: u32,
    },
    FreeParameter(StableTypeParameterRef),
}

#[derive(Clone, Debug, Eq, Hash, PartialEq, Deserialize, Serialize)]
pub struct ScopedOpenRecordTypeRef {
    pub fields: Box<[ScopedRecordFieldRef]>,
    pub tail: ScopedRecordTailRef,
}
```

and the additive variant:

```rust
ScopedTypeNode::OpenRecord(ScopedOpenRecordTypeRef)
```

Do not coerce a row-bound lambda variable into `ScopedTypeNode::Bound` in a place interpreted as a proper type. The bound identity is used in a **row-tail slot**, whose expected kind is `RecordRow`.

## 7.5 Fingerprints

Closed v1 records keep their existing fingerprint rule and tag.

Open records use a new form tag and hash:

```text
OPEN_RECORD_TAG
field_count
for each field in canonical order:
    field_name
    field_type_structural_fingerprint
tail_owner_stable_identity
tail_index
```

For a scoped open record, the tail contribution is either:

```text
BOUND_ROW_TAIL_TAG + depth + index
```

or:

```text
FREE_ROW_TAIL_TAG + stable-owner identity + parameter index
```

Lambda binder *names* never enter the hash.

## 7.6 Canonical field requirements

The validator and exporter must enforce:

- fields sorted by the same stable field-name ordering used by canonical semantic rows;
- no duplicate labels;
- every field child node has kind `Type`;
- an open tail references an existing type-parameter record;
- that parameter's kind node is exactly `RecordRow`;
- a closed record cannot secretly carry a synthetic/open tail through an extension;
- solver-local row variables are unrepresentable in the schema.

The metadata layer must never repair duplicate fields by choosing first/last. Invalid canonical input is an exporter/internal error; malformed serialized input is rejected.

## 7.7 Feature-bit law

Exporter rule:

```text
features.record_rows == true
iff
bundle contains at least one of:
  KindNode::RecordRow
  TypeNode::OpenRecord
  ScopedTypeNode::OpenRecord
  TypeParameterRecord whose kind resolves to RecordRow
```

A conservative producer may set the bit when `RecordRow` appears in an arrow kind even if there is no open record.

A producer must not set the bit merely because it supports record rows in principle.

# 8. Semantic-export integration for record rows

This workstream depends on **Spec 05's row semantic core**. 02.5 must not implement a second row store or solver inside `metadata/export.rs`.

## 8.1 Expected upstream semantic API

Before this section is implemented, the semantic layer must expose an equivalent of:

```rust
KindData::RecordRow

RecordRowData {
    fields,
    tail: RecordRowTail,
}

RecordRowTail::{
    Closed,
    Parameter(TypeParameterId),
}

RecordTypeData {
    row: RecordRowId,
}
```

or a semantically equivalent compact representation chosen by the Spec-05 implementation.

The metadata adapter must use public/internal semantic accessors, not inspect solver-private union-find state.

## 8.2 Files

Expected modifications after the Spec-05 row core exists:

```text
phalcom-semantic/src/metadata/export.rs
phalcom-semantic/src/metadata/mod.rs                # only exports if needed
phalcom-semantic/src/types/kind.rs                  # owned by Spec 05, consume here
phalcom-semantic/src/types/record_row.rs            # owned by Spec 05, consume here
phalcom-semantic/tests/metadata_export.rs
```

Do not add row-solver logic under `phalcom-semantic/src/metadata/`.

## 8.3 Export rules

When exporting a record type:

```text
row.tail == Closed
    -> emit existing TypeNode::Record(fields)

row.tail == Parameter(R)
    -> export R's TypeParameterRecord
    -> verify R.kind == RecordRow
    -> emit TypeNode::OpenRecord { fields, tail: stable(R) }

row.tail contains solver-local RecordRowVarId
    -> impossible for publishable canonical input;
       return MetadataExportError::NonPublishableRecordRow / equivalent
```

Do not zonk/solve the row inside the exporter. The exporter consumes a published canonical semantic product only.

## 8.4 Row parameter export

`MetadataExporter::export_type_parameter` already exports arbitrary `KindId` values. Once `KindData::RecordRow` exists, this same path should emit a `TypeParameterRecord` whose `kind` points to a `KindNode::RecordRow` node.

Do not call `store.parameter_form(row_parameter)` if that operation would create an ordinary type-form node. Revised Spec 05 explicitly forbids representing a row binder as `TypeData::Parameter`.

Any generic-signature export path that currently assumes every parameter can be materialized as a `TypeId` must be audited.

## 8.5 Generic constraints and row parameters

Schema v2 does **not** generalize `GenericConstraintRef` from `TypeNodeId` operands to a universal multi-domain term merely in anticipation of future row constraints.

Initial rule:

- row parameters may be declared and used as record tails;
- row solving uses internal row constraints from Spec 05;
- public source constraints directly comparing row terms remain gated unless a later semantic decision explicitly ratifies them.

If future source syntax requires `where R == S` for `RecordRow` terms, create a new schema version with typed constraint operands such as:

```rust
ConstraintOperandRef::{Type(TypeNodeId), RecordRow(...)}
```

Do not coerce a row into `TypeNodeId` to reuse the v1 constraint enum.

# 9. Record-row validator details

Modify `phalcom-type-meta/src/validate.rs`.

## 9.1 Kind validation

Extend the kind-node match:

```rust
KindNode::RecordRow => {
    // atomic; no child edges
}
```

Fingerprint validation must use a distinct stable tag from `Type` and `Arrow`.

`RecordRow` is atomic. Do not make it a child of `Type`, and do not derive `Type :: Type`-like relationships.

## 9.2 Open-record validation

For `TypeNode::OpenRecord(record)`:

1. require schema version >= 2;
2. require `features.record_rows`;
3. require the node entry's own `kind` to resolve to `KindNode::Type`;
4. validate every field child is backward/topological and has proper kind `Type`;
5. validate canonical field-name order and uniqueness;
6. locate `record.tail` in the parameter table by stable owner/index;
7. require the tail parameter's referenced kind to resolve to `KindNode::RecordRow`;
8. recompute and compare structural fingerprint;
9. charge node/edge/string budget exactly as for closed records plus the tail identity.

For `ScopedTypeNode::OpenRecord`:

- `Bound { depth, index }` must be inside a lambda scope;
- the referenced lambda binder kind at `(depth,index)` must be `RecordRow`;
- `FreeParameter` must resolve to a parameter record of kind `RecordRow`;
- field children remain scoped proper-type nodes;
- the open record itself has kind `Type`.

This requires scoped validation to carry a stack of lambda parameter-kind slices, not only binder counts.

## 9.3 New validator errors

Add precise variants equivalent to:

```rust
RecordRowFeatureRequired
RecordTailParameterMissing { owner, index }
RecordTailKindMismatch { expected: RecordRow, actual: KindNodeId }
RecordFieldOrderInvalid { node: u32 }
RecordDuplicateField { node: u32, field: Box<str> }
ScopedRecordTailOutOfScope { node: u32, depth: u32, index: u32 }
ScopedRecordTailKindMismatch { node: u32, depth: u32, index: u32 }
```

Use bounded display for owner/field data in error formatting.

## 9.4 Hostile-input tests

Add tests for:

- v2 open record with v1 header;
- v2 open record with feature bit false;
- tail parameter missing;
- tail parameter kind `Type` instead of `RecordRow`;
- duplicate labels;
- noncanonical label order;
- child kind not `Type`;
- scoped row tail escaping lambda depth;
- scoped row tail pointing to a `Type` binder;
- extremely wide row hitting node/edge/string budgets;
- nested row-bearing lambda depth hitting lambda budget;
- malformed fingerprint;
- attempt to encode a solver-local row variable through any public schema constructor should fail at compile/API level because no variant exists.

# 10. Runtime loading and reification of row-bearing records

02.5 should require as little runtime-specific machinery as possible.

## 10.1 No runtime `RecordRow` value token on ordinary objects

A record value still has its existing runtime class/representation. A static form:

```text
#{ name: String, | R }
```

does not attach `R` or any row identity to the runtime record value.

## 10.2 Base metadata loading

`phalcom-core/src/typing/loader.rs` can continue loading the validated bundle as immutable metadata. No special row allocation is needed during load.

The loader must reject a required schema-v2 row feature if the runtime build does not advertise support for it.

If extension capability negotiation is later centralized, reuse it; do not introduce a second row-specific feature registry.

## 10.3 Descriptor reification

The existing `reify_type_form` path does not recursively inspect structural children before allocating a synthetic descriptor. That is good and should remain true for open records.

An open-record type reifies as the same ordinary reflection descriptor category used for record types. It does **not** allocate a specialized runtime class and does not allocate a separate descriptor for every field or for the row tail until a public reflection operation asks for them.

## 10.4 Kind reflection

When Spec 03 kind reflection is implemented, `RecordRow` is one atomic kind descriptor/singleton analogous in role—not identity—to `Type`.

Exact public class/selector details remain Spec 03 authority.

02.5 requires only that the runtime metadata kind handle can distinguish `RecordRow` from `Type` and arrows.

## 10.5 `inspect.rs`

When row reflection lands, update `phalcom-core/src/typing/inspect.rs` so display of a base open record is deterministic:

```text
#{ name: String, age: Int, | R }
```

or the exact canonical display grammar chosen by Spec 04/03.

The display helper must:

- obey the existing depth limit;
- not recursively materialize descriptors;
- render tail parameter through stable metadata identity/presentation;
- avoid inventing a name if presentation metadata is unavailable; use a deterministic fallback based on owner/index.

`equivalent` continues to use structural fingerprints for base/base handles. The open-record fingerprint must therefore incorporate the stable tail identity.

## 10.6 Runtime overlay

Do not expand `RuntimeOverlayTypeNode` for open-record construction as part of the first row-metadata patch unless Spec 03's runtime record-construction workstream is ready.

Base artifact reflection of open records and runtime synthesis of new open record TypeForms are separate milestones.

When runtime synthesis is later enabled, add an overlay form equivalent to:

```rust
RuntimeOverlayTypeNode::OpenRecord {
    fields: Box<[(Box<str>, RuntimeTypeRef)]>,
    tail: RuntimeRowTailRef,
}
```

with the same sorting, duplicate, kind, and budget rules. That later operation requires `ConstructTypeForms`; it does not happen during ordinary record construction.

# 11. Runtime validation boundary hardening

This section restores a valuable invariant from the earlier Spec 02 and aligns it with revised Spec 03.

## 11.1 Validation is an explicit boundary, never ambient runtime policy

The presence of semantic metadata must not make Phalcom gradually start checking every runtime operation.

The only permitted deep-validation entry points are explicit boundaries such as:

1. `TypingContext.validate` from Spec 03;
2. a runtime contract whose semantics explicitly require structural validation;
3. a selected `Dynamic` ingress/egress policy that explicitly asks for validation;
4. native/FFI boundaries with a declared runtime contract;
5. deserialization/external-data validation;
6. reflective construction or invocation when the caller explicitly requests typed validation.

A future boundary may be added, but it must be named and observable. “Metadata exists” is never sufficient authority to invoke validation.

## 11.2 Current capability architecture already supports this distinction

`phalcom-core/src/typing/capability.rs` already defines:

```rust
TypingCapability::ValidateRuntimeValues
```

and the current `TypingCapabilities::for_profile` does not grant it merely because the profile is `RuntimePublic`, `ToolingDebug`, or `Proof`.

02.5 ratifies this separation:

> **Metadata visibility and runtime-validation authority are different axes.**

Do not change `for_profile` so all public/proof contexts automatically gain `ValidateRuntimeValues`.

An explicitly privileged context/session may add the capability through the existing capability restriction/grant mechanism according to Spec 03 security policy.

## 11.3 Internal engine ownership

When Spec 03 C7 is implemented, create or use one central internal module:

```text
phalcom-core/src/typing/validation.rs
```

Suggested internal seam:

```rust
pub enum RuntimeMatchMode {
    Shallow,
    Deep,
}

pub struct RuntimeValidationPolicy {
    pub max_nodes: usize,
    pub max_depth: usize,
    pub max_elements: usize,
    pub allow_mutable_snapshot_validation: bool,
}
```

The result must project into Spec 03's `TypeRelationResult`; do not invent a public 02.5 result hierarchy.

The implementation should keep internal evidence explicit enough to distinguish at least:

```text
NominalClassEvidence
DeepCurrentStateEvidence
TrustedCallableSignatureEvidence
DynamicBoundary
UnsupportedRepresentation
```

Names may differ; the semantic distinctions may not.

## 11.4 `matches` remains shallow

For `TypingContext.matches(value, against:)`:

- class/inheritance facts are admissible;
- exact immediate/runtime representation facts are admissible;
- trusted metadata directly attached to a *runtime callable/member identity* may be admissible according to §12;
- arbitrary container/object graph traversal is forbidden;
- an erased generic origin match cannot prove the applied arguments.

Thus:

```text
matches([1,2,3], List<Int>)
```

normally returns a dynamic boundary, even though the current elements happen to be integers.

## 11.5 `validate` may inspect current state, under budgets

Deep validation may inspect standard representations for which the runtime has a sound, bounded traversal rule.

For a standard immutable/current-state container, validation may prove a statement about the checked state:

```text
validate([1,2,3], as: List<Int>) -> satisfied
```

provided every element was checked and all budgets/policies were satisfied.

For mutable containers the evidence is **snapshot evidence** only:

```text
validated at world/time/state S
```

It does not become a permanent generic invariant and does not authorize future writes.

## 11.6 No hidden validation hooks

The initial implementation must not call the deep validation engine from:

```text
VM::dispatch...
Value::class
method activation
field write
List.add / Map.put / Set.add
constructor allocation
GC
normal return handling
```

If a contract or boundary wants validation, that boundary calls the validation engine explicitly.

This rule should be visible in code ownership: `typing::validation` is imported by reflection/contract/boundary modules, not by generic dispatch/value/layout machinery.

# 12. Higher-order callable validation

The earlier Spec 02 correctly warned that higher-order callable checking is fundamentally different from nominal class matching. Revised Spec 03 defines `matches`/`validate` but does not yet fully pin the witness rule. 02.5 closes that gap.

## 12.1 Runtime class is insufficient

These facts:

```text
value.class == Closure
value.class <: Function
value.class == BoundMethod
```

do not prove:

```text
value : (Int) -> String
```

because callable subtyping involves parameter/return semantics and the runtime class alone says nothing about those specific types.

## 12.2 Authoritative witness sources

A structural callable match/validation may succeed only if the runtime can obtain an authoritative semantic callable witness such as:

1. an exact compiled `Method` mapped by `MethodSemanticIndex` to a retained `CallableSemanticRecord`;
2. a closure/function value with a future explicit side-table mapping to its canonical compiled callable signature;
3. a trusted native/FFI callable contract retained in metadata;
4. a future checked callable wrapper whose creation itself validated and freezes/delegates the contract.

The existence of a selector or arity-only runtime `Signature` is not enough.

## 12.3 Initial conservative rule

Until closure/function semantic witnesses are implemented, use:

```text
matches(functionValue, CallableType(...))
    -> DynamicBoundary(CallableSignatureUnavailable)

validate(functionValue, as: CallableType(...))
    -> DynamicBoundary(CallableSignatureUnavailable)
```

for arbitrary callable values.

For an exact reified `Method` with an authoritative side-table entry, the runtime may compare the retained semantic signature against the requested callable type using the canonical callable relation rules.

## 12.4 Never test a function by calling it

Deep validation must **never** establish callable compatibility by invoking the callable on fabricated/sample inputs.

That would be:

- effectful;
- incomplete;
- non-deterministic;
- potentially non-terminating;
- potentially destructive;
- unable to prove behavior on all valid arguments.

Higher-order evidence is contractual/static metadata or a checked wrapper—not empirical testing.

## 12.5 Variance

Where an authoritative callable signature exists, structural callable compatibility uses the same semantic rule as static callable subtyping:

- parameters contravariant;
- return covariant;
- label/rest shape must be compatible;
- generic callable signatures require their own specialization/constraint handling rather than erasing binders.

Do not implement a simplified runtime-only covariance rule.

## 12.6 Bound methods

A `BoundMethod` closes a method over a receiver. Binding changes the invocation receiver, not the canonical callable parameter/result contract of the remaining explicit argument lane.

If runtime reflection can trace a `BoundMethod` to its underlying exact `MethodObject`, it may reuse that method's semantic witness after applying the same binding/view rules as Spec 03. It must not redispatch by selector and borrow the signature of a different live method.

# 13. Advanced metadata retention after Spec 05

The four existing profiles remain. The correction is to stop treating “advanced summary” as synonymous with “proof artifact.”

## 13.1 Profile is not the only retention dimension

The artifact already has:

```rust
MetadataFeatures::advanced_sections
```

Use it.

Define compiler/build retention policy conceptually as:

```rust
pub struct MetadataRetentionPolicy {
    pub profile: MetadataProfile,
    pub advanced_sections: BTreeSet<FeatureSectionId>,
}
```

This policy is a producer configuration. The artifact header records what was actually retained.

The exact compiler configuration type may live outside `phalcom-type-meta`; the schema crate should not depend on compiler flags.

## 13.2 Lightweight public summaries

The following Spec-05 sections may be retained in a `RuntimePublic`, `ToolingDebug`, or `Proof` artifact when explicitly enabled:

```text
advanced.effects.v1
advanced.exits.v1
advanced.termination.v1
advanced.contracts.v1
```

These sections can support reflection such as:

```text
method effects
method known raises/exits
method totality requirement/result
canonical contract summaries
```

without carrying verification conditions or solver certificates.

## 13.3 Heavy proof retention

`advanced.proofs.v1` is normally permitted only under `MetadataProfile::Proof`.

It may contain:

- normalized obligation IDs/fingerprints;
- proof result;
- assumptions;
- trust tier;
- backend identity/version;
- proof-kernel identity/version where applicable;
- certificate/evidence bytes or stable external reference;
- validated counterexample/source map information.

Do not require `Proof` merely to inspect an effect or termination summary.

## 13.4 RuntimeMinimal

`RuntimeMinimal` continues to retain only executable semantic roots and metadata genuinely needed for enabled runtime boundaries.

Advanced summaries are absent by default.

A future execution feature may require one lightweight summary in RuntimeMinimal, but that must be an explicit dependency—not “Proof includes it so retain Proof.”

## 13.5 Capability projection

Spec 03/05 may later add a capability such as `ObserveAnalysisSummaries`. Do not reuse `InspectProofs` to gate ordinary effect/exit/termination summary observation.

The metadata layer only needs to preserve the distinction so the public API can enforce it cleanly.

## 13.6 Extension fingerprints remain independent

Each section retains its own semantic fingerprint and schema version.

Changing proof evidence must not force the core type graph fingerprint to change.

Changing effect summary may invalidate proof artifacts that depend on it, but dependency invalidation is a semantic/proof concern; the metadata bundle itself does not merge the two records.

The revised Spec 02's core `TypeUseRecord` should remain compact. Rich provenance is optional and can be large.

Exact step enums are gated on the compiler query products; do not invent them in metadata before the semantic layer can produce them authoritatively.

This section can power:

- “why this type?” hover explanations;
- inference provenance;
- “why this method?” dispatch explanations;
- generic specialization traces;
- diagnostic cause chains;
- post-build semantic inspection.

The normal LSP should still read compiler snapshots directly during source editing. Serialized provenance is for artifact/debug tooling and reproducibility, not a required detour for editor queries.

When serialized diagnostic/provenance support lands, use an occurrence-to-diagnostic association equivalent to:

```rust
pub struct TypeUseDiagnosticLinks {
    pub occurrence_index: u32,
    pub diagnostics: Box<[StableDiagnosticRef]>,
}
```

The actual diagnostic record remains source-owned by the compiler semantic snapshot. `StableDiagnosticRef` must identify retained diagnostic data without copying diagnostic prose into canonical type identity. If no stable artifact diagnostic table exists yet, defer this link rather than collapsing several diagnostics into `TypeUseStatusRef::Invalid(one)`.

# 15. Foreign/native boundary extension contract

02.5 does not design Phalcom's full FFI. It preserves the metadata architecture needed to add one without another core-schema rewrite.

## 15.1 Information a foreign boundary may need

A future typed foreign/native boundary must be able to attach, where applicable:

```text
ABI identity/version
parameter/result semantic contract
ownership/lifetime policy
calling convention / representation contract
effects
exits/raises
blocking/scheduling behavior
trust/opacity classification
source/native symbol identity
```

These are independent facts. For example, `pure` does not imply “safe ABI,” and a sound type contract does not imply ownership correctness.

## 15.2 Extension namespace

Reserve a family such as:

```text
runtime.foreign_boundary.v1
```

or the final namespace selected by the FFI specification.

Do not add ABI/ownership fields to every `CallableSemanticRecord` before an FFI design exists.

## 15.3 Native metadata today

`phalcom-native-meta` already carries typed parameter/result, effects, raises, flow, trust, ABI mode, and source identity for native primitives. That producer remains a privileged source of semantic/native facts.

02.5 requires only that future foreign-boundary metadata lower into or extend the same stable semantic identity system. Do not create an unrelated FFI type graph.

## 15.4 Opaque boundaries

If a foreign/native boundary cannot provide a sound semantic type/effect/ownership contract, metadata records explicit opacity/trust-boundary information.

Opacity must not become:

- `Unknown` canonical type node;
- `pure`;
- `total`;
- `Proven`;
- a successful generic match.

# 16. Forward-compatibility ledger

The v2 changes must not encode speculative variants now, but the architecture must not preclude later versioned addition of:

- prenex kind parameters/schemes;
- standalone durable row terms if a real consumer emerges;
- recursive type/row binders with an explicit recursion encoding;
- intersections/refinement/singleton types;
- protocol/conformance metadata;
- associated types;
- richer generic constraints;
- variant rows;
- effect rows and effect polymorphism;
- exhaustive-pattern metadata;
- foreign ABI/ownership/lifetime contracts;
- persistent checkable proof certificates;
- per-expression debug facts;
- richer inference/dispatch provenance.

“Must not preclude” means:

- stable IDs are not derived from enum ordinal alone;
- unknown required features fail cleanly;
- optional extension sections can be skipped by execution consumers;
- current enums do not reserve fake semantic members with undefined meaning;
- raw compiler/runtime IDs do not leak into artifacts;
- future additions can be versioned without changing runtime class/selector identity.

It does **not** mean implementing placeholders such as `Any`, `Intersection`, `EffectRow`, or `KindParameter` in schema v2.

# 21. Performance and memory gates

02.5 exists partly to preserve a performance architecture. The amendment must not turn richer metadata into a runtime tax.

## 21.1 No-reflection program

A program that does not request runtime typing reflection/validation must not perform:

- row traversal;
- type-node traversal;
- descriptor allocation;
- generic validation;
- callable-contract validation;
- advanced-extension decoding beyond what loader policy requires for artifact acceptance.

Record-row metadata may occupy artifact/immutable metadata memory when retained, but ordinary object execution must not consult it.

## 21.2 Artifact size

Measure v1 and v2 metadata for:

- universe;
- std;
- representative non-row project;
- representative row-heavy project.

For a project with no row-aware forms, schema-v2 producer output should differ only by header/version/feature mechanics required by the final implementation; it should not bloat every record into a larger row payload.

This is another reason closed records retain the v1 `Record` form.

## 21.3 Validation cost

Deep runtime validation is charged explicitly to its policy budget.

At minimum measure:

- values visited;
- type nodes visited;
- recursion depth;
- cycle-table entries;
- elapsed work counter;
- budget termination reason.

No runtime deep-validation budget may fall back to success when exhausted.

## 21.4 Descriptor allocation

Reifying an open record with 100 fields initially allocates one root descriptor, not 100 field descriptors plus a tail descriptor.

Indexed field access materializes only the demanded child according to Spec 03's lazy API.

# 23. Deletion and cleanup criteria

# 27. Final normative checklist

An implementation conforms to 02.5 when all applicable statements below are true:

1. Spec 02's implemented architecture remains the baseline; 02.5 is a delta, not a rewrite.
2. No 02.5 code change collides with unfinished Spec-02 Step-3 artifact carriage.
3. Schema support has an explicit minimum/current version range.
4. Checked-in v1 artifacts remain readable by a v2-capable decoder.
5. Existing closed `TypeNode::Record` remains the closed-record wire form and retains its semantic fingerprint behavior.
6. Schema v2 adds `KindNode::RecordRow` without making it a proper type.
7. Schema v2 adds an open-record form whose tail is a stable row-kinded parameter.
8. A row-kinded generic parameter is never emitted as an ordinary `TypeNode::Parameter` proper type.
9. Scoped type lambdas can carry row-bound open-record tails without confusing row binders with proper type terms.
10. Open-record known fields are sorted, unique, and proper types.
11. Row-tail parameters resolve and have kind `RecordRow`.
12. `RecordRowVarId` and all solver-local row state are unrepresentable in durable metadata.
13. The metadata exporter does not run the row solver.
14. Loading row metadata allocates no synthetic descriptors by itself.
15. Reifying a row-bearing record remains lazy and creates no specialized runtime class/metaclass.
16. Ordinary values receive no row/generic runtime token.
17. Metadata profile and runtime-validation capability remain separate axes.
18. `RuntimePublic`, `ToolingDebug`, and `Proof` do not automatically authorize deep runtime validation.
19. Shallow `matches` never manufactures erased generic evidence.
20. Deep `validate` is explicit, capability-checked, bounded, and current-state-only for mutable structures.
21. Callable runtime class/arity alone cannot prove a structural callable type.
22. Higher-order success requires an authoritative semantic callable witness or a future checked wrapper.
23. Runtime validation never tests a callable by executing it on fabricated inputs.
24. Effects, exits, termination, contracts, and proofs remain independent semantic products.
25. Lightweight advanced summaries may be retained without the heavy Proof profile when explicitly enabled.
26. Proof evidence remains separately versioned and trust-aware.
27. Rich inference/dispatch provenance is optional ToolingDebug extension data, not canonical type identity.
28. Future foreign/native boundary metadata can carry ABI/type/ownership/effect/exit/trust information through versioned extension without a second type graph.
29. Unknown required extensions/features reject; unknown optional execution-irrelevant extensions may be skipped.
30. No 02.5 feature changes `Value`, selector identity, ordinary method dispatch, object layout, or class/metaclass wiring.
