# Suspending a computation the interpreter didn't finish walking

## The loop that calls itself

A bytecode interpreter, reduced to its essence, is a `while` loop with a `match` in it: fetch the next instruction, dispatch on its opcode, mutate some frame state, repeat. Everything the language can do — arithmetic, message sends, control flow — eventually bottoms out as a transformation this loop performs on data it owns: an operand stack, a chain of call frames, an instruction pointer. That ownership is the whole point. Because the loop owns its frames as *data* — a `Vec<Frame>` or equivalent, sitting on the heap or in a runtime-controlled arena — it can inspect them, copy them, serialize them, or simply stop looping and leave them sitting there. Nothing about the CPU's own call mechanism is involved in running a Lua-shaped or Python-shaped bytecode program from frame to frame; the interpreter's `call` instruction just pushes a new `Frame` struct and continues the same loop iteration.

This is why suspending such a computation looks, at first, almost embarrassingly easy. To pause a fiber, you don't need to unwind anything in the operating-system sense. You return a `Suspended` status out of the loop's entry point, carrying the frame stack (or a handle to it) with you. To resume, you call the entry point again, hand it the same frame stack, and the loop picks up exactly where it left off, because "where it left off" was never encoded in anything except data the runtime controls. No registers to save, no stack pointer to redirect, no operating system involved. This is the baseline intuition every design in this document either preserves, pays to extend, or abandons outright.

The complication is that real runtimes are not closed loops. A standard library needs to sort a collection with a user-supplied comparator, map a user block over every element, run a user's `catch` handler, or dispatch a reflective `invoke`. The cleanest way to implement all of these, from the host language's side, is to write ordinary host-language code — Rust, C, whatever the runtime is implemented in — that, partway through its own execution, calls back into the interpreter to run the user-level block, gets a result, and keeps going. This is **native re-entrancy**: the interpreter's own entry point gets invoked again, not from the top level where the program started, but from inside a host-language stack frame that itself sits *underneath* one of the interpreter's own frames, several layers down.

Once that happens, the tidy story above stops being true. The live computation — the thing you'd need to freeze in order to suspend it — is no longer just a `Vec<Frame>` sitting in memory the runtime owns. It's interleaved: some frames belong to the runtime's own frame stack, but between two of them sits a native call frame — the sort routine's frame, mid-loop, holding a Rust iterator and a partially-built result — that lives on the **host stack**: the actual machine call stack, laid out and unwound by the C/Rust calling convention and the CPU's `call`/`ret` instructions, not by anything the interpreter's data structures know about. That native frame has no serializable representation the runtime can save. It is not data. It is *control* — and control, in the native ABI, is either currently executing or it doesn't exist; there's no third state where it sits paused, inspectable, movable.

This is the actual problem this document is about, stated precisely: **a suspend point that is lexically underneath a native activation record the runtime does not own and cannot relocate cannot be captured by any suspension mechanism that only knows how to save runtime-owned data.** Everything downstream — the restriction, the escape hatches, the garbage-collector consequences, the naming of "function coloring" — is this one fact, worked out along different axes. The host stack **colors** a runtime's suspend capability in exactly the sense that a type system colors functions `async`/non-`async`: it silently partitions call sites into "you may suspend here" and "you may not," except the partition is drawn by the *shape of the call graph at runtime*, not by anything visible in the source.

## What "suspend" actually demands, decomposed

Before ranking the design space, it's worth pulling apart what suspending a computation requires, because the branches below differ in exactly which piece they buy and which they defer.

1. **Capture** — record enough about the current point of execution (instruction pointer, operand stack contents, local variables, the chain of pending calls) to reconstruct it later.
2. **Ownership** — the captured state must belong to something the suspension mechanism controls: it must be legal to stop touching it, let arbitrary other code run, and come back to it unchanged.
3. **Relocation** (sometimes) — if the runtime moves memory around (a moving garbage collector, a growable stack), the captured state must either be immune to that movement or updated consistently when it happens.
4. **Resumption** — a way to hand control back to exactly the point captured, with the illusion (from the suspended computation's point of view) that no time passed and nothing else ran in between.

A frame stack the interpreter's loop owns satisfies (1)–(4) almost for free: capture is "stop dereferencing this `Vec`," ownership is trivially true (the runtime allocated it), relocation is whatever the allocator already does to heap data, and resumption is "call the loop again with this `Vec`." A native call frame satisfies none of them without help: capture would mean serializing raw stack memory and CPU registers, ownership is contested (the OS/ABI, not the runtime, decides when that frame's memory is valid), relocation is actively hostile (moving a live stack frame while it's suspended is exactly the operation C calling conventions assume never happens), and resumption would require jumping back into the *middle* of a native function — not a thing `call`/`ret` can express.

Every design below is an answer to "so what do we do about native frames."

## Restricted suspension: refuse to let the problem exist

The simplest answer is to define the domain of the suspend operation to be exactly the frames the interpreter loop owns, and raise an error the moment a `yield` is attempted while any native re-entrant frame is live between the yield point and the fiber's own entry into the loop. Concretely: the runtime tracks, per fiber, whether it is currently executing "at native-call depth zero" relative to that fiber's start — i.e., whether every frame between here and the top is a runtime-owned `Frame`, not a host stack frame from a callback re-entry. If a native combinator (sort, map, forEach, a reflective call) is on the host stack anywhere in the chain, yielding is refused.

This is not a strawman option chosen to be knocked down; it is the design most embeddable interpreters reach for first, and for good reason. It costs nothing at steady state — the "am I at native depth zero" check is a counter increment/decrement around each re-entrant call, and the suspend operation itself is exactly the free `Vec`-swap described above. It requires no new stack-switching machinery, no new garbage-collector contract, no assembly. And it is *sound by construction*: nothing it allows can ever produce a corrupted native frame, because it never tries to freeze one.

What it forecloses is real, though, and it's not a narrow inconvenience: it means the language's own standard library becomes a map of where you may and may not suspend, and that map is drawn by implementation choices in the library, not by anything the language's grammar exposes. A user who writes `list.forEach(fn(x) { fiber.yield(x) })` gets a runtime error not because `yield` is semantically nonsensical there, but because whoever wrote `forEach` happened to implement it as a native loop that calls back into the interpreter rather than, say, desugaring to a bytecode-level loop over an iterator protocol. "The distinguishing programs" section below argues this is a much stranger property than it first looks.

It's worth noticing why this design pairs so naturally with **asymmetric** coroutines — `yield` always hands control back to whoever called `resume`, the way a subroutine call always returns to its caller, just resumably — rather than **symmetric** ones, where any coroutine explicitly transfers control to any other named peer with no privileged "caller" to return to. Asymmetric yield/resume has a built-in LIFO discipline: if fiber A resumes fiber B, A's continuation is exactly "on hold" until B either finishes or yields, at which point control returns to precisely A — which is just the ordinary call-stack discipline, one level up, and is why it maps so cleanly onto "swap out a frame stack, swap it back in." Symmetric transfer breaks that discipline on purpose: X can transfer to Y, Y can transfer to Z, and Z can transfer straight back to X, skipping Y entirely, which is not a stack-shaped relationship at all — there is no ambient "caller" to fall back to. That isn't a style preference; it changes which implementation strategies are even available. A design that leans on the frame-stack-swap intuition from the opening of this document gets asymmetric yield/resume almost for free and has to work to support symmetric transfer at all (it needs to keep every fiber's continuation addressable independently rather than nested LIFO-style), while a fully general stackful implementation — independent native stacks, switched by pointer — supports symmetric transfer just as easily as asymmetric, because "switch to stack X" never assumed a caller to return to in the first place.

## Full trampoline: buying back generality by rewriting the library, one primitive at a time

If native re-entrancy is the problem, the other side of the same coin is: stop re-entering natively. A **trampoline** (the general technique is also called **de-recursion**) restructures a function that would otherwise call itself or call back into an interpreter recursively so that, instead, it returns a description of the next step to a driving loop, which performs that step and calls back in — flattening what was native call-stack recursion into loop iteration over runtime-owned data. Applied to a callback-taking primitive like `sort` or `forEach`, this means: instead of the Rust `sort` function directly, recursively calling `interpret()` to run the comparator and then continuing its own Rust loop with the result, `sort` pushes a **continuation frame** — an ordinary `Frame`-shaped piece of data describing "I am partway through a merge sort, here is my partition state, next call the comparator on these two elements and hand the boolean back to me at this resumption point" — onto the *interpreter's own* frame stack, and returns to the interpreter's main loop rather than calling into it. The comparator call is now just another push in the same loop iteration the interpreter was already running. Nothing native is left mid-flight. A suspend at that point is exactly as free as a suspend anywhere else, because there is no longer an "anywhere else": every combinator's intermediate state now lives as runtime-owned data.

This is the mechanism that actually removes the restriction, and it deserves the sharpest question in this document: **is going from restricted to full-trampoline additive, or does it require rewriting what came before?**

The honest answer splits along two different meanings of "additive," and the split is the interesting part.

*At the level of programs*, it is additive: no program that worked under restricted suspension stops working once some combinator gets trampolined, and programs that used to hit "cannot suspend here" for a specific combinator simply stop hitting it once that combinator is converted. You can trampoline `forEach` this week and leave `sort` throwing the restricted-suspension error next month, and both states are internally consistent. The restricted domain doesn't have to shrink to empty in one commit; it can shrink combinator by combinator, monotonically, forever.

*At the level of engineering*, it is not additive at all — it is a rewrite, and a non-trivial one, repeated once per callback-taking primitive. The reason is that what makes native recursion convenient in the first place is that the host language's own call stack and local variables are already an implicit state machine: "where am I in this loop" is encoded for free as an instruction pointer plus some locals, maintained by the compiler that built the host binary. Trampolining a primitive means taking that implicit state machine and making it *explicit*: designing a `struct` or `enum` that names every point the loop could be paused at, and every piece of transient state that has to survive the pause (a merge sort's pending partitions are not the same shape as a `reduce`'s running accumulator, which is not the same shape as a generic `forEach`'s cursor). There is no generic transformation that does this automatically for arbitrary native code; each primitive's author has to re-derive its state machine by hand. Some are easy (`forEach` is close to a single index). Some are genuinely painful — de-recursing a recursive sort so that its call stack becomes an explicit stack of pending partitions, stored as runtime-owned frames rather than native recursion, is exactly the kind of transformation compiler courses assign as an exercise precisely because it's non-obvious.

So the bill for full trampolining is not paid by "the coroutine implementation" at all — the fiber machinery itself barely changes. It's paid by **every native primitive that takes a callback**, and by extension by whoever maintains the standard library, because the calling *protocol* between a primitive and the interpreter loop has to change globally: a primitive can no longer simply `return value`; it has to be able to return "here is a continuation frame, push it and re-enter the loop instead of returning to me." That's a change to the interpreter's dispatch architecture, not a local patch, even though each individual primitive's conversion is otherwise independent of the others. It also has a standing performance tax that restricted suspension doesn't: every trampolined call now allocates and pushes an explicit continuation frame where native recursion would have used a free host stack frame, and the interpreter's main loop now has an extra kind of state (paused primitives) to dispatch on.

The upshot: restricted → full-trampoline is a one-way ratchet that you can turn as slowly as you like, at a cost proportional to how much of the standard library you're willing to rewrite, paid mostly outside the fiber subsystem. It is never something you get by flipping a flag.

## Stackful coroutines: buy the generality wholesale, and hand the bill to the garbage collector

There's a second way to make native re-entrancy suspendable, which doesn't touch the standard library at all: give every fiber its own genuine native stack — a separate region of memory with its own stack pointer — and implement "suspend" as *switching which stack the CPU's stack pointer refers to*, via `makecontext`/`ucontext`, hand-written assembly, or a library that wraps the same idea (Rust's `corosensei` and `generator` crates, Go's runtime stacks, POSIX ucontext, Windows fibers). Suspending a fiber that's ten native frames deep inside a `sort` comparator callback is now no different, mechanically, from suspending one that's at the top level: you don't unwind anything, you don't need continuation frames, you just stop running instructions on that stack and point the CPU somewhere else. When you resume, the parked stack's frames are exactly as the ABI left them — locals, return addresses, saved registers, all still there — because nothing ever destroyed them. Every native call site becomes suspendable, unconditionally, with no per-primitive rewrite. This is the option that actually earns the restriction/full/stackful trilogy its name: it doesn't chip away at the restricted domain, it deletes the domain distinction outright.

The classic prose bill for this is portability and `unsafe`: hand-rolled context switching means architecture-specific register-save code, guard pages to catch stack overflow, and code that by its nature defeats a memory-safety checker (you are, after all, constructing a valid call stack out of nothing and later resuming into it as though a `call` instruction had put it there). That bill is real, but it is not the main one, and fixating on it understates what stackful coroutines actually cost.

### The bill is paid in garbage-collection terms

Any runtime with a tracing garbage collector needs to find the **roots** — the set of live references the collector must not reclaim, and (if the collector moves objects) must rewrite in place when it relocates them. In a single-stack interpreter, "the roots on the stack" means "the operand stack and locals of the one call chain that's currently executing," and a collector can arrange to be invoked only at points where it fully understands that chain's shape (a **safepoint**), because there's exactly one stack, and it's either idle (between top-level operations) or in a state the collector's author fully controls.

Stackful coroutines multiply this by the number of live fibers. Every suspended fiber is a parked native stack, frozen at whatever native program counter it happened to be executing when it yielded — which could be inside a leaf utility function, inside a library call, inside FFI, anywhere. That stack is a root set the collector must be able to find, and it did not stop at a boundary the collector's author chose; it stopped wherever the program happened to call `yield`. This forces one of two expensive commitments:

- **Conservative stack scanning**: treat every word in every parked stack that *looks like* it could be a valid heap pointer (falls in an allocated region, is suitably aligned) as if it were one, and keep it alive just in case. This is cheap to build but permanently forecloses a fully precise, *compacting* collector for anything reachable from a parked stack — you cannot safely overwrite a word on that stack with a new address, because you don't actually know it's a pointer rather than an integer that happens to share its bit pattern. At best you can pin the objects it might reference and leave them where they are, giving up the ability to compact around them.
- **Precise stack maps everywhere**: have the compiler emit, for every function, at every point a suspension could freeze it, metadata describing exactly which stack slots hold live references and of what shape. This makes full compaction possible even through parked stacks, but it means the compiler's codegen and the collector are now coupled at the level of *every function that might ever appear in any fiber's call chain* — not just runtime-internal code, but arbitrary user code, arbitrary FFI shims, everything. That is a whole-compiler commitment, not a coroutine-module one.

Either way, the deciding subsystem is the garbage collector (and, for the precise route, the code generator), not the fiber implementation, which by comparison is a few dozen lines of stack-pointer swapping. This is the sense in which "a parked native stack is a GC root the collector must scan *and potentially relocate*" is the single heaviest bill in this entire design space: it's not a local cost to the coroutine feature, it's a global constraint on what kind of collector the runtime is allowed to have, forever, for every object reachable from any stack, not just the ones fibers touch.

This also answers the reversibility question directly. **Is stackful coroutines → anything reversible?** No, in the same asymmetric sense as before but sharper: once user code depends on suspending through arbitrary native depth, you cannot restrict that back down without breaking programs that rely on it — but more importantly, the collector's scanning discipline (conservative-and-non-compacting, or precise-with-universal-stack-maps) is now baked into the codegen/runtime contract broadly, for code that has nothing to do with coroutines. Walking it back to a simpler, single-stack-precise design is not a coroutine-subsystem change; it's a collector rewrite touching every allocation site in the runtime. Compare this to restricted → trampoline, where an unconverted primitive just keeps throwing its restriction error forever with zero effect on anything else: that's a reversible-in-place, per-primitive decision. Stackful is a whole-runtime, one-way door. It commits far more of the system, and it commits it in a subsystem (the collector) that has nothing conceptually to do with coroutines at all.

## The outer edges: preemption, and the adjacent axis

**Preemption** — running fibers as real OS threads, or scheduling them with a timer interrupt rather than a voluntary yield — is the boundary case that removes the suspend-point question by removing the *voluntariness* of suspension: control can be taken away at literally any instruction, not just at points the program names with a `yield` call, because the OS scheduler (or a signal handler) does the taking, invisibly to the running code, and resumes it later with no semantic discontinuity the program can observe. That symmetry is exactly why it's a different kind of suspension than everything above — cooperative yield is a visible event the suspended code participates in (a fiber "knows" it yielded); OS preemption is not (a thread doesn't know it was descheduled). The bill shifts accordingly, away from "can this specific call site suspend" and onto the memory model: multiple stacks now genuinely execute concurrently rather than merely being parked one at a time, so the collector needs either a global stop-the-world synchronization point across every thread or a fully concurrent collector design, and the language needs real synchronization primitives and a race detector, because two fibers can now observe each other's half-written state, a hazard that simply cannot occur when only one stack is ever running at a time.

The adjacent axis worth naming once and setting aside: **resumable exception handling**, Smalltalk-style, where an unhandled condition suspends the failing computation (rather than unwinding it) so a handler can inspect it and choose to resume execution from the exact point of failure — this needs the identical property (the failing frame chain must be owned, inspectable, non-destroyed data, not a discarded native stack) triggered by a signal instead of a voluntary call, and everything argued above about native re-entrancy applies to it unchanged.

## The distinguishing programs

Here is the pair that makes the restriction concrete rather than abstract. Assume a runtime whose compiler lowers a `while` loop to backward jumps inside a single bytecode chunk (the loop body never leaves the code object it's compiled into), and whose standard library implements `forEach` as a native routine that takes a block argument and calls back into the interpreter once per element.

```
// Program A
i = 0
while (i < n) {
  fiber.yield(i)
  i = i + 1
}
```

```
// Program B
list.forEach(fn(x) {
  fiber.yield(x)
})
```

Program A suspends without incident, in every design discussed above including the cheapest, restricted one. The entire loop — condition check, body, increment, back-edge — is bytecode inside one chunk, executed by repeated iterations of the interpreter's own loop. There is no native call frame between the `yield` and the interpreter's entry point; every frame in the chain is a runtime-owned `Frame`.

Program B, under a restricted design, throws. The `yield` executes inside a runtime-owned frame for the block body, but that frame is nested *underneath* a native call frame — `forEach`'s own Rust stack frame, mid-loop, holding whatever index or iterator state it uses to walk the list — which is itself nested under the interpreter's outer entry. The interpreter's frame-stack representation has no idea that native frame exists, let alone how to freeze and later replay it.

The two programs look, to a programmer, like the same idea spelled two ways: "do this once per element of a sequence, yielding each time." Nothing in the *language semantics* of iteration distinguishes them. What distinguishes them is a decision made in an entirely different part of the system, for entirely different reasons — almost certainly performance: `while` is lowered to jumps because a dedicated bytecode form for the most common control construct in the language is worth optimizing, and `forEach` is implemented as native iteration because writing the loop once in the host language and calling back per element is simpler and often faster than expressing it as a generic bytecode-level `next`-message loop.

This is worth sitting with, because it is a genuinely strange property once you see it stated plainly: **a language-visible capability — "can I suspend at this call site" — falls directly and mechanically out of an optimizer's decision about what got inlined versus what got dispatched through a callback.** It is not that the language designer sat down and decided iteration-via-loop-construct should be more suspendable than iteration-via-higher-order-function; nobody decided that. It is an artifact of which subsystem happens to own the control flow at the point of interest — the compiler's front end (bytecode jumps, owned and replayable) versus the standard library's implementation strategy (native recursion, opaque and unowned) — and that ownership question could, in principle, flip with a future compiler version that decides to lower `forEach` differently, or optimize `while` differently, silently moving the suspend/no-suspend line without any change to the language specification at all. A restriction whose boundary is drawn by an implementation detail this incidental is a leaky abstraction in the strongest available sense: not "some detail occasionally shows through," but "the presence or absence of a runtime error at this call site is decided by which of two equally reasonable codegen strategies a library author picked."

## Lua: the restriction shipped, then the escape hatch shipped later

Lua is the cleanest historical instance of exactly this problem, named, hit in production, and then partially — not fully — solved in a later language version, which makes it the highest-value comparison available: the same restriction and a shipped example of the exact mechanism that lifts it, inside one language's own history.

Lua 5.0 and 5.1 implement `yield` by unwinding the Lua-level call chain of the coroutine being suspended. Lua-to-Lua calls are represented on Lua's *own* data stack (part of the `lua_State`), not the C call stack, which is precisely the "runtime-owned frames" property from the top of this document — a pure Lua call chain can suspend as cheaply as anything in the restricted design above. The trouble is any call sequence where a C function, itself invoked from Lua, calls back into Lua — the canonical example being something like `table.sort` with a Lua comparator, or `pcall` used from inside a nested context, or any C-implemented library function taking a Lua callback. That C function's own activation is a real frame on the actual C call stack, governed by the C ABI, and if the Lua code it calls back into tries to yield, the runtime would need to suspend not just the Lua call chain (which it can) but the C function's frame sitting in the middle of it (which it structurally cannot: C's `return` doesn't have a "come back to the middle of me later" mode). Lua 5.1 makes this a hard error rather than undefined behavior, with the message **"attempt to yield across a C-call boundary"** [flagged: I'm confident this is at least very close to the exact 5.1 wording; treat the precise punctuation/capitalization as approximate]. This is restricted suspension, arrived at independently and for the same structural reason argued above, years before "restricted vs. stackful" was common vocabulary for it.

Lua 5.2 (and 5.3 after it) narrows this, and the mechanism is worth getting exactly right because it is a small, self-contained instance of the trampoline argument from earlier in this document, applied per-function rather than to an entire standard library. The escape hatch is `lua_yieldk` (yield-with-continuation) paired with `lua_callk`/`lua_pcallk` (call-with-continuation) [flagged: mechanics as I recall them from Lua's reference manual and PIL; confident on the shape, less confident on exact function-signature details across the 5.2/5.3 line]. A C function that wants to call back into Lua and then *keep doing C work with the result* can no longer simply call `lua_call` and write straight-line C code after it, if it wants that callback to be yieldable — because if the callback yields, there is no C-stack mechanism to "come back to the middle of the C function" the way there would be for an ordinary return. Instead, it calls `lua_callk`, handing over not just the function and arguments but a **continuation function**: a separate C function pointer, plus a small integer/context value, that the Lua runtime will invoke *from scratch*, as a fresh call, when the coroutine is later resumed — passing it the eventual results, as if it had just returned from the yield point. The original C function's stack frame, and any local variables it held, are gone; they were never preserved, only the continuation pointer and the context value survive. So writing a yieldable C function under this scheme means manually splitting it into two pieces — "the part before the callback" and "the part after," expressed as two separate functions communicating only through Lua-visible state (upvalues, the context integer, values left on the Lua stack) rather than through C locals — which is precisely the "make the implicit native state machine explicit" transformation the full-trampoline branch requires, done by hand, opt-in, one C function at a time.

Being precise about what this did and did not buy: it made yieldable exactly those C functions whose authors were willing to restructure them into the call/continuation shape. It did not make an arbitrary, unmodified C function that calls `lua_call` directly, expecting a normal return so it can keep executing more straight-line C code with the result in its own locals, yieldable — that function still hits the same C-call-boundary error it always did, `lua_yieldk` or no. Nor could it magically preserve C-local state that the author didn't move into Lua-visible storage: the "continuation" genuinely restarts as a new call, it doesn't resume a frozen one. Lua 5.2/5.3, in other words, didn't remove the restriction; it added a manual, function-scoped trampoline mechanism that lets a library author trade rewriting effort for yieldability at exactly the call sites where they're willing to pay for it — which is the trampoline branch's additivity argument from earlier, replayed at the smallest possible grain, in a real shipped language.

## Go: the stackful branch taken all the way, and its own C boundary

Go took the other branch as fully as it's been taken in a mainstream production language: every goroutine gets its own real, initially small, growable stack, and the runtime can suspend a goroutine at essentially any point in its execution — blocked on a channel, on I/O, or (since around Go 1.14 [flagged: recalling the version loosely]) even mid-tight-loop via signal-based asynchronous preemption, not just at explicit function-call safepoints as in earlier versions. Because each goroutine has its own stack, none of the native-re-entrancy problem this document opens with applies *between goroutines*: a goroutine can be suspended arbitrarily deep in ordinary Go call frames, because those frames are parked, whole, on that goroutine's own stack, exactly as the stackful-coroutines section describes.

Go pays the GC bill in full and takes the expensive branch: the compiler emits **precise stack maps** at safepoints for every goroutine stack, so the collector always knows exactly which stack slots are live references, of exactly what shape, at every point a goroutine might be paused. This is what makes Go's stacks not merely scannable but *movable* — the runtime routinely copies a goroutine's entire stack to a larger allocation as it grows, which requires walking every frame on it and rewriting every internal pointer (including pointers *into* the stack itself, a strictly harder version of the relocation problem than plain heap compaction, since the stack can contain pointers to its own other frames). This is the single most expensive point in the whole design space actually built and shipped at scale, and it is exactly the "precise stack maps everywhere" branch flagged as a whole-compiler commitment above.

The confirming data point, and it's a clean one: Go's own answer to native (C) re-entrancy via `cgo` reintroduces the identical restricted-suspension boundary this document opens with, inside a runtime that otherwise solved the general problem as thoroughly as anyone has. A goroutine currently executing inside a `cgo` call is pinned to its OS thread and is not preemptible or stack-movable the way ordinary Go code is [flagged: general shape confident, exact current-Go specifics on cgo/preemption interaction not verified against source], precisely because C frames carry none of the precise stack-map metadata Go's own compiler guarantees for Go frames. Even the runtime that spent the most engineering budget in this document on making native re-entrancy suspendable hits the same wall the instant the "native" code in question is *actually* native (C, not Go) rather than more Go. This is strong evidence that the restriction isn't a property of under-resourced implementations; it's a property of the boundary between "frames the runtime's own metadata describes" and "frames it doesn't," and that boundary reappears wherever a truly foreign calling convention is involved, no matter how much has been built on the runtime's own side of it.

## JavaScript: the boundary gets a name, and it's drawn statically instead of discovered by crashing

JavaScript is the highest-value comparison in this document for a specific reason: it names, in ordinary developer vocabulary, the exact partition this whole document has been describing mechanically. The term is **function coloring**, popularized by Bob Nystrom's widely-read essay on the subject [flagged: attributing loosely from memory; the essay's title and general argument are what I'm confident of, not verifying exact publication details]: an `async function` is a different *color* of function from an ordinary one, a synchronous (non-async, non-generator) function cannot `await`, and calling an async function from inside a sync one forces a choice — block (impossible, or at least deeply undesirable, in JS's single-threaded event-loop model) or *become async yourself*, which is why the color is said to be "infectious": one async function anywhere in a call chain tends to push every caller above it toward the same color.

The reason this belongs in the same document as native re-entrancy in a bytecode VM is that JavaScript's restriction is not actually about host-language re-entrancy at all — there's no C frame in sight — and yet it has the identical shape, which is the generalizing move worth taking seriously: **the real dividing line was never "native vs. interpreted."** It's "does this frame's control state live in a representation the suspension mechanism knows how to capture." An `async function` or `function*` is compiled (conceptually, whether or not a given engine literally desugars it this way) into a resumable state machine — the exact full-trampoline transformation from earlier in this document, done by the compiler automatically instead of by hand: every `await`/`yield` point becomes a case a re-entry can jump to, and the function's locals live in a heap-allocated frame object rather than in ordinary stack-allocated locals, because *that* frame has to survive being suspended and resumed. An ordinary JS function is compiled with no such accommodation — its locals are wherever the engine's own calling convention puts them, and there is no way to suspend in the middle of one and come back, for exactly the reason a native C frame can't be suspended: nobody built the state-machine transform for it, so from the suspension mechanism's point of view, an un-colored JS function is exactly as opaque as a Lua C function or a Rust `forEach` primitive. It is worth being precise that plain JS generators do not lift this either: you cannot `yield` from inside a plain function called by a generator — only from the generator's own body, or through explicit `yield*` delegation to another generator — which is the textbook definition of a **stackless** coroutine (can suspend only from its own top-level activation, not from arbitrary nested calls it makes), as opposed to a **stackful** one (can suspend from any depth, the way Program A's `while`-loop case can trivially and the Go/native-stack branch can by construction). JS's contribution isn't a new mechanism; it's making the restricted/stackless boundary a *static, source-visible, type-checkable* fact (a function either is or isn't declared `async`/`function*`) rather than a *dynamic, discovered-at-runtime* one (a Lua/embedded-VM restriction you find out about by hitting the error at a particular call depth). Both are the same underlying invariant; JS chose to surface it in the type system instead of leaving it implicit in the call graph's shape.

## Wren: fibers as the only concurrency primitive, and where its own boundary probably sits

Wren is worth a dedicated look because it commits to fibers as the *sole* concurrency construct — there is no separate async/await, no generator sugar layered on top; every suspendable computation is a fiber, and fibers are also how the language expresses generator-like iteration and even error handling in some idioms. [flagged, moderate confidence, recalled from general familiarity with the language rather than verified against its source or docs: Wren's own VM maintains its call frames for Wren-to-Wren calls as data on a runtime-owned stack structure rather than by recursing the host C call stack per Wren call — closer in spirit to the restricted design's "cheap because runtime-owned" case than to a stackful implementation — which would mean ordinary, deeply nested Wren-to-Wren call chains can suspend/switch fibers without difficulty, because the whole chain is runtime-owned frames, the same property Program A's loop has above.] Where I'd expect (but am flagging as unverified) the restriction to reappear is exactly at the seam this document keeps finding: a **foreign method** — Wren's FFI, where a C function implements a Wren-visible method — that itself calls back into Wren (say, a C-implemented collection method invoking a Wren callback block) does so through the real C API entry point for calling a Wren function, which is a genuine C function call and therefore a genuine C stack frame sitting between the callback and the top. I'd expect that transferring to a different fiber, or yielding, from underneath such a re-entrant foreign call is either disallowed or unsupported, for the same structural reason as everywhere else in this document — but I have not verified this against Wren's actual source or changelog, and version-to-version details of exactly what's permitted around foreign-method re-entrancy are the kind of fine print I'd want to check before relying on it. Flagging this honestly rather than asserting it is more useful than a confident guess: the *shape* of the prediction ("small, fiber-native VM, restriction reappears at the FFI seam") is exactly what this document's theory predicts for any runtime built this way, which is itself informative even without the verification.

## What got cut, and why each one failed to earn space

**Erlang/BEAM** is cut because it doesn't share the fabric this document depends on: BEAM processes are scheduled by counting reductions (an instruction budget) and yielding to the scheduler at budget boundaries, uniformly, without any concept of "a native callback re-entered the interpreter mid-computation" — ordinary BEAM code has no C-call-boundary problem to hit, because there is no re-entrant native call happening in the paths reduction-counting covers. The place BEAM *does* have an analogous hazard — NIFs (natively implemented functions) that run too long and starve the scheduler, or that must be off-loaded to "dirty" schedulers — is a real tension, but it's a different axis (preemption granularity and scheduler fairness under a soft time budget), not the suspend-under-native-frame question this document is about, and folding it in would blur rather than sharpen the argument.

**Ruby's Fiber** is cut for redundancy, not irrelevance: it is a stackful design (historically built on a real machine stack per fiber, in the same family as the mechanism described in the stackful section), so including it would mean restating the GC-bill argument with different proper nouns. The one thing that would distinguish it — that MRI's collector has long scanned the C stack conservatively anyway, for reasons unrelated to fibers, because of its C-extension ecosystem — actually makes Ruby's marginal fiber-related GC bill *smaller* than Go's, not a new lesson: it's "more of the same conservative scanning it was already doing," not a new mechanism worth its own section.

**Python's `asyncio`** is cut for the same reason as Ruby, from the other direction: `async def` desugars to a mechanism close enough to generators that its restriction (`await` cannot cross into a plain synchronous function any more than `yield` can) is isomorphic to the JavaScript case already argued in depth. Running through it again would repeat the coloring argument with different keywords rather than add to it.

**C# and Kotlin** are cut for a related reason, with one footnote worth keeping: both popularized (arguably C#'s `async`/`await`, which predates and directly influenced JS's, more than either) the compiler-driven state-machine transform underlying the JS section — C#'s compiler generates an explicit `IAsyncStateMachine` type per async method, and Kotlin's `suspend fun`s are compiled via continuation-passing style with an actual `Continuation` parameter the compiler inserts at every suspend call site [flagged: confident on the general CPS-transform shape for Kotlin, less certain of exact current-compiler implementation details]. The only genuinely novel wrinkle either adds — that Kotlin's coloring is *maximally* explicit, a literal extra parameter threaded through generated bytecode rather than an implicit engine-level transform — is a real footnote on how mechanical the trampoline transform can be made, but it's a footnote on JS's lesson, not a second lesson.

## Three tensions the walk above leaves open

**A cheap switch and a restricted switch might be one design property wearing two names, not two.** Restricted suspension is cheap *because* it only ever has to save runtime-owned data, and it's restricted for the identical reason: native frames, being not runtime-owned, are excluded from what it can touch. Cheapness and restriction are two readings of the same underlying fact — "the suspension mechanism's domain equals the interpreter's own frame representation" — not two independent choices that happen to correlate. That said, it isn't a logical necessity: you could build a restricted design that's expensive anyway (defensively cloning the whole frame stack on every suspend, say, for reasons that have nothing to do with the restriction), and, as the trampoline section shows, you can spend real engineering effort to widen the restricted domain while keeping the *mechanism* cheap (no stack-switch, no context save) even though each converted primitive now costs an allocation it didn't before. So: the same insight tends to motivate both properties together in practice, which is why they show up paired in almost every restricted design examined here, but the pairing is an engineering correlation, traceable to a shared cause, not an inevitability.

**Optimizer decisions leaking into language semantics is not unique to suspension — suspension is just where it's most visible.** Any language feature whose behavior depends on "how much native call stack sits between here and the top" turns an implementation choice about inlining or dispatch strategy into an observable semantic fact, and yield/suspend is simply the sharpest instance because it fails loudly (a runtime error) rather than quietly (a subtly different stack-overflow depth, say, which is the same family of leak with a fuzzier symptom). A language designer who wants "equivalent" iteration constructs (a `while` loop and a `forEach` call) to actually behave equivalently under suspension has exactly two ways out: pay to trampoline everything so the equivalence is real, or make the inequivalence a first-class, statically visible fact — JS's route — so at least the leak is documented in the type system rather than discovered by a user hitting an error message that references an implementation detail they have no way to have known about.

**Sound-but-wider-than-necessary restriction is frequently the correct engineering call, and Lua's own history is the argument for it.** A blanket "no yield across any C call" rejects some programs that would, in a specific instance, actually be safe to suspend (a C function that calls back into Lua and holds no C-local state worth preserving across the callback, say) — it is not *precise*. Making it precise instead of blanket would require either per-call-site manual proof (a burden that has to be re-validated every time that primitive's internals change, since a refactor of `forEach`'s Rust guts that introduces a new local invalidates a "this call site was safe" judgment nobody re-checks) or a general static analysis capable of proving a native frame holds no unrecoverable transient state, which is not a tractable thing to build in general. Blanket restriction buys a simple, stable invariant — "yield never touches a native frame, full stop" — that survives every future refactor of the primitives it restricts without re-auditing anything, at the cost of rejecting some safe programs along with the unsafe ones. That trade is the right one precisely when native primitives are numerous, change often, and are written by people who cannot be expected to reason about coroutine safety on every edit — which describes most embeddable-language standard libraries, and is exactly why Lua shipped the over-restrictive blanket rule first and only later added `lua_yieldk` as a narrow, opt-in, manually-proven exception at the specific call sites someone was willing to pay to convert. Ship wide and sound, narrow it call-site by call-site as each one proves it's worth the rewrite, is a broader pattern than coroutines — but coroutines are where this document found it argued out loud, in a shipped language, across two major versions.

This is also close to where the theory this document covers actually bottoms out. Everything above assumes **one-shot** suspension: a fiber, once resumed, has its suspended state consumed — there is no second copy of "the program as it was at the yield point" lying around to resume again independently. A fully general theory of suspending computations doesn't stop there; **multi-shot continuations** (the `call/cc` family) allow a captured suspension point to be invoked more than once, producing more than one continuation of the same paused moment, which means the captured state has to be *copied*, not merely moved, on every capture — and for a stackful implementation that means cloning an entire parked native stack region per capture, with as many independently-live, independently-scanned-and-relocated copies as there are outstanding captures. That is a heavier version of exactly the GC bill argued above, not a different one, and it's the direction in which this document's simplifying assumption — every fiber is resumed at most once — stops holding. Coroutines, in that sense, are the well-behaved, one-shot restriction of a larger theory; this document has been about what it costs to support even that restricted case honestly, and the multi-shot generalization is where the costs above stop being merely large and start being the entire remaining subject.
