# When a Fiber Fails and Nobody Is Watching

## 1. The branches with real occupants

An uncaught error reaching the top of a fiber's own activation splits along two independent axes, but in practice only three combinations are actually inhabited by shipping languages.

**Axis one: does the resumer learn about the failure as a raised exception, or as an ordinary returned value?** Lua's coroutines take the returned-value branch: `coroutine.resume` never lets an error inside the coroutine propagate as a Lua exception at the call site. It catches it internally and returns `false, err` — a boolean status plus the error object, exactly like `pcall`. The coroutine becomes dead (further resume errors "cannot resume dead coroutine"), but the *caller's* control flow stays completely ordinary: if the caller doesn't check the boolean, the error is silently absorbed. This buys uniformity with Lua's existing `pcall` idiom and costs the thing that idiom is notorious for — it is trivially easy to forget to check the status, and nothing forces you to notice.

Ruby's `Fiber#resume` and, more concretely, generator-shaped coroutines in Python and JavaScript take the other side: an exception raised inside the generator/fiber body comes back out of the call that resumed it (`next()`, `.send()`, `Fiber#resume`) as a genuine, catchable exception at that call site (unverified in the fine details of Ruby's exact re-raise wrapping, but the shape — resume re-throws rather than returning a status — is the one I'm confident about). This buys the biggest thing a language with "ordinary exceptions with terminating semantics" already has: one error-reporting vocabulary, not two. It costs what Lua's branch avoids: the resumer's own exception-handling code is now on the hook for errors originating arbitrarily deep in something it merely woke up, and if it wasn't written expecting that, the exception keeps going up *its* frames too.

**Axis two: is the failure contained to the fiber, or does it take the whole host down?** Both branches above are "contained": only fibers *on the resumer chain* of the failure are affected, and siblings keep running. Go's goroutines occupy the uncontained branch: a panic reaching the top of a goroutine without `recover()` doesn't get handed to whoever spawned it as a value or a propagated error — it terminates the process. Go picked this deliberately (unrecovered panics are programmer error, not routine failure), and it's the branch with the most war stories: one missing `recover()` anywhere in a large concurrent program takes unrelated work down with it. I'm treating goroutines as the strongest occupant here even though they're preemptively scheduled across OS threads rather than cooperative fibers — the mechanism (what happens when an unhandled failure reaches the top with no supervisor) is the same shape, and no cooperative-fiber language I know of ships "kill the host" as its default.

A fourth logically possible cell — uncontained *and* delivered as a value — has no real occupant; if the host is going down there is no "return to the resumer" step left to deliver a value through, so it collapses to a footnote.

## 2. Mechanism, per branch

All three branches share a prefix: the failing instruction triggers the same terminating-unwind machinery already used for any in-fiber exception, walking the failing fiber's *own* frame array from the top and running each popped frame's `finally`/`ensure` blocks before discarding it. Nothing fiber-specific happens yet — it's ordinary unwind, scoped to whichever frame array is installed.

**Contained-as-value (Lua-shaped).** When the walk exhausts the failing fiber's frames with no handler anywhere in it, the runtime does not keep unwinding anywhere — there is no shared native call stack connecting this fiber's frames to the resumer's, so "run off the bottom" simply *is* this fiber's terminal state. The fiber object is tagged dead-with-error, the error value is stashed on it, and control returns to the resumer exactly the way an ordinary completed-fiber return would, except the resume expression evaluates to a failure tag instead of a value. The failing fiber's operand stack and frame array need no special reclamation — they were heap objects all along, so once unreachable, ordinary GC takes them — but they must *not* be torn down before the finally-driven unwind finishes, since that unwind can itself allocate or mutate objects other fibers already reference.

**Re-raise-and-relay (Ruby/Python-shaped).** The same walk and finally obligation apply, but instead of tagging-and-returning, exhausting the failing fiber's frames re-enters the unwind search *inside the resumer*, starting at the frame containing the resume call — as if that call site were the point of a freshly raised error. If the immediate resumer also has no handler, the same thing happens one level up: walk its frames, run its in-flight finally blocks, and if exhausted, hop again. This repeats across an arbitrarily deep resumer chain until a handler is found or the walk reaches the fiber with no resumer (the program's root activation), at which point it becomes an ordinary top-level uncaught error — not a new mechanism, just where the relay road ends. Every fiber touched by the relay, not only the endpoints, must have its finally blocks run and must be marked dead once its frames are exhausted — a fiber forcibly unwound out from under it cannot safely be resumed again, and that must be a checked error at the next resume attempt, not silent reuse of a stale frame array.

**Uncontained (Go-shaped).** The failing fiber still runs its own finally blocks on the way down, but once its frames are exhausted the runtime does not consult the resumer relationship at all — it abandons the interpreter loop and goes straight to program-level teardown. This is the mechanically cheapest branch (no per-hop bookkeeping, no dead-fiber tagging across a chain) and the most expensive in aggregate: sibling fibers sharing nothing with the failure's resumer chain get torn down mid-flight too, generally with no guarantee their finally blocks run in any well-defined order, since the teardown path was never designed as a well-behaved unwind — it's a shutdown.

The obligation every branch shares, and the easiest one to shortcut, is closing upvalues at each popped frame during this unwind — see §5.

## 3. The comparison cast

I'd put four names in a teaching document. **Lua**, because `coroutine.resume`'s boolean-plus-error return is the cleanest statement of the contained-as-value branch and the direct lineage for any bytecode VM with per-fiber stacks and an explicit `resume`/`yield` pair. **Wren**, because its fiber model — each fiber a heap object owning its own stack, a single interpreter loop switching which is installed, `Fiber.new(...).try()` catching a fiber's error versus an uncaught `call()` propagating past it (unverified in the exact API surface, but the shape is right) — is architecturally the closest sibling to a stackless-per-fiber-object design, and shows both axis-one branches can coexist as *different entry points* into the same fiber, not different languages. **Ruby**, for `Fiber#resume` re-raising at the call site, as the clean occupant of "exceptions stay exceptions across a resume." **Go**, as the load-bearing cautionary tale for the uncontained branch — not because goroutines are cooperative fibers, but because it's the one mainstream, widely-felt example of what "one missing handler kills everything" costs in production.

I'd cut **Erlang/Elixir**. "Let it crash" is famous vocabulary, but its mechanism — preemptively scheduled processes with independent heaps, failure communicated through links and monitors to a supervision tree — solves a *different* problem (fault isolation among many independent actors) than a resumer chain built by explicit, cooperative `resume` calls. Naming it would smuggle in a scheduler and a supervisor tree the reader doesn't have. I'd also cut **Kotlin coroutines**: structured concurrency's exception propagation to a parent `Job` is real and well-designed, but answers a scope-hierarchy problem, and explaining it requires importing `CoroutineScope`/`Job` machinery with no analogue in a bare resumer-chain design — its own document, not a paragraph. And I'd cut **C#/JS `Promise` rejection propagation** as decorative: identical vocabulary to Python/JS generators (a rejected awaited value throws at the `await`), so naming it would repeat a point rather than add one.

## 4. Tensions with other committed features

The terminating-unwind machinery already walks frames and promotes captured cells for ordinary in-fiber exceptions; extending it across fiber boundaries means every unwind call site now needs to know whether it's allowed to cross a fiber's frontier at all. A routine written assuming "the call stack" is one contiguous structure will, without a deliberate boundary parameter, either stop too early (silently dropping the relay) or walk into memory belonging to a different fiber's array entirely.

Cleanup constructs compound this: the relay branch requires every fiber on the chain to run its own finally blocks, in frame order, *before* hopping to the next fiber up — not as a batch after the fact. An implementation that unwinds the origin fully, collects the error, and only then unwinds the resumer as an independent top-level operation can let a resumer's finally block observe global state the origin's finally already mutated, without that ordering ever having been a deliberate, documented guarantee — an accident of implementation order rather than a promise the language makes.

GC rooting is the sharpest collision. If the tracer treats "live interpreter state" as "whatever the currently-installed fiber's buffers are" — the obvious thing to write first — then every fiber below the running one in the resumer chain, plus any dead-but-referenced failed fiber holding a stashed error value (which may itself reference locals via a backtrace), is invisible to the tracer despite being reachable through a live fiber object. Roots must include every fiber transitively reachable from any live root: the entire resumer chain plus any dead fiber someone still holds a handle to, not just whichever buffers happen to be installed right now.

Last, the dynamic (not lexical) shape of resumption means the relay cannot be resolved at compile time — there is no fixed "outer scope" to walk to, because which fiber resumed which is a runtime fact built by whoever happened to call resume this time. The unwind must read an actual runtime field on the fiber object at the moment of failure, and identical fiber code can propagate to a different ancestor chain on different runs — exactly the property that makes Lua's contained-value branch attractive to some codebases: it never asks the reader to reason about a resumer graph the source text doesn't show.

## 5. The trap

My recommendation: default to the re-raise-and-relay branch — an uncaught error propagates as an ordinary exception at the immediate resumer's resume call site, relaying up the dynamic resumer chain exactly like any nested exception would — because the language already committed to "ordinary exceptions with terminating semantics," and a second, silent, returned-value error channel alongside that is the kind of duplication that gets forgotten at exactly the call site that matters. I'd still want an explicit opt-in primitive (a protected resume, Lua/Wren-shaped) for supervisory code — schedulers, test harnesses — that genuinely wants a failure reported as data rather than control flow.

The bug I'd expect a competent-but-rushed implementation to actually ship: skipped upvalue closing on the failing fiber's *own last frames* during the unwind that precedes the hop. Per-frame unwind almost always already closes upvalues as part of popping a frame in the ordinary case, because that's needed for correctness there regardless of fibers. But once someone is implementing "this fiber is dying anyway," it's a natural, wrong shortcut: once we've hit the bottom of this fiber's frames with no handler, the rest of the per-frame teardown is about to become garbage, so skip closing upvalues for the last few frames and jump straight to tagging the fiber dead. That shortcut is invisible in every fiber that completes normally or fails with no escaped state — the overwhelming majority of test coverage. It only bites when a frame being unwound had a local captured by a closure that had *already* escaped upward — handed to the resumer, stored in a global, stashed in another fiber — before the failure happened later in that same fiber's execution. The escaped closure is left referencing a stack slot inside a frame array the shortcut just dropped as garbage without promoting the capture to the heap, and the next read through that closure sees a stale or reused slot instead of the value it was supposed to keep observing. The concrete thing to go looking for: a fiber that captures a local in a closure, hands that closure to its caller, then later raises uncaught past the end of its own frames — then check whether the caller's closure still reads a sane value or garbage.
