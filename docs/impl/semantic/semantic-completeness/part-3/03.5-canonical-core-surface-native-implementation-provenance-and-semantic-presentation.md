**Date:** 2026-08-22

## 0. Authority and implementation contract

This specification fills a gap that became visible only after Specs 01–03 were implemented.

Phalcom now has all of the following at once:

1. a compiler-owned canonical semantic model;
2. durable semantic metadata and runtime type reification;
3. an explicit typing-reflection API;
4. a mature native primitive registration system in Rust;
5. core-universe `.ph` modules that represent the user-visible library source surface.

Those pieces are individually coherent, but the repository still has **two different descriptions of the core method surface**:

- the native primitive registry describes what the runtime actually installs;
- `phalcom-semantic::types::native::register_standard_surfaces` manually recreates a selected static surface for the checker.

At the same time, many universe `.ph` files intentionally contain only thin source shells even when their effective behavior is implemented by dozens of native primitives. Consequently, a user or tool looking at “the core source” does not necessarily see the method surface that the runtime and static semantic engine know exists.

Spec 03.5 therefore establishes one additional architectural layer:

> **The canonical core surface is a merged, queryable semantic/presentation model whose native half is derived from the native primitive manifest, whose source half is derived from real Phalcom declarations, and whose implementation provenance is explicit.**

It must feed static semantics, documentation, reflection, and tooling without pretending that Rust code is Phalcom code and without introducing fake executable declarations.

### 0.1 Normative distinction

This document distinguishes four things that must never be collapsed:

```text
semantic declaration surface
    what selectors, signatures, types, constraints, and contracts mean

runtime implementation
    the executable method body used by the VM

implementation provenance
    where/how that executable implementation came from

presentation
    how tools explain the method to a human
```

A native method may have:

```text
semantic surface        (Int) -> Int
runtime implementation  Rust primitive function
provenance               NativePrimitive + Rust source location
presentation             Phaldoc + effects + “native” annotation + conceptual sketch
```

The presentation is not an executable body and is not semantic authority.

### 0.2 Concurrency contract with Spec 04

Spec 04 will modify parser/AST/type-form source syntax. Spec 03.5 is deliberately designed so that its first five workstreams do **not** require those files.

Until Spec 04 publishes a stable parser/AST handoff, Spec 03.5 MUST NOT make competing edits to:

- `phalcom-ast/src/ast.rs` generic/type-form declaration structures;
- `phalcom-ast/src/parser.rs` type syntax;
- `phalcom-type-syntax` grammar owned by Spec 04;
- source annotation lowering owned by Spec 04.

The canonical presentation model defined here is a separate IR. It does not require a fake `MethodDef` or fake parser AST node.

# 1. Executive assessment

The current repository has already solved most of the hard infrastructure necessary for this work.

## 1.1 What is already strong and should be retained

The native macro is significantly richer than the user-facing universe source suggests. A primitive declaration can already carry:

- canonical owner;
- selector;
- parameter types;
- return type;
- complete callable type;
- raised-error information;
- effects;
- instance/class side;
- visibility;
- stability;
- introduction/deprecation/replacement lifecycle;
- ABI;
- return-flow semantics;
- intrinsic identity;
- trust classification.

The macro also emits a distributed `PrimitiveDescriptor` containing `NativeSourceSpec` with module path, Rust function name, file, and line.

Runtime installation already consumes the distributed `PRIMITIVES` registry deterministically.

Specs 02–03 already established the pattern that static semantic information should stay outside hot runtime objects: `MethodSemanticIndex` maps live method objects to metadata rather than inflating every `MethodObject`.

These are excellent foundations.

## 1.2 The central defect: the native/core surface currently has four descriptions

Repository archaeology shows that the problem is broader than the semantic checker alone. The current tree contains **four partially overlapping representations** of native/core members:

1. **Rich Rust primitive attributes** — `#[phalcom_native_macros::primitive(...)]` carry selector, types, effects, raises, flow, lifecycle, intrinsic, trust, ABI, and source provenance and emit the new distributed `PRIMITIVES` registry.
2. **Legacy runtime installation** — `phalcom-core/src/universe/primitives.rs::Universe::install_primitives` still manually installs a very large method list using `primitive!`, `primitive_static!`, `primitive_internal!`, `primitive_shape!`, and related macros.
3. **VM-free editor surface** — `phalcom-native-surface/src/lib.rs` manually maintains `NATIVE_CLASSES` and `NATIVE_MEMBERS`; the LSP merges those records into its core surface.
4. **Compiler semantic surface** — `phalcom-semantic/src/types/native.rs::register_standard_surfaces` manually recreates a much smaller typed subset for the checker.

The VM bootstrap currently invokes **both** `Universe::install_primitives(&mut vm)` and `crate::native::install::install_registered_primitives(&mut vm)`. The second path is the new descriptor-driven architecture; the first is the legacy floor. Therefore even runtime installation itself is mid-convergence.

This is exactly the kind of multi-authority state that becomes expensive once typing, reflection, LSP, documentation, and source presentation all become richer.

For example, a Rust primitive may declare:

```rust
#[phalcom_native_macros::primitive(
    Int,
    "bitCount",
    params = [],
    returns = Int,
    types = "() -> Int",
    effects = pure
)]
```

Yet today:

- runtime availability may come from the legacy install list and/or the new descriptor registry;
- LSP availability comes from a separate `NATIVE_MEMBERS` entry with only a coarse return shape;
- static-checker availability depends on whether `register_standard_surfaces` happens to mention the selector;
- docs/provenance live elsewhere again.

**There must be one authored native declaration and deterministic generated projections, not four independently edited method lists.**

## 1.3 The presentation defect

The mismatch is also visible to humans.

`phalcom-core/core/universe/src/scalar/bool.ph` contains a source implementation for `toString` and comments explaining that control-flow behavior is native. The executable methods `not`, `and`, `or`, `ifTrue`, `ifFalse`, and the paired conditional live in Rust primitives.

Likewise, the newly implemented `universe.reflection.typing` package contains very small `.ph` source shells while most behavior is installed through native primitives.

This organization is correct for execution, but poor if `.ph` source is treated as the complete conceptual library definition.

The solution is **not** to copy Rust behavior into fake Phalcom method bodies. The solution is to make implementation provenance and semantic presentation first-class tooling data.

## 1.4 Recommended architecture

Create a **Canonical Core Surface** pipeline in which the rich primitive attribute is the authored native source of truth and `phalcom-native-surface` becomes its generated VM-free projection:

```text
Rust #[primitive(...)] declaration
          |                         \
          | macro expansion         \ repository generator
          v                          v
  PRIMITIVES runtime registry   phalcom-native-surface/generated
          |                          |
          |                          +--> semantic compiler
          |                          +--> VM-free LSP
          |                          +--> Phaldoc/presentation
          v                          |
   runtime installation <---- conformance ----+

.ph source declarations ----------------------+
                                                v
                                      CanonicalCoreSurface
```

`phalcom-native-surface` is retained because the LSP is deliberately VM-free and already depends on it. What changes is its authority model: the giant hand-maintained `NATIVE_MEMBERS` table becomes generated output checked against the same attributes that build the runtime descriptors.

The source branch remains authoritative for actual Phalcom-source declarations and bodies. A merge/conformance layer reconciles source and generated-native records by canonical method identity.

## 2.2 The procedural macro is the correct native authoring point

### File

`phalcom-native-macros/src/lib.rs`

The `#[primitive(...)]` macro parses and validates the fields above and emits both:

1. a static `PrimitiveSurfaceSpec`;
2. a distributed `PrimitiveDescriptor` registered into `crate::native::PRIMITIVES`.

It also records source provenance using:

```rust
NativeSourceSpec {
    module_path: module_path!(),
    rust_name: ...,
    file: file!(),
    line: line!(),
}
```

The macro is therefore the canonical place to add **native-only presentation metadata**, because the method implementation and its semantic declaration are authored together.

It is not necessary and would be harmful to parse Rust source later to rediscover this information.

## 2.4 `phalcom-native-surface` is the existing VM-free tooling seam — but its table is handwritten

### Files

- `phalcom-native-surface/src/lib.rs`
- `phalcom-lsp/Cargo.toml`
- `phalcom-lsp/src/semantic/core_source.rs`

The `phalcom-native-surface` crate explicitly describes itself as:

> canonical native member declarations shared by the runtime and tooling

and deliberately has no VM/AST/LSP dependency.

That architectural boundary is correct and should be retained.

However its contents are currently another manually curated list:

```rust
pub const NATIVE_CLASSES: &[NativeClass] = &[ ... ];
```

`NativeMember` carries only:


where `NativeReturnShape` is intentionally coarse.

By contrast, the Rust `#[primitive]` attribute already knows the full callable type, effects, raises, flow, lifecycle, intrinsic, trust, ABI, and Rust provenance. This makes the current `phalcom-native-surface` table both a duplication and a lossy projection.

The LSP depends on this crate precisely because it must remain VM-free. `phalcom-lsp/src/semantic/core_source.rs::build_core_surface` merges `NATIVE_CLASSES` and `NATIVE_MEMBERS` into source core declarations and uses sentinel AST indexes/ranges for native-only members. That is a useful precedent for source/native merging, but the input table should be generated from the authoritative primitive declarations rather than edited separately.

`phalcom-core/src/universe/primitives.rs::validate_native_surface` also compares the live runtime floor against `NATIVE_MEMBERS`, which is good drift detection but still validates one handwritten list against another handwritten list.

The LSP should not hard-code Rust primitives or use fake AST locations as native identity. It should consume the generated native surface and the compiler-owned canonical callable semantics.

# 3. Non-negotiable laws

## 3.1 One native semantic declaration

For a native primitive identified by:

```text
(owner, side, selector)
```

there is exactly one authoritative native declaration record.

Its type/effect/flow/lifecycle metadata originates from the primitive macro output.

No second handwritten semantic signature is permitted in `phalcom-semantic` after migration.

## 3.2 Executable implementation and presentation remain distinct

A conceptual or displayed implementation must never be callable, compiled, optimized, used for proof, or treated as the source body.

```text
presentation(body) != executable(body)
```

Tools MUST carry an explicit provenance flag so a conceptual sketch cannot be confused with source code.

## 3.3 Native fallback and intrinsic optimization are not exclusive

A primitive with an intrinsic ID is still a native primitive unless the runtime has literally no native implementation.

Correct model:

```text
implementation.kind = NativePrimitive
implementation.intrinsic = Some(BoolNot)
```

Incorrect model:

```text
implementation.kind = Intrinsic
```

when a Rust primitive remains the semantic/runtime fallback.

This distinction matters because intrinsic replacement may be disabled, deoptimized, or unavailable while the native primitive remains valid.

## 3.4 Runtime behavior is unchanged

The canonical surface model must not change:

- selector identity;
- ordinary lookup;
- class/metaclass identity;
- method dictionary keys;
- inline-cache keys;
- allocation/layout;
- primitive ABI;
- access checks;
- dispatch world-version semantics.

## 3.5 Static semantics consume metadata, not runtime VM objects

`phalcom-semantic` must remain VM-independent.

It may consume a VM-free native surface manifest from `phalcom-native-meta` or an equivalent VM-free adapter.

It must not depend on `phalcom-core::native::PRIMITIVES` directly if doing so creates a semantic → VM crate dependency.

This requirement drives the manifest/export design in §6.

## 3.6 Source methods remain source-authoritative

If a method is actually written in `.ph`, its executable source body and source declaration remain source-owned.

Native metadata does not override a source implementation merely because the selector matches.

A matching source/native method is legal only under an explicitly defined role such as:

- source declaration shell + native implementation binding;
- source wrapper intentionally calling a lower-level primitive;
- platform replacement selected by build configuration.

Otherwise it is a conformance error.

## 3.7 No Rust-source parsing as semantic input

Do not inspect the textual Rust function body to infer:

- types;
- effects;
- exceptions;
- flow;
- conceptual behavior.

Those facts must be declared in metadata or remain unknown.

## 3.8 Tooling paths are not durable public identity

`file!()` and Rust line numbers are useful in a developer checkout but unsuitable as stable public metadata keys.

Durable identity is `PrimitiveKey` plus schema/model version.

Raw Rust path/line information is debug provenance only.

## 3.9 Unknown remains unknown

If native metadata says:

```rust
effects = unknown
```

presentation must show unknown, omit the claim, or explicitly label it unknown.

It must not infer purity from an innocent-looking conceptual sketch.

## 3.10 User code cannot forge implementation authority

Even after Spec 04 supports richer attributes, user source must not be able to write an ordinary attribute that magically turns a method into:

- a trusted native primitive;
- a privileged native method;
- a compiler intrinsic;
- a kernel-backed implementation.

Those are compiler/runtime provenance classes, not decorative annotations.

# 4. Terminology and ontology

## 4.1 Canonical method key

Use the existing native identity shape wherever possible:

```rust
struct CanonicalMethodKey {
    owner: StableDeclarationIdentity,
    side: DispatchSide,
    selector: CanonicalSelector,
}
```

For core native methods, `UniverseKey` is a compact producer-side representation. At the semantic boundary it maps to the normal core `DeclarationId`.

Selectors continue to include their canonical label/slot structure. No type information enters key identity.

## 4.2 Semantic surface

The semantic surface answers:

> What callable does this declaration expose under this key?

It contains:

- generic signature if any;
- parameter labels/names/types;
- return type;
- visibility/access semantics relevant to static lookup;
- semantic authority/provenance;
- eventually contracts/effects/exits where those domains become canonical.

The surface does not contain a Rust function pointer.

## 4.3 Executable implementation

Recommended representation:

```rust
enum ExecutableImplementationKind {
    PhalcomSource,
    NativePrimitive,
    Generated,
    Abstract,
    External,
}
```

Do not make `Intrinsic` a mutually exclusive arm.

Instead:

```rust
struct ImplementationTraits {
    intrinsic: Option<NativeIntrinsicId>,
    abi: Option<PrimitiveAbi>,
    trust: ImplementationTrust,
}
```

A native primitive can therefore be both:

```text
NativePrimitive + intrinsic BoolNot
```

## 4.4 Provenance

Provenance answers:

> Why does this method exist, and where is its executable implementation defined?

Suggested variants:

```rust
enum MethodImplementationOrigin {
    Source {
        module: StableModuleRef,
        range: SourceRange,
    },
    Native {
        primitive: PrimitiveKey,
        debug_source: Option<NativeDebugSource>,
    },
    Generated {
        generator: GeneratedMethodKind,
        origin: StableDeclarationRef,
    },
    Abstract,
    External {
        boundary: ExternalBoundaryKind,
    },
}
```

This must stay independent from `PublishedTypeAuthority`.

A method can be source-implemented but compiler-inferred in typing, or native-implemented but carry a declared/trusted signature. These are different axes.

## 4.5 Presentation

Presentation answers:

> What should a human see?

It may contain:

- rendered signature;
- docs;
- implementation badge;
- intrinsic badge;
- effects/raises/flow summary;
- stability/deprecation;
- conceptual explanation;
- developer source link where available.

Presentation data never participates in type identity, relation solving, code generation, or runtime dispatch.

# 6. Target architecture: make `phalcom-native-surface` generated, rich, and authoritative as a projection

The repository already contains the right VM-free crate. Spec 03.5 should evolve it instead of inventing a parallel provider abstraction.

## 6.1 Authored truth vs generated truth

The source of authorship remains the Rust primitive attribute:

```rust
#[phalcom_native_macros::primitive(
    Bool,
    "not",
    params = [],
    returns = Bool,
    types = "() -> Bool",
    intrinsic = BoolNot,
    effects = pure
)]
```

From that one declaration, produce two checked projections:

```text
A. executable projection
   proc-macro expansion -> PrimitiveSurfaceSpec + PrimitiveDescriptor -> PRIMITIVES

B. VM-free projection
   source-declaration generator -> phalcom-native-surface generated records
```

The generated projection is checked into the repository or otherwise made available before normal compilation so that `phalcom-lsp` can remain VM-free.

This is not “two sources of truth.” It is source + generated artifact, analogous to generated parser tables or schema bindings. CI must fail when the generated artifact is stale.

## 6.2 Why `phalcom-native-surface` cannot simply enumerate `PRIMITIVES`

The LSP explicitly has no `phalcom-core` dependency. The distributed `PRIMITIVES` entries are emitted into `phalcom-core` because they contain executable function pointers.

Linking `phalcom-core` into the LSP solely to discover primitives would violate the existing LSP architecture and increase startup/runtime coupling.

Therefore a VM-free compiled surface is necessary.

## 6.3 Generation strategy

Do **not** use procedural-macro filesystem side effects.

Recommended generation pipeline:

1. scan `phalcom-core/src/primitive/**/*.rs`;
2. parse Rust syntax with `syn` only far enough to identify `#[phalcom_native_macros::primitive(...)]` attributes and their attached Rust `///` docs;
3. parse the attribute payload with the **same normalized declaration parser** used by the procedural macro;
4. produce deterministic generated Rust data in `phalcom-native-surface`, for example `src/generated.rs`;
5. run the generator in `--check` mode in CI and repository verification;
6. separately compare generated records to runtime `PRIMITIVES` in core tests.

Parsing the primitive **attribute** is acceptable and intentional. Parsing Rust function bodies to infer semantics remains forbidden.

## 6.4 Shared declaration parser

Today `PrimitiveAttrArgs` parsing lives inside the proc-macro crate. A generator should not implement a second attribute grammar.

Recommended small refactor:

```text
phalcom-native-decl/              # normal library, tooling/compile-time only
    normalized.rs
    parse.rs
    validate.rs

phalcom-native-macros
    -> uses phalcom-native-decl

native-surface generator
    -> uses phalcom-native-decl
```

`phalcom-native-decl` may depend on `syn`, `proc-macro2`, `phalcom-native-meta`, and `phalcom-type-syntax`; it must not depend on the VM.

If the repository strongly prefers fewer crates, a shared non-proc-macro support library under `phalcom-native-macros` may be used instead, but **one parser implementation** is mandatory.

## 6.5 Rich generated surface model

Change `phalcom-native-surface` from a coarse handwritten `NativeMember` table to a generated record that preserves the authoritative metadata needed by compiler and tooling.

Suggested shape:

```rust
pub struct NativeSurfaceRecord {
    pub key: PrimitiveKeyOwned,
    pub kind: NativeMemberKind,
    pub visibility: NativeVisibilityRef,
    pub stability: NativeStabilityRef,
    pub callable: NativeCallableSurface,
    pub raises: NativeRaisesSurface,
    pub effects: NativeEffectsSurface,
    pub flow: NativeReturnFlowSurface,
    pub lifecycle: NativeLifecycleSurface,
    pub intrinsic: Option<NativeIntrinsicRef>,
    pub trust: NativeTrustRef,
    pub abi: PrimitiveAbiRef,
    pub documentation: NativeDocumentation,
    pub conceptual: Option<ConceptualPresentationRecord>,
    pub debug_source: Option<NativeDebugSourceRecord>,
}
```

Prefer reuse of stable VM-free enums/records from `phalcom-native-meta` rather than duplicating enum vocabularies in `phalcom-native-surface`. The surface crate may add owned/serializable wrappers where `'static` references from macro metadata are inconvenient.

## 6.6 Preserve the current crate boundary

Target dependency direction:

```text
phalcom-native-meta
       ^
       |
phalcom-native-surface <----- generated projection
       ^        ^
       |        |
phalcom-semantic   phalcom-lsp
       ^
       |
phalcom-core  (+ macros/runtime descriptors)
```

`phalcom-semantic` should add a dependency on `phalcom-native-surface` and import the same generated records the LSP uses.

`phalcom-core` continues to depend on the surface for conformance validation and may use it to enrich runtime implementation indexes.

No dependency from `phalcom-native-surface` to `phalcom-core` is allowed.

## 6.7 Legacy runtime migration

Before deleting `Universe::install_primitives`, build a four-way census:

```text
A = legacy Universe::install_primitives installed keys
B = generated phalcom-native-surface keys
C = distributed PRIMITIVES keys
D = semantic imported native keys
```

Classify:

```text
A ∩ C    migrated runtime primitive
A - C    legacy-only primitive that still needs #[primitive] migration
C - A    descriptor-only primitive
B △ C    generator/manifest drift
D △ B    semantic import bug or unsupported semantic form
```

Only when all intentional runtime primitives are represented in `C` and `B == C` may the legacy manual installer be deleted.

## 6.8 Core-class relationship duplication discovered by the same census

`phalcom-native-surface::NATIVE_CLASSES` currently carries class/superclass relationships, while `phalcom-semantic/src/workspace.rs` also hard-codes a core hierarchy list and the runtime bootstrap constructs the kernel tower independently.

This is adjacent to, but separable from, native method convergence.

Spec 03.5 SHOULD eliminate the method duplication first. During that work it MUST report class-relation discrepancies. If no separate class-bootstrap migration is already scheduled, add one VM-free canonical relation table under `phalcom-native-meta`, for example:

```rust
pub struct UniverseClassRelationSpec {
    pub class: UniverseKey,
    pub superclass: Option<UniverseKey>,
}
```

or extend the existing universe declaration model where that is semantically correct.

Consumers:

```text
runtime bootstrap
compiler semantic hierarchy
LSP bootstrapped core classes
core presentation
```

must then derive from the same relation data.

Do **not** force every source-defined universe helper class into `UniverseKey` merely to remove `NATIVE_CLASSES`. Classes such as source-only/generated helpers should remain source-owned. The canonical relation catalog should cover only the bootstrap identities for which Rust already owns class existence.

If this relation migration proves larger than the native-member work, record it as an explicit 03.5 follow-on gate rather than silently leaving `NATIVE_CLASSES` described as canonical.

## 6.9 Canonical merge layer

Introduce or extend a core-surface module in `phalcom-semantic`, for example:

```text
phalcom-semantic/src/core_surface/
    mod.rs
    native.rs
    source.rs
    merge.rs
    conformance.rs
    presentation.rs
```

Its native input is `phalcom-native-surface`, not `phalcom-core`.

Its output maps canonical declaration/member identity to the implemented Spec 01.5 callable/signature registry plus implementation/presentation metadata.

# 7. Replace handwritten native semantic surfaces

This is the highest-priority implementation tranche.

## 7.1 Current transitional function

Delete eventually:

```text
phalcom-semantic/src/types/native.rs
    register_standard_surfaces(...)
```

The generic type-normalization helpers in the same file remain valuable and should be retained/moved as appropriate.

## 7.2 Generic native registration algorithm

For every generated `phalcom-native-surface` method record, in stable key order:

1. map `UniverseKey` to the core `DeclarationId`;
2. resolve the declaration's canonical type form/kind;
3. lower native generic parameters if/when present;
4. lower each parameter type using existing `resolve_native_type_form` machinery;
5. lower the return type;
6. preserve external labels from selector/callable metadata;
7. construct or look up the canonical `CallableId`;
8. populate `CallableSemanticSignature` with `EvidenceAuthority::TrustedNative` / the ratified native authority;
9. attach the callable ID to the declaration-side selector surface;
10. retain implementation origin separately as native;
11. emit a structured diagnostic if any declared native type form cannot be resolved;
12. never silently substitute `Object`, `Dynamic`, or `Unknown` when the metadata claims a concrete unsupported form.

## 7.3 Selector/callable conformance

For every `PrimitiveSurfaceSpec`, validate:

```text
selector slot count == declared parameter count
selector labels       == callable external labels
params                 agrees with callable.parameters
returns                agrees with callable.return_type
side                   agrees with target runtime side
visibility             agrees with installed member visibility
```

The primitive macro already performs some of this. The generated-surface importer should still assert the invariant at the boundary because generated artifacts can be stale/corrupt and may later be loaded from packaged toolchains.

## 7.4 Generic native methods

The current native macro/type-spec system has type-expression support but may not yet expose method-generic binders.

Do not invent a second generic syntax in Spec 03.5.

When Spec 04 makes generic method declaration syntax canonical, the native metadata model may gain an explicit generic-signature field compatible with Spec 01.5.

Until then:

- core class generic parameters may be referenced according to the already supported native type spec;
- genuinely method-generic native methods remain gated;
- no fake monomorphic signature is permitted.

## 7.5 Error policy

A malformed built-in native surface is a toolchain defect, not an ordinary user diagnostic.

Recommended startup/build behavior:

```text
native manifest duplicate key        -> deterministic startup/build failure
unknown UniverseKey                  -> impossible by enum construction
unresolvable declared native type    -> internal semantic diagnostic + compile gate
selector/type arity mismatch         -> macro compile error when local; manifest validation error when loaded
runtime installer mismatch           -> invariant failure in tests/debug; structured initialization failure in release
```

## 7.6 End state

Neither `phalcom-semantic` nor `phalcom-lsp` should maintain a manually curated list of Int/Float/String/etc methods.

It should conceptually do:

```rust
core_surface::register_native_surfaces(
    native_catalog,
    &mut semantic_db,
    ...
)?;
```

Adding a new `#[primitive]` with valid metadata, followed by the deterministic native-surface generation/check step, should automatically make that callable visible to static core dispatch and VM-free LSP tooling without editing either `phalcom-semantic` or an `NATIVE_MEMBERS` table.

That is the key acceptance law of Spec 03.5.

# 8. Source/native surface merge

## 8.1 Why a merge is necessary

The universe is a mixed implementation library:

- some behavior is source-defined;
- some behavior is native;
- some source methods are wrappers around native primitives;
- some native primitives may be intrinsified;
- future generated methods may coexist with both.

A useful core browser cannot choose only one source.

## 8.2 Merge key

Merge by canonical callable identity:

```text
(owner declaration, dispatch side, selector)
```

not by function name, arity alone, source filename, or Rust symbol.

## 8.3 Merge outcomes

Define explicit outcomes:

```rust
enum SurfaceMergeOutcome {
    SourceOnly,
    NativeOnly,
    SourceDeclarationNativeImplementation,
    SourceWrapperOverNative,
    Generated,
    Conflict(SurfaceConflict),
}
```

The second and third cases are important for core source presentation.

## 8.4 Native-only method

A native-only method appears in the canonical presented class surface even if no `.ph` method body exists.

Example conceptual presentation:

```text
Bool
  not() -> Bool
    implementation: native primitive
    intrinsic: BoolNot
    effects: pure
```

This solves the “empty source shell” problem without fabricating source declarations.

## 8.5 Source-only method

A source method appears normally with its true source range/body and no native badge.

## 8.6 Source declaration + native implementation

If Phalcom later adopts explicit native declaration stubs in `.ph`, they must be represented as **declarations without executable source bodies**, linked by canonical key to a native implementation.

Spec 03.5 must not introduce this new source grammar ahead of Spec 04 or a dedicated native-declaration syntax decision.

For now, this role can exist internally/presentationally without parser syntax.

## 8.7 Source wrapper over native

If a source method intentionally calls another internal primitive, both remain real methods with different keys. Do not merge them merely because they are semantically related.

## 8.8 Conflict

If source and native providers independently claim the same executable key with no explicit binding role, reject the ambiguity.

Never use “native wins” or “source wins” as an undocumented precedence rule.

# 9. Implementation provenance model

## 9.1 Why provenance is separate from type metadata

These facts answer different questions:

```text
return type Int           -> semantic type fact
native Rust primitive     -> implementation fact
pure                      -> semantic behavior summary
intrinsic BoolNot         -> optimization/implementation trait
file src/primitive/...    -> debug source provenance
```

Do not overload `PublishedTypeAuthority` or `EvidenceAuthority` with implementation origin.

## 9.2 Recommended data types

Add to a VM-free shared model, preferably `phalcom-native-meta` for native records and `phalcom-semantic::core_surface` for merged records:

```rust
#[derive(Clone, Copy, Debug, Eq, Hash, PartialEq)]
pub enum ImplementationKind {
    Source,
    NativePrimitive,
    Generated,
    Abstract,
    External,
}

#[derive(Clone, Debug, Eq, PartialEq)]
pub struct MethodImplementationInfo {
    pub kind: ImplementationKind,
    pub intrinsic: Option<StableIntrinsicId>,
    pub trust: ImplementationTrust,
    pub abi: Option<PrimitiveAbi>,
    pub source: Option<ImplementationSource>,
}
```

`StableIntrinsicId` should project the existing enum without forcing its Rust enum representation into long-lived external schemas if versioning becomes necessary.

## 9.3 Runtime mapping

Do not add this structure to `MethodObject`.

Extend the existing side-table architecture:

```rust
pub struct MethodImplementationIndex {
    by_method: HashMap<ObjRef, RuntimeImplementationRef>,
}
```

or unify the two external mappings into:

```rust
pub struct MethodMetadataIndex {
    by_method: HashMap<ObjRef, RuntimeMethodMetadataRef>,
}

pub struct RuntimeMethodMetadataRef {
    pub callable: Option<RuntimeCallableRef>,
    pub implementation: Option<RuntimeImplementationRef>,
}
```

Recommendation: **unify the side-table entry, not the durable schemas**. One hash lookup per reflected method is preferable to multiple independent maps, while semantic callable metadata and implementation metadata remain logically separate.

## 9.4 Installation binding

`phalcom-core/src/native/install.rs` has the exact live `method_id` at installation time.

Immediately after:

```rust
let method_id = vm.heap.alloc(Object::Method(...));
```

bind:

```text
method_id -> native PrimitiveKey / implementation record
```

When semantic metadata later resolves the same callable, enrich the same side-table entry with `RuntimeCallableRef`.

Do not search all classes by selector after installation to reconstruct this relation.

## 9.5 World mutation

If methods can be replaced reflectively, implementation metadata follows the live method object, not merely `(class, selector)`.

Replacing a method creates/installs a different method object and must not leave the old native provenance attached to the new method.

The side table therefore keys by `ObjRef` as Spec 03 already does.

# 10. Native documentation

## 10.1 Current gap

Source Phaldoc can be harvested from `.ph` files. Native methods often have useful Rust `///` documentation, but that documentation is not currently a canonical Phalcom API documentation input.

## 10.2 Capture docs at macro expansion

The procedural macro already receives `syn::ItemFn`, including its attributes.

Extract `#[doc = "..."]` attributes during expansion and emit a static native documentation record.

Suggested model:

```rust
#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub struct NativeDocumentationSpec {
    pub text: &'static str,
    pub format: NativeDocumentationFormat,
}

pub enum NativeDocumentationFormat {
    PhaldocCompatibleMarkdown,
    PlainMarkdown,
}
```

Do not retain a `Vec<String>` in each descriptor at runtime. Emit one concatenated static string.

## 10.3 Documentation style rule

Rust documentation attached to a Phalcom primitive should describe the **Phalcom API contract**, not Rust implementation mechanics.

Good:

```rust
/// Returns the number of one bits in the absolute integer value.
///
/// @returns Number of set bits.
```

Less useful as public Phaldoc:

```rust
/// Calls `BigInt::magnitude().to_u32_digits()` and folds the limbs.
```

Implementation details may still exist in normal Rust comments below the public doc block.

## 10.4 Merge with source Phaldoc

For a source-defined method:

```text
source Phaldoc wins because source declaration is authoritative
```

For a native-only method:

```text
native documentation is the Phaldoc source
```

For a future source-declaration/native-implementation pair:

```text
source declaration Phaldoc is public API documentation
native Rust docs are developer implementation documentation
```

Do not concatenate two conflicting public descriptions silently.

## 10.5 Existing LSP parser reuse

`phalcom-lsp/src/hover.rs` already defines `PhaldocDoc` parsing/normalization behavior.

Long-term, the Phaldoc data model/parser should move to a reusable crate/module so source Phaldoc and native docs share one parser.

Do not duplicate tag alias rules in the primitive macro.

A practical staged route is:

1. macro captures raw docs;
2. semantic/presentation layer carries raw docs;
3. LSP reuses its existing parser for rendering;
4. later extract `PhaldocDoc` into a shared package when a standalone documentation tool needs it.

# 11. Conceptual implementations: the “fake body” problem

A major goal is to let a user conceptually understand native methods without falsely claiming the displayed body is executable Phalcom source.

There are three possible designs.

## 11.1 Option A — place fake Phalcom bodies in real universe `.ph` source

Example:

```phalcom
class Bool {
  not {
    self.ifTrue { false }.ifFalse { true }
  }
}
```

while the runtime actually installs a Rust primitive for `not`.

**Reject.**

Reasons:

- the compiler may accidentally compile/install the body;
- navigation lies about execution provenance;
- tests may validate the fake body instead of the native implementation;
- semantic drift becomes harder to detect;
- bootstrap ordering/duplicate selector behavior becomes ambiguous;
- users may expect edits to the displayed body to affect execution.

## 11.2 Option B — mechanically translate Rust bodies to Phalcom-like code

**Reject.**

Rust implementations use representation details, VM helpers, error machinery, BigInt operations, stack windows, and optimized paths that do not have one faithful Phalcom translation.

A translation would be pseudo-decompilation, not semantics.

## 11.3 Option C — explicit non-executable conceptual presentation

**Ratify.**

A native method may optionally carry a conceptual explanation or Phalcom-like sketch that is tagged as presentation-only.

Recommended model:

```rust
pub enum ConceptualPresentation<'a> {
    None,
    Narrative(&'a str),
    PhalcomSketch(&'a str),
    SemanticTemplate(ConceptualTemplateId),
}
```

This data is never passed through the normal parser/compiler pipeline.

## 11.4 Why allow both narrative and sketch

Some operations are naturally expressible as a sketch:

```text
Bool.not
conceptual sketch:
    self.ifTrue(|| { false }, ifFalse: || { true })
```

Others are better explained narratively:

```text
Int.bitAt(index)
conceptual behavior:
    returns the two's-complement bit at a non-negative index;
    very large indices use sign extension
```

Forcing every primitive into pseudo-source would make complex implementation details look simpler than they are.

## 11.5 Semantic templates for common primitives

For a small number of sacred/intrinsic methods, a structured template may be better than free text:

```rust
enum ConceptualTemplateId {
    BoolNot,
    BoolAndLazy,
    BoolOrLazy,
    BoolIfTrue,
    BoolIfFalse,
    BoolIfTrueIfFalse,
}
```

The renderer knows how to show these in current Phalcom syntax.

This avoids duplicating strings across primitives and makes intrinsic semantics testable.

Do not create dozens of templates prematurely. Start with cases where the semantics are language-significant.

## 11.6 Macro authoring syntax

A later 03.5 workstream may add native-only fields such as:

```rust
#[phalcom_native_macros::primitive(
    Bool,
    "not",
    params = [],
    returns = Bool,
    types = "() -> Bool",
    intrinsic = BoolNot,
    effects = pure,
    conceptual = template(BoolNot)
)]
```

or:

```rust
conceptual = phalcom("self.ifTrue(|| { false }, ifFalse: || { true })")
```

The macro MUST NOT parse the sketch as authoritative method source.

If syntax validation is desired, use a presentation-only parser/linter and report its failure as a documentation build error—not as a semantic method-body error.

## 11.7 Rendered virtual source

A tool may render:

```text
class Bool {
  @native
  @intrinsic(#BoolNot)
  @pure
  not -> Bool

  // conceptual equivalent — non-executable
  // self.ifTrue(|| { false }, ifFalse: || { true })
}
```

The `@native`, `@intrinsic`, and `@pure` lines in this view are **presentation annotations**, not necessarily legal user-source attributes.

The renderer must visually label the file/document as generated semantic presentation.

# 12. Presentation IR

## 12.1 Do not synthesize parser AST

Spec 03.5 needs a dedicated immutable presentation IR so it can run in parallel with Spec 04 and avoid coupling documentation to syntax AST evolution.

Suggested structures:

```rust
pub struct ClassPresentation {
    pub declaration: StableDeclarationRef,
    pub name: Box<str>,
    pub kind: PresentedDeclarationKind,
    pub generic_signature: Option<PresentedGenericSignature>,
    pub superclass: Option<PresentedTypeForm>,
    pub members: Box<[MethodPresentation]>,
    pub docs: Option<PresentedDocumentation>,
}

pub struct MethodPresentation {
    pub callable: StableCallableRef,
    pub display_signature: Box<str>,
    pub implementation: MethodImplementationPresentation,
    pub semantic_summary: MethodSemanticSummary,
    pub docs: Option<PresentedDocumentation>,
    pub conceptual: Option<ConceptualPresentationRecord>,
}
```

## 12.2 Semantic summary

```rust
pub struct MethodSemanticSummary {
    pub effects: PresentedEffects,
    pub raises: PresentedRaises,
    pub flow: PresentedReturnFlow,
    pub stability: PresentedStability,
    pub lifecycle: PresentedLifecycle,
}
```

These are projections of authoritative metadata. They are not a second semantic calculus.

## 12.3 Renderer interface

Presentation should support multiple renderers:

```rust
trait SurfaceRenderer {
    type Output;
    fn render_class(&self, class: &ClassPresentation) -> Self::Output;
}
```

Initial renderers:

- concise hover Markdown;
- full virtual Phalcom-like source;
- Phaldoc/API page model;
- debug/CLI textual dump.

## 12.4 Deterministic ordering

Members sort by a stable key such as:

```text
side -> selector canonical encoding
```

not hash-map iteration order or Rust registration order.

This is necessary for golden docs, virtual documents, reproducible builds, and meaningful diffs.

# 13. Runtime reflection surface

Spec 03 already supplies semantic type reflection. Spec 03.5 may add implementation reflection without changing `MethodObject` layout.

## 13.1 Minimal public surface

Recommended additive selectors on `Method`:

```phalcom
implementationKind -> Symbol
isNative -> Bool
isIntrinsic -> Bool
```

Possible symbols:

```text
#source
#native
#generated
#abstract
#external
```

These answer non-sensitive high-level provenance.

## 13.2 Detailed implementation object

Detailed information should be an explicit reflection query rather than a large group of getters on `Method`:

```phalcom
TypingContext.implementationOf(_ method: Method) -> TypingResult
```

or, if this is considered general rather than typing reflection:

```phalcom
Reflection.implementationOf(_ method: Method) -> ReflectionResult
```

Recommendation: put implementation provenance under **general reflection**, while allowing `TypingContext.signatureOf(method)` to remain the type-specific path.

Do not make typing context the owner of non-typing facts merely because it already has method metadata.

## 13.3 Capability policy

High-level `#native` / `#source` classification can be public.

Detailed Rust source provenance should require a tooling/debug capability/profile.

Never expose privileged implementation internals merely because RuntimePublic type metadata is present.

Suggested capability:

```text
OBSERVE_IMPLEMENTATION_PROVENANCE
```

ToolingDebug may include it; RuntimePublic need not.

## 13.4 Rust source information

Public distributed runtime reflection should not guarantee local absolute Rust file paths.

Expose a logical developer record when available:

```text
module: phalcom_core::primitive::boolean
symbol: bool_not
sourceFile: optional debug path
line: optional debug line
```

The first two can be stable enough for development tooling. File and line remain optional.

# 14. LSP integration

## 14.1 Hover composition

`phalcom-lsp/src/hover.rs` already composes keyword, selector, and Phaldoc information.

Add a canonical-core presentation contribution.

A hover for `Bool.not` should be able to show, compactly:

```text
Bool.not -> Bool
native primitive · intrinsic BoolNot · pure

Returns the logical negation of the receiver.
```

A hover for `Int.bitCount` can show:

```text
Int.bitCount -> Int
native primitive · pure

Returns the number of set bits in |self|.
```

Do not dump Rust paths by default.

## 14.2 Replace fake AST sentinels with explicit member origin

When 03.5 touches the LSP core surface, replace the assumption that every `MemberSurface` has a valid AST reference.

Recommended representation:

```rust
#[derive(Clone, Debug)]
pub enum MemberOrigin {
    Source(MemberAstRef),
    Native(NativeSurfaceId),
    Generated(GeneratedMemberOrigin),
}

pub struct MemberSurface {
    ...
    pub origin: MemberOrigin,
}
```

Then:

```rust
ModuleSurface::callable_index()
```

indexes only `MemberOrigin::Source`, while native definition/presentation queries use `NativeSurfaceId` directly.

Remove:

```text
usize::MAX AST indexes
Default::default() source ranges as native identity
```

A zero/default range may still be used in a protocol type that requires an optional range only if the API explicitly represents “no source range”; it must not stand in for a real location.

The current `native_return: Option<NativeReturnShape>` field should be deprecated as an independent typing authority. Once the generated native surface carries full callable types and `phalcom-semantic` imports them, LSP typing should use the formal semantic signature. A coarse return-shape projection may remain only as a deliberately advisory fallback for incomplete semantic snapshots.

## 14.3 Signature help/completion

Where the LSP already consults core semantic surfaces, switch the provider to the canonical surface generated from primitive metadata.

The goal is stronger than displaying native annotations:

> every native primitive that is part of the canonical public surface becomes statically discoverable automatically.

## 14.4 Definition navigation

Three navigation tiers are useful:

### Tier 1 — real Phalcom source exists

Navigate to the true `.ph` declaration/body.

### Tier 2 — native-only method in developer checkout

Navigate to a generated virtual core document by default, with an optional “open native implementation” action that targets Rust source when the workspace contains the compiler repository.

### Tier 3 — installed runtime/SDK

Navigate to the generated virtual core document or packaged API documentation. Do not manufacture an invalid filesystem URI to a Rust source path that does not exist.

## 14.5 Virtual core document

Introduce an internal URI namespace only if the client/backend architecture can support it cleanly, for example:

```text
phalcom-core:/universe/Bool
```

The content is generated from `ClassPresentation`.

This document is read-only and explicitly marked generated.

If custom virtual document delivery would require substantial editor protocol work, 03.5 may initially provide the same presentation through hover and a CLI/debug dump. The presentation IR must not depend on a particular client transport.

## 14.6 No second type checker

LSP never reconstructs callable types from `PrimitiveSurfaceSpec` itself.

It consumes the compiler-owned canonical semantic surface or its published presentation projection.

That preserves the Spec 01 rule of one formal semantic authority.

# 16. Metadata and artifact strategy

## 16.1 RuntimePublic should stay lean

Raw Rust source paths, full docs, and conceptual bodies are not necessary for ordinary runtime type reflection.

Do not put them into the mandatory core `SemanticMetadataBundle` fields.

## 16.2 Use the 02.5 extension seam

Spec 02.5 established extension sections precisely for optional durable domains.

Recommended tooling extension:

```text
feature id: core.implementation-presentation
schema version: 1
required: false
```

Potential contents:

```rust
pub struct ImplementationPresentationSection {
    pub methods: Box<[ImplementationPresentationRecord]>,
}
```

Key records by `StableCallableRef` or stable primitive key, never by runtime `ObjRef`.

## 16.3 Profiles

Suggested retention:

| Data | RuntimeMinimal | RuntimePublic | ToolingDebug | Proof |
|---|---:|---:|---:|---:|
| implementation kind | optional/no | yes or derivable | yes | yes |
| intrinsic ID | no | optional | yes | yes |
| effects/raises summary already required semantically | as required | as required | yes | yes |
| public docs | no | optional | yes | yes |
| conceptual body | no | no | yes | optional |
| Rust module/symbol | no | no | yes | optional |
| raw file/line | no | no | debug-only | no requirement |

If `RuntimePublic` can derive native/source classification from already-loaded runtime method state, do not duplicate it in metadata.

## 16.4 Compatibility

The extension is optional. An older runtime that does not understand it may ignore it unless marked required.

Core type metadata schema does not need another breaking bump merely to add presentation.

# 17. Source annotations and displayed annotations

## 17.1 Presentation annotations are not necessarily language attributes

Tools may render:

```text
@native
@intrinsic(#BoolNot)
@pure
```

as **display annotations**.

This does not mean user code can write them or that Spec 04 must add them to grammar.

## 17.2 Future source-level native declarations

A future language design may choose explicit source declarations such as:

```phalcom
@native
not -> Bool
```

with no body.

That is a separate syntax decision and should be ratified only after Spec 04 establishes typed declaration grammar.

Spec 03.5 prepares the semantic link but does not force this syntax.

## 17.3 Why this separation matters

It allows immediate tooling improvement without creating a backwards-compatibility commitment around `@native`, `@intrinsic`, or fake bodies in user syntax.

The primitive manifest already carries behavior summaries that are richer than the current manually registered static surface.

```rust
EffectSpec::Pure
EffectSpec::Known([...])
EffectSpec::Unknown
```

Keep unknown explicit.

## 18.2 Raises summary



and presentation renders the canonical form.

# 19. Intrinsic semantics

## 19.1 Intrinsic ID is not semantic truth by itself

`NativeIntrinsicId::BoolNot` identifies a compiler/runtime optimization opportunity.

The callable signature and behavior contract remain separate metadata.

## 19.2 Intrinsic conformance

Each intrinsic ID must have a single canonical expectation record describing at least:

- legal owner/selector;
- expected side;
- required callable shape;
- semantic guard conditions;
- fallback primitive requirement where applicable.

Tests should prove that a primitive claiming `BoolNot` matches that expectation.

## 19.3 Presentation

Tooling can show an intrinsic badge because it helps explain why a core method may be optimized specially.

It should not imply that the method lacks a normal message-send meaning.

# 20. Performance requirements

## 20.1 No per-query registry scans

Build an indexed native/core catalog once.

Do not scan every primitive on each hover, completion, semantic member lookup, or reflection query.

## 20.2 No hot MethodObject growth

Keep implementation metadata in side tables / shared immutable catalogs.

## 20.3 No presentation allocation during ordinary execution

If the user does not invoke reflection/tooling, VM execution should not allocate docs or rendered conceptual bodies.

## 20.4 String rendering is demand-driven

Store structured records and static strings. Render full virtual source only on request.

## 20.5 Catalog fingerprint

Compute a deterministic structural fingerprint from the native surface catalog.

This supports:

- cache invalidation;
- reproducible tests;
- stale LSP core-surface detection;
- artifact compatibility diagnostics.

The fingerprint must ignore unstable raw file paths if they are debug-only.

# 21. Security and authority

## 21.1 Internal primitives

A presentation layer may know an internal method exists, but public reflection/tooling must respect existing visibility policies.

Do not expose internal selectors in an ordinary public API listing unless the user/tooling context has corresponding authority.

## 21.2 Privileged trust

`NativeTrust::Privileged` is implementation authority.

Do not surface it as a user-settable attribute and do not let a conceptual presentation inherit privileged execution rights.

## 21.3 Source paths

Absolute build-machine paths can leak environment details.

Before durable serialization, normalize or omit raw paths. Prefer logical module/symbol identifiers.

## 21.4 Conceptual text

Treat conceptual text as documentation content. It cannot cause reflective invocation, evaluation, macro expansion, or code loading.

# 22. Conformance framework

Introduce a single cross-layer validator that can answer:

> Does the core semantic surface presented to the compiler/tooling match what the runtime can actually install?

## 22.1 Required checks

For every native descriptor:

- key is unique;
- owner exists in universe catalog;
- selector is canonical;
- selector shape matches callable metadata;
- types lower successfully;
- class/instance side is valid;
- internal selector/visibility invariants hold;
- intrinsic claim is valid;
- lifecycle metadata is internally consistent;
- replacement selector exists or is explicitly external/deferred when policy requires;
- runtime descriptor exists;
- semantic callable is generated;
- presentation record can be generated.

For every canonical source method:

- source callable has stable identity;
- source/native collision is classified;
- source docs attach to the correct member;
- source implementation is not mislabeled native.

## 22.2 Census tests

Add deterministic counts/snapshots by owner and side, for example:

```text
Bool instance native methods: ...
Int instance native methods: ...
...
```

Do not assert only a global count; per-owner snapshots make drift actionable.

## 22.3 Differential test

After migration:

```text
native catalog semantic surface
    ==
semantic DB core callable surface
```

for every supported native primitive after canonical lowering.

This is the test that makes deletion of `register_standard_surfaces` safe.

# 28. Rejected alternatives

## 28.1 Keep handwritten semantic core methods

Rejected because it guarantees drift and makes every new primitive a multi-file semantic change.

## 28.2 Generate `.ph` files and compile them as core truth

Rejected for native methods because generated bodies would either be fake or would require a new native-binding syntax. The canonical semantic manifest should not be forced through source syntax merely to appear source-like.

## 28.3 Put all primitive metadata on `MethodObject`

Rejected due hot-object memory cost, GC tracing concerns, runtime/tooling coupling, and existing successful side-table architecture.

## 28.4 Treat Rust source as the documentation/source browser

Rejected as the primary user view. Rust code exposes VM representation mechanics rather than Phalcom semantic contracts and is unavailable in many installed environments.

It remains an optional developer navigation target.

## 28.5 Automatically infer conceptual source from Rust

Rejected as unsound and misleading.

## 28.6 Make every implementation detail public runtime reflection

Rejected. High-level provenance is useful; raw source/debug/trust internals should remain capability/profile controlled.

## 28.7 Introduce `@native` user syntax now

Rejected for this tranche because Spec 04 is about to establish typed declaration grammar and attributes must not be rushed into a backwards-compatible surface merely to solve presentation.

# 32. Final normative architecture

After Spec 03.5, the core method pipeline should read conceptually as:

```text
                         AUTHORING

        .ph source                         Rust primitive source
            |                          #[primitive(...)]
            |                             /           \
            |                    proc macro             generator
            |                       |                     |
            |                       v                     v
            |                  PRIMITIVES       phalcom-native-surface
            |                 descriptors        generated records
            |                       |                 /       \
            |                       |                /         \
            |                       |        semantic import    VM-free LSP
            |                       |              |               |
            v                       |              v               v
   source declaration surface       |       CanonicalCoreSurface presentation
   source body / Phaldoc             |              |               |
            |                        |              v               v
            +------------------------+------> runtime provenance  hover/docs
                             |               /      |
                             v              /       v
                     compiler semantics    /    reflection
                     CallableId/signature /
                             |            /
                             v           /
                         typecheck       /
                         dispatch       /

                         EXECUTION

 PRIMITIVES / PrimitiveDescriptor ----------> sole VM native installation
 .ph compiled source -----------------------> bytecode method installation

```

The critical invariant is:

> **One semantic surface, multiple faithful projections.**

Native execution remains native. Source execution remains source. The rich `#[primitive]` declaration is authored once; `PRIMITIVES` and `phalcom-native-surface` are checked projections of it. Static semantics sees the complete canonical callable surface. Reflection can say which implementation class backs a method. Documentation and IDEs can show a coherent Phalcom-facing universe. Conceptual bodies can explain native semantics without becoming a lie about executable source.

That is the purpose of Spec 03.5.
