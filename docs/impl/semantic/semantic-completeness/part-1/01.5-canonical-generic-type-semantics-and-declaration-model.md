## 1. Purpose and authority

This document fills the semantic gap between Spec 01's compiler-owned query architecture and the later specifications that serialize, reify, parse, display, or consume typing facts.

The central rule is:

> **Phalcom has one canonical generic semantic language. Source syntax, native declarations, generated declarations, compiler checking, LSP presentation, CLI checking, REPL analysis, durable metadata, and runtime reflection are projections of that language. None owns a second interpretation of generics.**

Spec 01 remains authoritative for identity lifetimes, proper-type boundaries, query state, cancellation, budgets, invalidation, snapshots, and formal ownership. This specification is authoritative for what a generic declaration or type-level form *means* once represented inside that architecture.

This document intentionally precedes durable metadata and public reflection. A metadata schema cannot be frozen before it knows the semantic objects it must encode, and a reflection API cannot truthfully expose generic information before the compiler has one canonical declaration model.

## 2. Repository-grounded current state

### 2.1 Existing generic kernel is real but incomplete

**Observed current implementation.** `phalcom-semantic` already has the right low-level separation between canonical type-form identity and kind identity. [`TypeId`](../../../../phalcom-semantic/src/types/id.rs#L3) is explicitly store-local and may denote either a proper type or constructor form; [`KindId`](../../../../phalcom-semantic/src/types/id.rs#L22) is separately interned. [`KindData`](../../../../phalcom-semantic/src/types/kind.rs#L5) contains `Type` and arrow kinds. [`TypeStore::apply_type_form`](../../../../phalcom-semantic/src/types/store.rs#L257) kind-checks application, supports partial application, and flattens an already-applied origin before interning the result.

This is retained. Phalcom does not need a replacement type kernel; it needs a complete semantic layer around it.

### 2.2 Type parameters have correct owner/index identity but insufficient data

**Observed current implementation.** [`TypeParameterOwner`](../../../../phalcom-semantic/src/types/parameter.rs#L6) distinguishes declaration and callable ownership. [`TypeParameterData`](../../../../phalcom-semantic/src/types/parameter.rs#L12) contains owner, `u16` index, source name, and kind. [`GenericSignature`](../../../../phalcom-semantic/src/types/parameter.rs#L20) contains only owner and parameter IDs.

This is a sound identity seed: textual names are not semantic identity. It is insufficient for declaration-site variance, `where` constraints, source provenance, generic interface fingerprints, and generic method inference.

### 2.3 Current canonical type forms do not include type lambdas or `Self`

**Observed current implementation.** [`TypeData`](../../../../phalcom-semantic/src/types/store.rs#L32) contains `Never`, `Unit`, `ClassObject`, nominal forms, applications, unions, tuples, records, callables, declaration parameters, and inference variables. There is no canonical type-lambda form and no canonical owner-relative `Self` form.

`TypeLambda` and `Self` therefore cannot be added honestly by metadata or reflection alone. They must first exist in this semantic layer.

### 2.4 Substitution is eager and allocation-heavy

**Observed current implementation.** [`TypeSubstitution::apply`](../../../../phalcom-semantic/src/types/substitution.rs#L33) recursively clones/rebuilds applications, unions, tuples, records, and callables into `TypeStore`. [`substitution_for_applied`](../../../../phalcom-semantic/src/types/substitution.rs#L110) constructs a `HashMap<TypeParameterId, TypeId>` by pairing declaration generic parameters with application arguments.

This implementation is a useful **materialization primitive**, but it must not become the default strategy for every specialized member lookup, hover, completion request, inherited member lookup, relation query, or method call. Doing so would turn generic use into repeated subtree reconstruction and interning.

### 2.5 Generic relations are currently hard-coded invariant

**Observed current implementation.** [`is_subtype`](../../../../phalcom-semantic/src/types/relation.rs#L79) is boolean and [`TypeData::Applied`](../../../../phalcom-semantic/src/types/relation.rs#L126) is currently a subtype only when origins and argument arrays are exactly equal. The declaration hierarchy stores only `DeclarationId -> DeclarationId`, so it cannot represent a generic superclass template such as `Names<T> is Sequence<Option<T>>`.

Spec 01 separately requires result-rich bounded relations. This specification supplies the missing generic relation semantics those relation queries must use.

### 2.6 Current local constraint solving is not a generic method solver

**Observed current implementation.** [`TypeConstraint`](../../../../phalcom-semantic/src/types/constraint.rs#L9) has equality, subtype, and `HasMember`. [`LocalConstraintSolver`](../../../../phalcom-semantic/src/types/constraint.rs#L34) binds inference variables directly to `TypeId`s, returns a boolean from `solve`, and leaves `HasMember` to another layer. It does not model independent lower/upper candidate sets, ambiguity, underconstraint, occurs-check failure, bounded recursive generic constraints, or cancellation.

The current solver remains a seed/test scaffold. It is not the normative algorithm for generic method inference.

### 2.7 Semantic callable signatures are duplicated and cloned

**Observed current implementation.** [`CallableSignature`](../../../../phalcom-semantic/src/dispatch.rs#L52) stores selector, `Vec<CallableParameter>`, and return knowledge. [`MemberSurface`](../../../../phalcom-semantic/src/surface.rs#L9) separately stores fields by name, fields by `FieldId`, callable return knowledge by `CallableId`, and complete callable signatures by selector. [`SurfaceDispatchResolver::resolve_dispatch_on_owner`](../../../../phalcom-semantic/src/dispatch.rs#L105) returns a cloned signature.

[`register_class_surface`](../../../../phalcom-semantic/src/checker/declaration.rs#L24) repeatedly lowers annotations while building the surface, and body checking later lowers many of the same annotations again. This is the wrong ownership boundary for generic specialization: a callable must have one stable semantic identity and one canonical declared signature, while specialization is a view over that signature.

### 2.8 Call checking consumes already-materialized signatures

**Observed current implementation.** [`match_callable_arguments`](../../../../phalcom-semantic/src/checker/call.rs#L27) walks a concrete `CallableSignature`, compares synthesized argument knowledge to the stored concrete parameter knowledge, and returns a cloned return `TypeKnowledge`. It has no generic instantiation phase and no expected-result-driven method type argument inference.

### 2.9 Source and native declarations cannot yet express the target model

**Observed current implementation.** [`ClassDef`](../../../../phalcom-ast/src/ast.rs#L227) has no generic binder list. [`MethodDef`](../../../../phalcom-ast/src/ast.rs#L702) has no generic binder/constraint list. Existing `TypeAnnotationExpr` is richer than the source parser, while [`Parser::parse_type_annotation`](../../../../phalcom-ast/src/parser.rs#L1396) currently parses only static references/qualified names.

**Observed current implementation.** [`phalcom-native-meta/src/types.rs`](../../../../phalcom-native-meta/src/types.rs#L5) supports `Type`/arrow kinds and symbolic generic parameter names, but its parameter records have no variance or canonical constraints, and its type-expression vocabulary has no type lambda.

The source parser and native parser may remain separate front ends. Their *lowered semantic output* must converge here.

### 2.10 Runtime methods intentionally do not contain static generic signatures

**Observed current implementation.** [`MethodObject`](../../../../phalcom-core/src/method/object.rs#L158) stores the runtime calling signature, holder, visibility/access metadata, contract closures, and attributes. It does not carry a compiler `CallableSignature` or generic semantic tree.

That is the correct runtime default. This specification does **not** authorize inflating every runtime method object with static generic state. Runtime reflection may use an external metadata/identity side table when metadata is retained.

### 2.11 LSP callable summaries are advisory, not formal generic authority

**Observed current implementation.** `phalcom-lsp/src/semantic/callable.rs` defines its own advisory `CallableSignature`, `ParameterSignature`, and interprocedural `CallableSummary`. Spec 01 already requires the compiler-owned formal snapshot to remain authoritative while LSP `ValueShape` analysis remains advisory.

Generic declarations, constraints, inferred method type arguments, `Self`, and specialized member types therefore come from `phalcom-semantic`; LSP may present or enrich them but may not invent a second formal generic calculus.

## 3. Non-negotiable semantic laws

### 3.1 Two axes remain distinct

**Ratified/normative design.** The completed tower remains unchanged:

```text
value.class     runtime class identity
value : T       static value-typing judgment
T :: K          kinding judgment over a type form
```

A runtime class object may *denote* a nominal type form or constructor, but the runtime object and the semantic form are not collapsed.

Examples:

```text
42.class == Int
42 : Int
Int :: Type

List.class == List class
List :: Type -> Type
List<Int> :: Type
```

`Type` is an atomic kind. Nothing in this document derives `Type :: Type`.

### 3.2 Static typing never changes runtime dispatch identity

For every program that differs only in legal type metadata:

```text
selector(program_typed)   == selector(program_untyped)
class(value_typed)        == class(value_untyped)
layout(C_typed)           == layout(C_untyped)
metaclass(C_typed)        == metaclass(C_untyped)
allocation(C_typed)       == allocation(C_untyped)
```

Type arguments do not enter selector identity, method lookup, inline-cache keys, field layout, allocation, superclass identity, or metaclass identity.

### 3.3 Generic application is semantic, not runtime specialization

`List<Int>` creates no runtime subclass or metaclass. An ordinary instance still satisfies:

```phalcom
xs.class === List
```

A static fact `xs : List<Int>` belongs to the compiler semantic model, not the object's runtime header.

### 3.4 Canonical semantic equality is not runtime identity

Within one store, canonical structural forms may be represented by equal `TypeId`s. Across stores/snapshots/processes, numeric IDs are not comparable. Durable equivalence is structural/fingerprint-based.

Runtime descriptor `===` is a VM/context caching property, not the definition of semantic equivalence.

### 3.5 A form has exactly one kind in one semantic store

For every publishable canonical type form `t` in store `S`:

```text
exists! k. kind_S(t) = k
```

A value-typing position requires `k = Type`. Constructor-kinded forms are legal only where a constructor is expected or as explicit type-form values.

## 4. Canonical generic semantic domains

### 4.1 Kinds

The required first-order kind calculus remains:

```text
Kind ::= Type | Kind -> Kind
```

Arrow associates right in source:

```text
Type -> Type -> Type
== Type -> (Type -> Type)
```

The implementation may continue canonical flattening into the existing multi-parameter `KindData::Arrow { parameters, result }` representation:

```rust
pub enum KindData {
    Type,
    Arrow {
        parameters: Box<[KindId]>,
        result: KindId,
    },
}
```

Thus the source/kinding judgment:

```text
Map :: Type -> Type -> Type
```

may be represented internally as `parameters = [Type, Type], result = Type`.

Kind arrows express *applicability only*. They do not encode variance.

### 4.2 Stable generic binders

Declaration and callable binders use owner-plus-index identity. Names and ranges are provenance/presentation.

Target record:

```rust
#[derive(Clone, Copy, Debug, Eq, Hash, PartialEq)]
pub enum Variance {
    Covariant,
    Contravariant,
    Invariant,
}

#[derive(Clone, Debug, Eq, Hash, PartialEq)]
pub struct TypeParameterData {
    pub owner: TypeParameterOwner,
    pub index: u32,
    pub name: Box<str>,
    pub kind: KindId,
    pub variance: Variance,
    pub source: Option<SourceOrigin>,
}
```

The increase from `u16` to `u32` is recommended for consistency with dense ID domains and to avoid an arbitrary public semantic ceiling. An implementation may retain compact storage if it proves overflow rejection at lowering boundaries; it must not silently truncate.

### 4.3 Generic signatures own constraints

Constraints belong to the binder *scope/signature*, not to one parameter record:

```rust
#[derive(Clone, Debug, Eq, PartialEq)]
pub struct GenericSignature {
    pub owner: TypeParameterOwner,
    pub parameters: Box<[TypeParameterId]>,
    pub constraints: Box<[GenericConstraint]>,
}

#[derive(Clone, Debug, Eq, Hash, PartialEq)]
pub enum GenericConstraint {
    Subtype {
        lower: TypeTerm,
        upper: TypeTerm,
    },
    Equivalent {
        left: TypeTerm,
        right: TypeTerm,
    },
}
```

This permits constraints involving multiple parameters, enclosing declaration parameters, F-bounds, lower bounds, and higher-kinded applications without duplicating or pretending that every relation is a unary “bound”.

Examples:

```phalcom
class Sorted<T> where T <: Comparable<T> { ... }
class Adapt<A, B> where A <: B { ... }
class Exact<A, B> where A == B { ... }
class Sink<T> where Number <: T { ... }
```

Canonical semantics:

```text
T <: Number      Subtype(lower=T,      upper=Number)
Number <: T      Subtype(lower=Number, upper=T)
T == U           Equivalent(left=T, right=U)
```

`Subtype` is initially a relation between proper forms of kind `Type`; higher-kinded shape is constrained by binder kind annotations and by applying constructors to proper arguments. `Equivalent` requires kind-compatible operands and may compare constructor-kinded forms as well as proper types. A kind mismatch is an invalid constraint, not a false subtype result.

### 4.4 No default generic arguments in the canonical record yet

The previous `default: Option<TypeId>` proposal is removed from the initial canonical data shape. Generic defaults affect application arity, inference, API evolution, reflection, and source compatibility. They require their own design before occupying a versioned schema.

### 4.5 `TypeTerm` and canonical forms

Most lowered declaration signature positions can use canonical `TypeId` directly once `Self` and type lambdas are representable. A distinct `TypeTerm` wrapper is still recommended at declaration/query boundaries to prevent accidentally requiring immediate materialization:

```rust
pub enum TypeTerm {
    Canonical(TypeId),
    SelfType(SelfTypeTerm),
    View(TypeView),            // query-local / non-publishable
    Infer(InferVarId),         // solver-local / non-publishable
}
```

A production implementation may encode `SelfType` as a canonical `TypeData` variant instead. The normative requirement is semantic: declaration signatures must represent owner-relative `Self` without replacing it prematurely with one concrete nominal type, while view/inference terms must be rejected at publication boundaries.

## 5. Generic declaration scopes

### 5.1 Declaration generics

Canonical source intent:

```phalcom
class Box<T> { ... }
class Producer<+T> { ... }
class Consumer<-T> { ... }
class Functor<F: Type -> Type> { ... }
```

Omitted kind is `Type`.

Declaration generic parameters may appear in:

- the declaration's instance-side superclass/supertype template;
- instance fields;
- instance callable parameter/return signatures;
- instance callable `where` constraints;
- nested type forms and type lambdas;
- effects/proofs later, when those specs consume this signature language.

### 5.2 Method generics are independent scopes

Methods may bind their own parameters:

```phalcom
map<U>(transform: (T) -> U) -> List<U> { ... }
```

For `class Box<T>`, `T` and `map<U>` have different semantic owners. Same-name shadowing does not collapse identities:

```phalcom
class Outer<T> {
    convert<T>(value: T) -> T { ... }
}
```

The inner `T` is `TypeParameterOwner::Callable(convert)`, not the declaration parameter.

### 5.3 Class-side generic rule

**Ratified/normative design.** Declaration generic parameters are not implicitly bound on class-side calls because class-side state and dispatch belong to the unspecialized origin class. There is no runtime `Box<Int> class`, no ambient applied-class context, and no transparent forwarding from an applied type descriptor to the origin's class-side method table.

Therefore a class-side callable must not publish a signature with an unbound declaration generic parameter.

Instead, class-side factories declare method generics explicitly:

```phalcom
class Box<T> {
    @class
    make<U>(value: U) -> Box<U> { ... }
}
```

or return a semantically closed type.

This rule also applies to class-side fields: origin-owned class state cannot have a per-specialization `T` value/type merely because the declaration is generic.

A future explicit reflective construction API may consume a type form plus values, but that operation remains explicit and does not alter ordinary class-side dispatch.

### 5.4 Variance is declaration-site only

`+T` and `-T` are allowed only for nominal/declaration generic parameters whose constructor applications participate in subtype relations.

Method generic binders and type-lambda binders do not declare variance. Their kinds express admissible application shapes only.

## 6. Source syntax contract owned semantically by 01.5

Spec 04 owns complete parsing, precedence, recovery, ranges, and formatting. The following fragments are nevertheless normative semantic input and supersede conflicting portions of the current Spec 04.

### 6.1 Generic binder kind annotations use `:`

```ebnf
generic-parameters ::= "<" generic-parameter ("," generic-parameter)* ">"
generic-parameter  ::= variance? identifier kind-annotation?
variance           ::= "+" | "-"
kind-annotation    ::= ":" kind-expression
```

Examples:

```phalcom
class Box<T> { ... }
class Functor<F: Type -> Type> { ... }
map<U>(...) -> U { ... }
```

`::` remains the *semantic kinding judgment* in documentation and reflection reasoning:

```text
List :: Type -> Type
```

It is not the source binder annotation token.

### 6.2 All generic constraints use `where`

Inline parameter bounds are removed.

```ebnf
where-clause       ::= "where" generic-constraint ("," generic-constraint)*
generic-constraint ::= type-form "<:" type-form
                     | type-form "==" type-form
```

Thus:

```phalcom
class SortedSet<T> where T <: Comparable<T> { ... }
```

is valid. Inside a `where` clause, `==` denotes semantic type-form equivalence; it is not an ordinary runtime `==` message send. Constraint operands are kind-checked before relation evaluation. An inline `class SortedSet<T <: Comparable<T>>` form is not part of the language.

### 6.3 Finite exact-set constraints are deferred

The current Spec 04/05 form:

```phalcom
where T in (Int, Float)
```

is removed from the initial canonical generic calculus. It introduces a third constraint relation with separate inference, normalization, reflection, and diagnostics without a current requirement that cannot be represented by later sum/union/protocol design.

The token/idea may be reconsidered later; no metadata enum tag is reserved as if its semantics were final.

### 6.4 Type lambda syntax

The ratified operator is `=>>`. The normative semantic input fragment is:

```ebnf
type-lambda           ::= "<" type-lambda-parameter
                              ("," type-lambda-parameter)* ">"
                          "=>>" type-form

type-lambda-parameter ::= identifier kind-annotation?
```

A type-lambda parameter with no kind annotation defaults to `Type`, exactly like declaration/callable generic parameters.

Examples:

```phalcom
<T> =>> Result<T, Error>
<A, B> =>> Pair<A, B>
<F: Type -> Type, T> =>> F<T>
```

Implementations must tokenize and accept `=>>`, not `>>` or `=>`.

Spec 04 must define exact precedence/recovery. Semantically, the lambda body extends over a complete type form, and parentheses may be used to make a lambda the origin of a subsequent application.

### 6.5 No `F<_>` placeholder syntax

Higher-kinded parameter shape is expressed by its kind:

```phalcom
<F: Type -> Type>
```

and anonymous constructors are expressed by type lambdas:

```phalcom
<T> =>> Result<T, Error>
```

`F<_>` and `F<_, _>` are not generic kind-bound syntax.

## 7. Type application semantics

### 7.1 Application judgment

For a form `F :: K1 -> ... -> Kn -> R` and supplied arguments `A1 :: K1 ... Am :: Km`, where `m <= n`:

```text
F<A1, ..., Am> :: K(m+1) -> ... -> Kn -> R
```

When `m = n`, result kind is `R`.

A value-typing position requires the final result kind to be exactly `Type`.

### 7.2 Canonical flattening law

Application is semantically associative in the argument spine:

```text
apply(apply(F, [A]), [B])  ≡  apply(F, [A, B])
```

This matches the current `TypeStore::apply_type_form` flattening behavior and prevents representational differences between `Map<String><Int>`-style chained internal application and `Map<String, Int>` source sugar.

### 7.3 Partial application

Partial application is first-class at the semantic type-form level:

```text
Map :: Type -> Type -> Type
Map<String> :: Type -> Type
Map<String, Int> :: Type
```

`Map<String>` is invalid as the type of a runtime value because it is not of kind `Type`. It is valid as:

- a higher-kinded argument requiring `Type -> Type`;
- the result/body of a type-level expression requiring that kind;
- an explicit runtime type-form value when reified.

### 7.4 Application pipeline for declarations

Low-level structural kind application and high-level generic declaration application must not be conflated.

Normative high-level pipeline:

```text
origin + supplied arguments
  -> resolve origin kind/signature
  -> validate argument kinds
  -> bind supplied declaration parameters
  -> compute residual kind/remaining parameters
  -> specialize constraints by known bindings
  -> evaluate now-decidable constraints
  -> preserve unresolved constraints for partial application
  -> beta-normalize type-lambda origins when applicable
  -> normalize/canonicalize result
```

Constraint outcomes are not booleans. At minimum:

```rust
pub enum ConstraintCheckOutcome {
    Satisfied,
    Rejected(ConstraintFailure),
    Deferred(DeferredConstraintSet),
    DynamicBoundary(DynamicBoundary),
    Blocked(BlockReason),
    Cancelled,
    BudgetExceeded(BudgetReport),
    InternalFailure(IncidentId),
}
```

`Deferred` is valid for a partial constructor when a constraint references an unsupplied parameter. A fully publishable proper application may not hide a refuted or unsolved required constraint.

### 7.5 No intermediate allocation requirement

The semantic law is expressed in terms of results, not heap/interner steps. Implementations may batch:

```text
apply(F, [A, B])
```

without first interning `F<A>`, and may beta-reduce a type lambda directly without interning `Applied(TypeLambda, args)`.

## 8. Type lambdas

### 8.1 Semantic role

A type lambda is a first-class type-level form, not an executable value closure:

```phalcom
<T> =>> Result<T, Error>
```

It has a kind derived from binder kinds and body kind. For example:

```text
<T> =>> List<T>                     :: Type -> Type
<A, B> =>> Pair<A, B>               :: Type -> Type -> Type
<F: Type -> Type, T> =>> F<T>       :: (Type -> Type) -> Type -> Type
```

The runtime may later reify this semantic form as a `TypeLambda` descriptor when the program explicitly asks to retain/use the form as a value. That descriptor does not execute a Phalcom closure to perform type substitution.

### 8.2 Alpha equivalence is mandatory

Binder names are not semantic identity:

```text
<T> =>> List<T>
≡α
<U> =>> List<U>
```

Therefore canonical lambda identity must not be derived from source binder names or a naive `TypeParameterOwner::TypeLambda(TypeLambdaId)` cycle.

### 8.3 Canonical bound-variable representation

Recommended representation uses a scoped, alpha-normalized body arena:

```rust
#[repr(transparent)]
pub struct TypeLambdaId(u32);

#[repr(transparent)]
pub struct ScopedTypeId(u32);

#[derive(Clone, Debug, Eq, Hash, PartialEq)]
pub enum ScopedTypeData {
    /// Lambda-bound variable; index is semantic identity inside this scope.
    Bound { depth: u32, index: u32 },

    /// A canonical free form from the enclosing semantic store.
    Free(TypeId),

    Applied {
        origin: ScopedTypeId,
        arguments: Box<[ScopedTypeId]>,
    },
    Union(Box<[ScopedTypeId]>),
    Tuple(Box<[ScopedTupleElement]>),
    Record(Box<[ScopedRecordField]>),
    Callable(ScopedCallableType),
    Lambda(TypeLambdaId),
}

#[derive(Clone, Debug, Eq, Hash, PartialEq)]
pub struct TypeLambdaData {
    pub parameter_kinds: Box<[KindId]>,
    pub body: ScopedTypeId,
    pub result_kind: KindId,
}
```

Equivalent locally nameless, de Bruijn, or index-based representations are allowed. The invariant is mandatory: alpha-renaming cannot change structural identity.

Source binder names/ranges belong in provenance:

```rust
pub struct TypeLambdaProvenance {
    pub parameter_names: Box<[Box<str>]>,
    pub parameter_sources: Box<[SourceOrigin]>,
    pub lambda_source: Option<SourceOrigin>,
}
```

Provenance is excluded from semantic equality/hash-consing.

### 8.4 Lambda parameters are not declaration `TypeParameterId`s

Declaration/callable parameters are stable interface binders. Lambda-bound variables are lexical binders internal to a structural type form. They therefore use separate scoped identity.

When reflection materializes lambda parameters, it may expose a logical reference `(TypeLambdaId, index)` plus source name if retained. That runtime reflection identity is derived *after* lambda canonicalization and does not define the lambda's canonical hash.

### 8.5 Beta reduction

Application of a type lambda performs capture-avoiding substitution:

```text
(<T> =>> Result<T, Error>)<Int>
    ↦β Result<Int, Error>
```

For multiple parameters:

```text
(<A, B> =>> Pair<A, B>)<Int, String>
    ↦β Pair<Int, String>
```

Partial application produces a residual constructor/lambda without capturing free variables:

```text
(<A, B> =>> Pair<A, B>)<Int>
    ≡ <B> =>> Pair<Int, B>
    :: Type -> Type
```

The implementation may represent the residual form directly as a normalized lambda or another canonical constructor spine. It must satisfy semantic equivalence and residual-kind laws.

### 8.6 Capture avoidance

Substitution must preserve lexical scope. A free declaration parameter cannot become bound accidentally, and nested lambdas must shift/rename indices correctly.

Required property:

```text
free(substitute(body, env))
= (free(body) - domain(env)) ∪ free(range(env) used by body)
```

modulo bound variables of nested lambdas.

### 8.7 Lambda constraints are not added in the first tranche

Type-lambda binders may have kind annotations. A dedicated `where` clause attached directly to anonymous type lambdas is deferred. This does not prevent a lambda body from referring to enclosing constrained declaration/callable parameters.

## 9. Substitution, environments, and lazy specialization

### 9.1 Semantics versus representation

The semantic meaning of applying `Box<Int>` to an instance member declared with `T` is ordinary substitution. The implementation is **not** required to eagerly reconstruct every member type.

The hot-path representation must prefer a compact environment/view:

```rust
#[derive(Clone, Copy, Debug, Eq, Hash, PartialEq)]
pub struct EnvironmentRef(/* compact arena/small-inline handle */);

pub struct TypeEnvironment {
    pub bindings: SmallBindingMap,
    pub self_binding: Option<SelfBinding>,
}

#[derive(Clone, Copy, Debug, Eq, Hash, PartialEq)]
pub struct TypeView {
    pub root: TypeId,
    pub environment: EnvironmentRef,
}

#[derive(Clone, Copy, Debug, Eq, Hash, PartialEq)]
pub struct SpecializedCallableView {
    pub callable: CallableId,
    pub environment: EnvironmentRef,
}
```

Exact Rust types may change after profiling. The semantic contract does not.

### 9.2 Environment lookup

For a view `⟨t, ρ⟩`:

```text
view(Parameter(p), ρ) = ρ[p] if bound, otherwise Parameter(p)
view(Self(s), ρ)      = specializeSelf(s, ρ)
view(atomic, ρ)       = atomic
```

Composite children are traversed lazily as views until a caller requires a materialized canonical form.

### 9.3 Materialization boundary

`TypeSubstitution::apply` or its successor remains available as an explicit materializer. Materialization is appropriate when:

- publishing a semantic product whose API requires a concrete canonical `TypeId`;
- exporting durable metadata;
- computing a stable structural fingerprint;
- runtime reflection explicitly requests the concrete form/child;
- a relation/normalization operation requires a canonical key;
- repeated reuse crosses a measured threshold where interning is cheaper than repeated view traversal.

It is not the default for every member lookup.

### 9.4 Lazy/eager equivalence law

For every publishable type `t` and environment `ρ`:

```text
materialize(view(t, ρ)) ≡ substitute(t, ρ)
```

This is a required differential/property test across all canonical type constructors.

### 9.5 Allocation discipline

Common operations after warmup should allocate nothing:

- declaration generic signature lookup;
- parameter lookup by index;
- kind lookup;
- member selector -> `CallableId` lookup;
- reading a callable parameter's unspecialized type;
- constructing a small specialization environment that fits inline/scratch storage;
- reading a specialized child through a `TypeView`;
- cached subtype/equivalence queries.

The implementation must not create runtime descriptor objects during compiler/checker/LSP semantic calculation.

## 10. Constraints

### 10.1 Canonical relation vocabulary

The initial generic constraint language contains exactly two semantic relations:

```text
Subtype(lower, upper)
Equivalent(left, right)
```

This is deliberately more general than “upper bound”.

Protocol/conformance-like requirements, once protocols are semantically available, use the subtype relation where protocol satisfaction participates in the type relation:

```phalcom
where T <: Serializable
```

The future protocol coherence specification decides *how* that relation is proven; generic syntax does not gain a separate ad hoc bound relation merely because the proof path can be nominal, protocol, or structural.

### 10.2 Constraint ownership

A generic signature owns its constraints in source order for diagnostics/provenance, while canonical semantic comparison may normalize relation operands and order where order is not semantically relevant.

Constraints may reference:

- parameters of that signature;
- enclosing declaration parameters visible in the callable scope;
- nominal/applied/tuple/record/callable forms;
- type lambdas/type applications;
- `Self` when valid for the declaration scope.

They may not reference solver-local inference variables in a published signature.

### 10.3 F-bounds

F-bounds are valid:

```phalcom
class Node<T> where T <: Comparable<T> { ... }
```

They require cycle-aware, budgeted relation evaluation. A recursive constraint is not rejected merely because it is recursive; nor is it accepted coinductively without the relation policy from Spec 01/05.

### 10.4 Partial application and deferred constraints

Given:

```text
C<A, B> where A <: F<B>
```

application `C<X>` may not be able to decide the constraint before `B` is supplied. The partial constructor remains valid with a residual/deferred constraint specialized by `A = X`.

A fully saturated application must surface `Rejected`, `Blocked`, `DynamicBoundary`, `Cancelled`, or `BudgetExceeded` honestly rather than producing a normal proper type and hiding the state.

### 10.5 Constraint normalization and fingerprints

Constraint structural fingerprints use semantic forms and stable owner/index binders, never source names or raw store IDs.

Alpha-renaming a method/declaration binder without changing owner-relative positions does not change constraint semantic structure.

## 11. Variance

### 11.1 Variance belongs to declaration parameters

```phalcom
class Producer<+T> { ... }
class Consumer<-T> { ... }
class Cell<T> { ... }
```

`+T` is covariant, `-T` contravariant, unmarked `T` invariant.

Kind and variance are orthogonal:

```text
F :: Type -> Type
```

does not imply whether `F` is covariant, contravariant, or invariant in its argument.

### 11.2 Applied nominal subtyping

For the same validated nominal origin `C` with parameter variance vector `v`:

```text
C<A1...An> <: C<B1...Bn>
```

iff every parameter relation succeeds according to its declared variance:

```text
Covariant(i):      Ai <: Bi
Contravariant(i):  Bi <: Ai
Invariant(i):      Ai ≡ Bi
```

Origins that differ use generic inheritance/supertype traversal before argument comparison.

Until a declaration's variance has been validated and published, relations must not assume the source annotation is sound. Migration may conservatively treat unvalidated applications invariant, but a declaration claiming `+`/`-` cannot publish successfully without validation.

### 11.3 Variance occurrence algebra

Use polarity composition:

| Context | Polarity |
|---|---|
| callable result | positive |
| callable parameter | negative |
| read-only field | positive |
| write-only field | negative |
| mutable read/write field | invariant |
| invariant constructor parameter | invariant |
| covariant nested parameter | preserve |
| contravariant nested parameter | flip |

Composition laws:

```text
+ ∘ + = +
+ ∘ - = -
- ∘ + = -
- ∘ - = +
0 ∘ x = 0
x ∘ 0 = 0
```

where `0` means invariant.

### 11.4 Diagnostic occurrence paths

A variance failure must identify the semantic occurrence path, not merely say “invalid variance”:

```text
declared +T
  -> field `consumer`
  -> callable parameter 0
  -> nested Consumer argument (-)
  -> T occurs positive/negative contrary to declaration
```

The occurrence path is compiler data and may later be presented by CLI/LSP/reflection diagnostics.

## 12. Generic inheritance

### 12.1 Superclass identity and supertype template are different facts

Runtime inheritance remains declaration identity:

```text
Names runtime superclass = Sequence runtime class
```

Static generic inheritance additionally records a template:

```phalcom
class Names<T> is Sequence<Option<T>> { ... }
```

Canonical semantic fact:

```text
GenericSupertypeTemplate(
    declaration = Names,
    super = Sequence<Option<Parameter(Names, 0)>>
)
```

The current `MapTypeHierarchy<DeclarationId, DeclarationId>` remains useful for runtime/nominal superclass identity but is insufficient as the sole static hierarchy representation.

### 12.2 Specialization law

For declaration environment `ρ = { T -> String }`:

```text
specialize(supertypeTemplate(Names), ρ)
≡ Sequence<Option<String>>
```

This specialization should normally be a lazy `TypeView`.

### 12.3 Subtype traversal

To test:

```text
Names<String> <: Sequence<Option<String>>
```

relation logic:

1. identifies origin `Names`;
2. reads its static supertype template;
3. constructs the receiver environment from supplied arguments;
4. views/specializes the supertype template;
5. continues the relation on the specialized supertype.

No specialized runtime class is created.

### 12.4 Inheritance cycles and invalid templates

Generic supertype templates must be kind-correct and proper where a superclass/supertype is required. Cycle policy is owned by Spec 01's bounded hierarchy/query architecture and later recursive-type gates. A generic template must never bypass runtime superclass-cycle rules.

## 13. `Self`

### 13.1 `Self` is owner-relative, not `value.class`

`Self` is a semantic type term anchored to a declaration and semantic role. It is not resolved by asking the runtime receiver for `.class`.

Recommended internal shape:

```rust
#[derive(Clone, Copy, Debug, Eq, Hash, PartialEq)]
pub enum SelfRole {
    /// Instance type denoted by the current declaration, including specialization.
    InstanceType,
    /// Type of the lexical/dynamic receiver value itself.
    ReceiverValue,
}

pub struct SelfTypeTerm {
    pub owner: DeclarationId,
    pub side: DispatchSide,
    pub role: SelfRole,
}
```

### 13.2 Source `Self`

The source type spelling `Self` denotes `InstanceType` for the owning declaration. Therefore class-side factories may return the dynamic/owner-relative instance type without pretending that the class object itself is an instance.

The compiler's implicit `self` binding is separate:

- instance side `self` uses `ReceiverValue` and specializes to the instance receiver type;
- class side `self` uses `ReceiverValue` and specializes to the class-object receiver type.

This removes the common ambiguity between “the type produced by this class” and “the type of the class object receiving this class-side message”.

### 13.3 Generic specialization

Inside `class Box<T>` instance-side context with receiver `Box<Int>`:

```text
Self[InstanceType]  ↦ Box<Int>
T                   ↦ Int
```

An inherited member keeps its defining `Self` anchor but specializes to the actual static receiver according to the relation/member-lookup environment. This permits fluent inherited APIs without replacing `Self` with the defining base class too early.

### 13.4 No ambient class-side applied context

A class-side call to origin `Box` does not magically bind `T`. The class-side generic rule in §5.3 still applies. `Self` does not provide a hidden channel for declaration type arguments.

## 14. Canonical callable and field declaration model

### 14.1 One callable identity, one declared signature

Replace the current duplicated surface representation with an identity-indexed canonical table:

```rust
pub struct CallableSemanticSignature {
    pub callable: CallableId,
    pub owner: DeclarationId,
    pub side: DispatchSide,
    pub selector: Selector,
    pub generics: Option<GenericSignature>,
    pub parameters: Box<[CallableParameterSemantic]>,
    pub return_type: TypeTerm,
    pub source: Option<SourceOrigin>,
}

pub struct CallableParameterSemantic {
    pub index: u32,
    pub local_name: Box<str>,
    pub external_label: Option<Box<str>>,
    pub rest: RestMode,
    pub ty: TypeTerm,
    pub source: Option<SourceOrigin>,
}

pub struct CallableSignatureTable {
    // dense/secondary map in implementation, conceptual mapping here
    pub by_id: /* CallableId -> CallableSemanticSignature */,
}
```

`CallableId` is the stable semantic identity. Selector/side are lookup keys, not alternate signature identities.

Effects, exits, contracts, termination, proof summaries, documentation, and inference provenance attach to `CallableId` through separate tables/query products. Do not bloat the core signature merely to anticipate every future analysis axis.

### 14.2 Member surfaces map selectors to IDs

Target conceptual surface:

```rust
pub struct MemberSurface {
    pub fields_by_name: /* Name -> FieldId */,
    pub callables_by_selector: /* Selector -> CallableId */,
}
```

Field/callable type data live in canonical identity tables. This removes current duplication where `MemberSurface` stores both `CallableId -> return TypeKnowledge` and `Selector -> CallableSignature`.

### 14.3 Specialized lookup returns a view

For `Box<Int>` member lookup:

```rust
pub struct SpecializedMemberView {
    pub callable: CallableId,
    pub environment: EnvironmentRef,
}
```

Reading parameter or return types yields `TypeView`s specialized under the environment. The dispatch resolver does not clone and recursively substitute a complete signature unless a caller explicitly asks to materialize it.

### 14.4 Fields have one semantic identity table

Recommended:

```rust
pub struct FieldSemanticSignature {
    pub field: FieldId,
    pub owner: DeclarationId,
    pub side: DispatchSide,
    pub name: Box<str>,
    pub mutability: FieldMutability,
    pub ty: TypeTerm,
    pub source: Option<SourceOrigin>,
}
```

Variance validation, reflection, generated accessors, hover, and field initialization checking consume the same field record.

### 14.5 Runtime `MethodObject` remains compact

Do not copy `CallableSemanticSignature` into every `MethodObject`.

When runtime typing metadata is retained, Spec 02/03 should provide a VM-owned mapping equivalent to:

```text
Method ObjRef / method runtime identity -> StableCallableRef / CallableId-equivalent metadata key
```

Lookup should be O(1) or near-O(1) and avoid repeated selector/name reconstruction. The map is absent when typing reflection metadata is disabled.

## 15. Generic method inference

### 15.1 Scope

Phalcom adopts local/bidirectional generic method inference, not global principal-type inference.

Given:

```phalcom
identity<T>(value: T) -> T
```

and:

```phalcom
const x: String = identity("x")
```

argument and expected-result information may constrain the fresh instantiation of `T`.

### 15.2 Instantiation algorithm

For each generic call candidate:

1. allocate one fresh solver-local `InferVarId` per callable generic parameter;
2. instantiate callable parameter/return terms as lazy views over that inference environment;
3. collect argument-to-parameter constraints;
4. collect receiver/specialization constraints;
5. if an expected result type is available, collect result-to-expected constraints;
6. solve equality/lower/upper relationships deterministically;
7. run occurs checks before binding a variable to a term containing itself;
8. zonk solved variables;
9. validate the callable's canonical `where` constraints under the solution;
10. classify unsolved variables explicitly;
11. materialize only the final result/diagnostic forms that require canonical IDs.

### 15.3 Solver state

A generic solver variable tracks evidence, not just one eager substitution:

```rust
pub struct InferVarState {
    pub equal: Option<TypeTerm>,
    pub lowers: SmallVec<[TypeTerm; 2]>,
    pub uppers: SmallVec<[TypeTerm; 2]>,
    pub provenance: SmallVec<[InferenceCause; 2]>,
}
```

Exact data structures are profiling decisions. The semantic requirement is to preserve enough lower/upper/equality information to distinguish a valid principal local solution from an arbitrary first binding.

### 15.4 Terminal outcomes

```rust
pub enum GenericInferenceOutcome {
    Solved(GenericSolution),
    Ambiguous(AmbiguityReport),
    Underconstrained(UnderconstrainedReport),
    Conflicting(ConstraintConflict),
    DynamicBoundary(DynamicBoundary),
    Blocked(BlockReason),
    Cancelled,
    BudgetExceeded(BudgetReport),
    InternalFailure(IncidentId),
}
```

No unsolved inference variable may escape by silently becoming `Dynamic`, `Any`, `Object`, `Never`, or the first encountered bound.

### 15.5 Determinism

Constraint insertion order may affect diagnostic provenance ordering but cannot affect a successful canonical solution. Worklists use deterministic stable ordering for equal-priority facts.

### 15.6 Budgets and cancellation

Generic inference is query-local. It receives Spec 01 relation/query budgets and cancellation tokens. Cancellation or budget exhaustion never publishes a solved signature/result produced after the terminal condition.

## 16. Declaration lowering and publication staging

### 16.1 Required phase order

Compiler semantic construction becomes:

```text
parse / source product
  -> declaration shells
  -> allocate declaration generic binders
  -> lower declaration GenericSignature + where constraints
  -> lower generic supertype template
  -> allocate callable/field identities
  -> allocate callable generic binders
  -> lower canonical field/callable signatures
  -> validate kinds/proper positions
  -> validate variance
  -> validate class-side no-unbound-declaration-param rule
  -> publish declaration interface
  -> check bodies against published signature IDs/views
```

This staging is compatible with Spec 01's semantic SCC/interface publication model.

### 16.2 Do not re-resolve declarations in body checking

Body checking receives `CallableId`/`FieldId` and canonical signature tables. It must not reparse or independently re-resolve the same annotation merely to reconstruct expected parameter/return types.

The current repeated annotation lowering in `checker/declaration.rs` is a migration target.

### 16.3 Publishability

Before a declaration interface becomes authoritative, validate:

- every value-typing slot is proper kind `Type`;
- every constructor slot has the expected kind;
- no `InferVarId`, query-local `TypeView`, transient environment handle, or scoped lambda-bound node escapes;
- all generic parameter references are owned/visible in the scope;
- no class-side signature contains an unbound declaration generic parameter;
- all required constraints are structurally valid;
- variance is validated;
- superclass/supertype templates are kind-correct;
- source/native/generated declarations obey the same canonical rules;
- IDs belong to the correct store/generation.

### 16.4 Interface fingerprints

Public/interface fingerprints include semantically relevant:

- declaration kind;
- generic parameter count/order/kinds/variance;
- canonical constraints;
- generic supertype template;
- field signatures and mutability;
- callable selector/side/generic signature/parameter labels-rest-types/return type;
- later effect/contract axes when their owning specs require them.

Source binder names may affect source/navigation fingerprints, but canonical semantic fingerprints must not depend on alpha-equivalent lambda binder names or raw `TypeId` allocation order.

## 17. Generated declarations and attributes

### 17.1 Semantic preservation invariant

> **Any compiler transformation that can derive a generated declaration's type exactly must preserve or synthesize that canonical semantic signature. It may not downgrade known information to unannotated/unknown merely because the declaration was generated.**

This applies to:

- `@get`;
- `@set`;
- `@construct`;
- `@data`;
- `with` helpers;
- sealed variants and variant constructors;
- generated visitor methods;
- future user attributes/macros that declare members through authorized compiler APIs.

### 17.2 Current accessor gap

The current attribute expansion path creates generated getters with `return_annotation: None` and setters whose generated parameter annotation can be absent (`phalcom-core/src/compiler/attributes.rs`, accessor derivation around source lines 1166–1203). That is acceptable only as a transitional AST implementation; semantic lowering must carry the source field's exact type into the generated callable signature.

Example:


must publish a getter semantically equivalent to:

```text
name -> String
```

### 17.3 Variants

Runtime/public result types in later reflection APIs may use native sealed variant classes. The current source `VariantDef` payload representation is not yet a complete generic typed ADT syntax. Do not block canonical result APIs on that parser feature.

Generated/native variant declarations may initially attach canonical semantic payload/callable signatures directly through compiler/native metadata construction, provided they produce the same signature tables as source declarations would.

## 18. Type-form expressions and runtime values

### 18.1 One language, explicit semantic boundary

Phalcom permits type forms to become values for reflection, but their semantic normalization is compiler-authoritative.

Distinguish:

```phalcom
const xs: List<Int> = ...        // annotation only; no runtime type object needed

const listType = List<Int>       // explicit type-form value; reify on value boundary

const ResultOf = <T> =>> Result<T, Error>
                                    // first-class type-lambda form; reify if value survives
```

### 18.2 Type application is not overridable runtime `<>` dispatch

The source conceptual lowering `List.<>(Int)` describes a uniform semantic operation. The compiler does not perform an ordinary user-overridable message send to decide what `List<Int>` means in a type-form context.

This preserves determinism, purity of semantic analysis, and the separation between runtime message dispatch and static type calculation.

### 18.3 Lazy reification

If a type-form expression remains compile-time-only, allocate no runtime descriptor.

If it escapes into runtime value space:

- nominal form -> reuse existing class object;
- atomic kind -> reuse singleton kind descriptor;
- synthetic application/union/tuple/record/callable/lambda -> request one root descriptor from runtime typing registry;
- child descriptors remain lazy until inspected;
- weak canonicalization may reuse a live descriptor without retaining it forever.

## 19. Runtime erasure and typed dispatch boundary

### 19.1 Erasure law

A live ordinary value proves its runtime class, not an erased applied generic type.

For a value whose runtime class is `List`:

```text
runtime can prove cheaply:     value.class == List
runtime cannot infer safely:   value : List<Int>
```

No per-instance generic token is introduced.

### 19.2 Static type-directed dispatch

A compiler feature such as future `@typecase`/typed multimethod selection may consume canonical `TypeId`, `CallableId`, parameter signature IDs, and relation queries directly. It does not need runtime descriptor objects.

### 19.3 User-defined runtime typed dispatch

Runtime reflective typed dispatch uses explicit metadata/context APIs such as:

```text
TypingContext.signatureOf(method)
TypingContext.matches(value, against: typeForm)
TypingContext.validate(value, as: typeForm)
```

Exact API naming belongs to Spec 03.

Nominal checks can use existing runtime class inheritance. Applied/deep structural generic checks may return a dynamic/erasure boundary or require explicit deep validation with size/cycle budgets.

### 19.4 No ambient applied receiver context

Reject:

- `Type.currentApplication`;
- hidden call-frame generic arguments;
- applied descriptor forwarding to origin class-side methods;
- generic type arguments in selector/cache identity.

## 20. Reflection requirements imposed on later specs

Spec 03 owns exact runtime class names/capabilities. This specification requires that the semantic information below be reflectable when retained and authorized.

### 20.1 Type-form common surface

The ratified reflection vocabulary that later specs must preserve is:

```text
type.kind
type.equivalentTo(other)
type.subtypeOf(other)
type.display
type.freeParameters
type.remainingParameters
```

`equivalentTo` expresses semantic type equivalence; `subtypeOf` invokes the bounded semantic subtype relation and therefore may project a result-rich relation outcome rather than a bare success-biased boolean. `display` is presentation and does not participate in identity. These selectors are semantic reflection operations; they do not invoke user-overridable type normalization.

`freeParameters` and `remainingParameters` are distinct:

- **freeParameters** — all free stable binders referenced by a form;
- **remainingParameters** — unsatisfied application slots of a partially applied constructor.

### 20.2 Applied form

```text
.origin
.arguments
.remainingParameters
.kind
```

### 20.3 Type parameter

```text
.owner
.index
.name
.kind
.variance
.constraints          // derived from owning GenericSignature
```

`upperBounds` may be a derived convenience view over `Subtype(parameter, upper)` constraints; it is not canonical storage.

### 20.4 Type lambda

```text
.kind
.parameters
.body
.freeParameters
.<>(...)               // semantic application
```

Lambda parameter names are provenance; equivalence remains alpha-insensitive.

Reflected kinds use the corresponding ratified vocabulary:

```text
kind.arguments
kind.result
```

Atomic `Type` has no arguments and no result; arrow kinds expose their canonical argument kinds and result kind.

### 20.5 Callable declaration

Reflection must be able to inspect:

- callable identity;
- owner and side;
- selector;
- generic parameters and constraints;
- parameter count;
- each parameter's index/local name/external label/rest mode/type;
- return type;
- source/documentation when retained;
- later effects/contracts/termination by separate attached products.

This is required for typed dispatch libraries and semantic tooling.

### 20.6 Lazy collection APIs

Reflection must not require eagerly allocating a tuple and descriptors for every parameter/argument/member merely to inspect one element.

Provide low-level indexed/count access equivalent to:

```text
parameterCount
parameterAt(index)
parameterTypeAt(index)
argumentCount
argumentAt(index)
constraintCount
constraintAt(index)
```

Ergonomic collection properties may return lightweight views or lazily materialized collections.

## 21. Runtime result variants

### 21.1 Compiler-internal results

Internal semantic computation uses Rust enums/compact query records. It must not allocate VM objects merely to represent compiler states.

### 21.2 Runtime reflection projection uses sealed variants

When exposed to Phalcom code, result domains should use native sealed variant classes rather than status symbols plus incompatible optional payload fields.

Required semantic shape:

```text
TypingResult
  Known(value)
  Unknown(reason)
  Invalid(diagnostics)
  Unavailable(reason)
  Cancelled
  BudgetExceeded(report)
  InternalFailure(id)

TypeRelationResult
  Satisfied(evidence)
  Rejected(failure)
  DynamicBoundary(boundary)
  Blocked(reason)
  Cancelled
  BudgetExceeded(report)
  InternalFailure(id)
```

No-payload variants may be singleton instances to avoid repeated allocation.

### 21.3 Terminal-state honesty

Keep distinct:

- `Unknown`/`Blocked`: insufficient semantic information/dependency;
- `Rejected`/`Invalid`: contradiction or invalid operation;
- `DynamicBoundary`: explicitly open runtime boundary;
- `Cancelled`: caller stopped work;
- `BudgetExceeded`: operation intentionally bounded;
- `InternalFailure`: implementation incident.

Cancellation and budget exhaustion are never encoded as `Blocked` and never serialized as a completed semantic fact.

## 23. Compiler, CLI, REPL, and LSP ecosystem

### 23.1 Compiler

The compiler consumes the `SemanticDb` declaration/callable signature tables directly. Code generation remains runtime-shape-driven; typing may prove optimizations only when their guards/fallbacks preserve semantics, but generic type metadata does not change selector or layout identity.

### 23.2 `phalcom check`

CLI checking consumes the same formal snapshot/query results as compilation. It does not deserialize runtime metadata to check source and does not own a second generic solver.

Generic diagnostics printed by CLI therefore use the same IDs, constraints, inference outcomes, and occurrence paths that LSP receives.

### 23.3 LSP

Formal semantic features include:

- hover: generic parameters, kinds, variance, `where` constraints, specialized return/member types;
- completion: members specialized under receiver environment without eager signature cloning;
- signature help: callable method generics plus inferred type arguments and unresolved constraints;
- go-to-definition: stable type parameter owner/source;
- inlay hints: optionally inferred method generic arguments;
- diagnostics: variance paths, constraint failures, inference ambiguity, kind mismatch, unsaturated type constructor;
- semantic explanation: substitution/inference provenance when requested.

The existing advisory LSP callable/value summaries remain advisory and cannot produce rejecting formal facts on their own.

### 23.4 REPL

The final REPL owns a persistent semantic session, not a fresh unrelated inline analyzer per cell:

```text
REPL session project
  cell/module 1
  cell/module 2 -> depends on 1
  cell/module 3 -> depends on 1,2
```

Edits invalidate dependent semantic queries. Old runtime `TypingContext`s may remain pinned to the metadata generation from which they were produced; a new cell publishes a new snapshot/generation.

No REPL call frame contains an ambient `current generic application`.

## 24. Metadata and runtime-registry amendments

### 24.1 Spec 02 is downstream of this calculus

Before metadata schema v1 freezes, it must encode at least:

- type-lambda nodes with alpha-normalized semantics;
- generic parameter kind/variance/provenance references;
- signature-owned generic constraints;
- generic supertype templates;
- owner/index parameter references;
- canonical callable signatures;
- canonical field signatures;
- `Self` terms/roles as needed by callable/member signatures;
- stable structural fingerprints independent of raw IDs.

Metadata export consumes already-solved, publishable semantic products. It does not run generic inference or discover constraints.

### 24.2 No broad per-descriptor `Arc<RwLock<RuntimeTypeArena>>` requirement

Amend Spec 02's initial implementation sketch. Prefer:

```text
VM
  RuntimeTypingRegistry
    immutable validated LoadedTypeMetadata
    bounded dynamic/synthetic overlay
    weak descriptor cache
    world-sensitive query cache
```

Descriptors should carry compact registry/node handles where possible. Common metadata reads should be immutable and lock-free/read-only. Synchronization is confined to overlay mutation/cache insertion, not every descriptor property read.

A safe `RwLock` implementation may be used as a migration baseline if necessary, but it is not the desired permanent ABI/data-shape contract and must not be embedded so deeply that lock-free immutable reads become incompatible.

### 24.3 Weak descriptor cache must tolerate stale handles

The weak-cache algorithm must use a non-panicking generational lookup equivalent to `heap.try_get(obj_ref)`. A stale weak `ObjRef` is an expected cache miss, not an internal invariant that permits `heap.get` to panic.

### 24.4 Runtime `Value` representation remains unchanged

Do not add a `Value` tag/immediate encoding for `TypeId`, `KindId`, or type-lambda IDs merely to save occasional reflection allocation. `Value` is a hot runtime representation; rare explicit reflection must not tax every runtime value.

## 25. TypeStore lifecycle and canonical identity

### 25.1 Dense IDs remain preferred

Retain compact store-local IDs for hot semantic operations. `TypeId == TypeId` and `KindId == KindId` are O(1) within a validated store context.

### 25.2 Store-qualified boundaries

At subsystem/query/snapshot boundaries, raw IDs must be associated with a store/generation identity as Spec 01 requires. Accidentally comparing `TypeId(42)` from two stores is invalid even if both numbers are 42.

### 25.3 Long-lived editor stores

The target is compatible with segmented immutable epochs:

```text
TypeStore epoch E
  frozen segment 0
  frozen segment 1
  current append segment

compaction/high-water event
  -> create epoch E+1
  -> new snapshots use E+1
  -> old snapshots retain E while alive
```

This avoids requiring one globally locked, forever-growing mutable interner.

The exact compaction threshold is performance-gated. Structural fingerprints, not numeric IDs, define cross-epoch semantic equivalence.

## 26. Aliases and record-row hooks

### 26.1 Transparent aliases

If transparent aliases remain part of Spec 04, they have stable declaration identity for:

- navigation;
- source diagnostics;
- invalidation;
- metadata provenance.

Semantic equivalence expands them through a bounded cycle-aware alias query. They do not create a runtime class or distinct allocation identity.

Generic alias binders/constraints use the same `GenericSignature` model.

### 26.2 Record rows

`RecordRow` remains a distinct semantic kind/domain if the ratified row feature lands. Row parameters must not be represented as ordinary proper `Type` parameters or fake sentinel fields.

This specification requires generic environments/substitution infrastructure to be extensible to typed row-domain bindings, while full row unification/subtyping remains owned by Spec 05.

Do not generalize “row” into one untyped variable namespace shared by records, variants, and effects.

## 28. Performance and memory requirements

Performance is a semantic architecture requirement because a theoretically clean generic model that allocates on every editor/member query would undermine Phalcom's intended use.

### 28.1 Zero-cost ordinary runtime

Programs that do not explicitly request typing reflection pay no per-object runtime cost for:

- generic argument tokens;
- synthetic type descriptor objects;
- specialized runtime classes/metaclasses;
- generic selector keys;
- per-instance type metadata;
- hidden generic call-frame context.

### 28.2 Semantic hot-path targets

After warmup, the following should be zero-allocation or amortized-zero-allocation under ordinary small cases:

- `kindOf(TypeId)`;
- declaration -> `GenericSignature` lookup;
- `TypeParameterId` -> parameter data lookup;
- selector -> `CallableId` lookup;
- `CallableId` -> signature lookup;
- building a small receiver specialization environment;
- reading specialized parameter/return views;
- cached relation lookup;
- repeated LSP hover over unchanged declaration.

### 28.3 Avoid eager subtree reconstruction

A receiver like:

```text
Repository<User, Map<String, Option<Result<Int, Error>>>>
```

must not cause every member signature to be recursively substituted and interned merely because completion asks for the member names.

Specialize only the type slots actually inspected.

### 28.4 Required benchmarks

Add benchmarks/metrics for:

1. repeated generic member lookup on a saturated receiver;
2. repeated lookup on partially applied higher-kinded forms;
3. nested generic application normalization;
4. alpha-equivalent type-lambda interning;
5. beta reduction with deep body;
6. partial type-lambda application;
7. generic method inference with argument-only evidence;
8. inference with expected-result evidence;
9. inherited generic member lookup through several supertype templates;
10. warm LSP hover/completion/signature-help loops;
11. cold versus incremental generic interface rebuild;
12. edit/revert TypeStore high-water behavior;
13. runtime reflection root-only descriptor allocation;
14. child-by-index reflection allocation;
15. weak descriptor reclamation.

Measurements record allocations, canonical nodes created, environment/view creations, relation-cache hits, elapsed CPU, and high-water memory. Absolute thresholds are set from Phalcom corpus data, not copied from another compiler.

### 28.5 Performance deletion criterion

The generic implementation is not complete if the main member-lookup/checking path still calls eager recursive `TypeSubstitution::apply` for every lookup when an equivalent lazy view is available.

## 29. Mathematical and property laws

These are normative tests, not explanatory examples.

### 29.1 Kind uniqueness

```text
kind(t) = k1 ∧ kind(t) = k2  => k1 = k2
```

### 29.2 Application flattening

```text
apply(apply(F, A), B) ≡ apply(F, A ++ B)
```

when both sides are well-kinded.

### 29.3 Residual kind

If:

```text
F :: K1 -> ... -> Kn -> R
```

then applying the first `m` well-kinded arguments yields exactly:

```text
K(m+1) -> ... -> Kn -> R
```

### 29.4 Alpha equivalence

```text
<T> =>> B[T] ≡ <U> =>> B[U]
```

for capture-avoiding renaming.

### 29.5 Beta reduction

```text
(<T> =>> B[T])<A> ≡ B[A/T]
```

### 29.6 Substitution identity

```text
subst(t, {}) ≡ t
```

### 29.7 Substitution composition

For compatible environments:

```text
subst(subst(t, ρ1), ρ2) ≡ subst(t, ρ2 ∘ ρ1)
```

with capture avoidance.

### 29.8 Lazy/materialized equivalence

```text
materialize(view(t, ρ)) ≡ subst(t, ρ)
```

### 29.9 Stable binder identity

Two declaration/callable parameters are identical iff owner and index identify the same stable binder in the same semantic owner/store context. Equal source names do not imply identity.

### 29.10 Constraint alpha-invariance

Renaming source binder display names without changing owner-relative structure does not change canonical constraint truth or structural fingerprint.

### 29.11 Variance soundness

For validated declaration `C`:

```text
+ parameter: A <: B => C<A> <: C<B>
- parameter: A <: B => C<B> <: C<A>
invariant:   C<A> <: C<B> only through A ≡ B (for same-origin argument comparison)
```

### 29.12 Generic inheritance specialization

```text
super(D<args>) ≡ specialize(superTemplate(D), params(D) := args)
```

### 29.13 `Self` specialization

Member lookup under static receiver `R` must yield the same result whether `Self` is specialized lazily in a view or materialized through explicit substitution.

### 29.14 Runtime invariance

Adding/changing legal static generic metadata cannot alter selector identity, runtime class/metaclass relationships, instance layout, or allocation shape.

### 29.15 Publishability

No published interface, snapshot export, metadata DAG, or runtime reflection descriptor root contains solver-local inference IDs, scoped lambda-bound nodes outside their lambda, transient view handles, or foreign-store IDs.

### 29.16 Cross-consumer formal agreement

For the same semantic snapshot/generation:

```text
compiler formal answer
== phalcom check formal answer
== REPL formal answer
== LSP formal static answer
```

Presentation may differ; semantics may not.

### 29.17 Clean/incremental equivalence

After any edit sequence reaching source state `S`:

```text
freshAnalysis(S) ≡ incrementalAnalysis(S)
```

for canonical public semantic products and diagnostics, independent of internal numeric ID allocation.

### 29.18 Metadata determinism

Semantically equivalent fresh stores export byte/structurally identical canonical metadata independent of `TypeId` allocation order, subject to the exact encoding policy in Spec 02.

7. replace status-symbol result objects with sealed variant-class projections where public runtime API is implemented;
8. `Cancelled` and `BudgetExceeded` are distinct from `Blocked`;
9. runtime applied generic matching acknowledges erasure and may require explicit deep validation.

### 33.4 Spec 04 — User-Facing Type Syntax and Lowering

Supersede:

- `F :: Type -> Type` binder annotation -> `F: Type -> Type`;
- inline `parameter-bound` -> removed;
- all constraints -> `where`;
- add `==` semantic equivalence constraint;
- allow lower bound by operand order (`Number <: T`);
- `T in (Int, Float)` -> deferred/not in initial core;
- add type-lambda syntax `<T> =>> ...`;
- add explicit type-form value-expression integration so type forms can be reflected without pretending annotations are runtime expressions;
- no `F<_>` placeholder syntax.

Existing core annotation syntax, record-row decisions, alias spelling, parser recovery responsibilities, and formatting responsibilities remain Spec 04-owned unless separately changed.

### 33.5 Spec 05 — Advanced Kinds, Constraints, Effects, and Proofs

Move basic generic ownership into 01.5:

- declaration/callable generic signatures;
- variance base semantics;
- subtype/equivalence generic constraints;
- ordinary F-bounds;
- generic inheritance;
- `Self` base semantics;
- type-lambda calculus;
- generic method inference contract.

Amend its target `TypeParameterData` by removing canonical `bounds` and `default` fields. Spec 05 retains:

- prenex kind polymorphism/kind variables beyond the base explicit kind calculus;
- advanced row solving;
- effects/exits/termination;
- contracts and proofs;
- solver/prover trust/artifacts;
- any future richer constraint categories after ratification.

### 33.6 Spec 07 — implementation plan

Replace old generic Phase D cards with or map them onto workstreams G1–G14 in §31. In particular:

- do not implement finite exact-set constraints;
- implement type lambdas before metadata schema freeze;
- implement lazy specialization before optimizing generic member lookup;
- create canonical callable/member identity tables before reflection depends on them;
- preserve generated member types;
- make compiler/LSP/CLI/REPL convergence an explicit generic acceptance gate.

## 35. Intentional deferrals and gates

Effects, exits, contracts, and proof semantics remain owned by Spec 05. In particular, the ratified `@total` meaning is **termination proven only**: it does not imply purity, absence of effects, absence of exceptions, or absence of allocation. Generic signatures must leave attachment points for those independent semantic axes without folding them into types or constraints.

The architecture must leave room for, but does not define or enable:

- public kind-parameter/kind-polymorphism syntax;
- higher-rank type/kind quantification;
- dependent types or dependent kinds;
- `Type :: Type` or universe hierarchy;
- `Any` admission/semantics;
- intersections and overload-set coherence;
- associated types/type members;
- negative constraints;
- finite exact-set `in (...)` constraints;
- generic parameter defaults;
- use-site variance;
- constrained anonymous type-lambda `where` clauses;
- recursive aliases/ADTs without guardedness policy;
- protocol declaration/coherence details;
- effect polymorphism/handlers;
- proof backend/kernel details;
- per-instance reified generic tokens;
- runtime specialized generic classes/metaclasses;
- type-directed selector identity.

A later feature may add a new canonical form/constraint domain, but it must preserve the laws and ownership boundaries here.

## 36. Acceptance gates

### Gate 01.5-G — ecosystem convergence

### Gate 01.5-H — metadata/reflection readiness

Pass when the complete publishable semantic graph required by Spec 02/03 can be exported without inventing missing generic semantics, and runtime reflection can remain lazy/erased without changing the object model.

## 37. Final normative summary

1. Phalcom keeps the completed separation between runtime class identity, static value typing, and kinding.
2. Generic metadata never participates in selector identity, runtime dispatch, layout, allocation, or instance runtime class.
3. `Type` and arrow kinds classify proper types and constructors; arrow kind carries no variance information.
4. Declaration and method generics use stable owner-plus-index parameter identity; names are provenance.
5. Source generic kind annotation is `F: Type -> Type`; `::` remains the kinding judgment notation.
6. All generic bounds/constraints use `where`; no inline parameter bound syntax is part of the language.
7. Initial canonical generic constraints are subtype and semantic equivalence; lower bounds are represented by operand order; finite exact-set constraints are deferred.
8. Variance is `+T`/`-T`/invariant and exists only on declaration/nominal parameters.
9. `F<_>` placeholder higher-kinded syntax is rejected; explicit kinds and type lambdas cover the use cases.
10. Type lambdas use `<T> =>> ...`, are first-class semantic type forms, are alpha-equivalent by binder position, and beta-normalize under application.
11. Lambda-bound variables are a scoped domain distinct from declaration `TypeParameterId`s and solver `InferVarId`s.
12. Generic application supports partial application and satisfies application-spine flattening/residual-kind laws.
13. High-level application validates signature constraints; low-level interning does not own declaration semantics.
14. Substitution is the semantics; lazy environments/views are the default specialization representation for hot paths.
15. Eager substitution remains an explicit materialization operation, not the ordinary member-lookup strategy.
16. Applied nominal subtyping uses validated declaration variance, not hard-coded argument equality.
17. Generic inheritance stores a static supertype template in addition to unchanged runtime superclass identity.
18. `Self` is owner-relative and specializes from the static semantic receiver/environment, never by reading runtime `.class`.
19. Class-side members do not receive ambient declaration generic bindings; factories use explicit method generics or closed result types.
20. Every callable and field has one stable semantic identity and one canonical declared signature; member surfaces index those identities.
21. Generic method inference is local/bidirectional, query-local, bounded, deterministic, and may not leak solver variables.
22. Generated declarations preserve every exactly derivable type instead of downgrading to unknown.
23. Source, native, and generated declarations lower to the same semantic algebra.
24. Type-form expressions may become runtime values, but semantic type application/lambda reduction is compiler-authoritative and not overridable user dispatch.
25. Runtime instances carry no generic token. Applied generic runtime validation is explicit and may encounter an erasure/dynamic boundary.
26. Reflection must expose generic declarations/type lambdas/signatures lazily and distinguish `freeParameters` from `remainingParameters`.
27. Runtime reflection result APIs use sealed variants with cancellation and budget exhaustion distinct from semantic blockage.
28. Durable metadata is downstream: it serializes already-solved publishable forms and must include type lambdas, constraints, supertype templates, and canonical member signatures before schema freeze.
29. Runtime type registries favor immutable reads, compact handles, narrow synchronized overlays, weak descriptor caching, and safe stale-handle lookup.
30. Compiler, CLI, REPL, and LSP formal typing are one ecosystem over one compiler-owned semantic snapshot.
31. Performance acceptance requires zero ordinary-runtime generic overhead and avoidance of eager semantic allocations on repeated generic queries.
32. Every implementation must satisfy the property laws, publishability rules, differential clean/incremental tests, and cross-consumer agreement specified here.
