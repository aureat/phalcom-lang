
Part 05.1 establishes the language and semantic truth of elimination. Part 05.2 is forbidden from rediscovering that truth from source names, runtime classes, or family lookup.

The central language rule is:

> Every accepted Phalcom `match` expression is statically proven total.

A `match` has no ordinary runtime fallthrough and no user-level `MatchError`. The semantic analyzer proves that every reachable value in the scrutinee domain is covered. Closed ADTs and GADTs are analyzed through exact constructor space. Union types, including unions written through transparent type aliases, participate directly in coverage. Open or otherwise unprovable domains require an irrefutable `_` arm unless supported structural reasoning proves the domain empty.

Pattern syntax reuses Phalcom's selector/family model rather than inventing a second variant naming system:

```phalcom
Animal::Dog                  // exact singleton/getter variant
Animal::Dog()                // exact nullary constructor variant
Animal::Dog(x)               // exact callable selector
Animal::Dog(_, named: age)   // exact labeled callable selector
Animal::Dog(...)             // callable selector-pattern over Dog family
Animal::Dog(x, ..., named: y)// partial callable selector-pattern
Animal::Dog*                 // whole Dog variant family
```

The same forms may use contextual owner shorthand when the expected pattern domain determines a unique owner:

```phalcom
match animal {
    Dog(name) => ...
    Cat* => ...
}
```

`_` is a first-class recursive wildcard pattern. It matches every value admitted at its pattern position and binds nothing. It is not special-cased only as a final fallback:

```phalcom
Result::Error(_, reason: _)
Some(Ok(_))
_ => fallback()
```

Or-patterns are supported:

```phalcom
Result::Ok(x) | Result::Cached(x) => use(x)
```

Every alternative must introduce the same binding names. The type of a shared binding is the semantic join of the alternative-specific binding types. Only proof facts established by every successful alternative survive into the common branch environment.

GADT elimination is proof-producing. A successful exact case observation establishes an `ExactCase` fact and introduces the variant declaration's `CaseTypeEnvironment` into the branch after compatibility with the scrutinee specialization is solved. GADT reachability must not be implemented as ordinary subtype filtering: a generic `Expr<T>` can match `Expr::Int` because that match establishes `T = Int`; a known `Expr<Int>` cannot match a `Bool -> Expr<Bool>` case because the equalities contradict.

Part 05.1 ends by publishing stable semantic match products. These products contain exact `VariantId` candidates, candidate-specific payload field identities, branch bindings, branch proof environments, coverage/reachability results, exhaustiveness status, witnesses, and match result knowledge. Part 05.2 consumes these products and must not re-resolve variant names or selector patterns.

# 5. Match Is an Expression

The canonical surface is:

```phalcom
match scrutinee {
    pattern => expression
    pattern => {
        statements
        expression
    }
}
```

Example:

```phalcom
const value = match result {
    Result::Ok(x) => x
    Result::Error(_, reason: message) => {
        log(message)
        fallback()
    }
}
```

Normative rules:

1. `match` is an expression, not a statement-only construct.
2. the scrutinee is an expression;
3. each arm has one pattern and one branch expression;
4. a braced body is an ordinary block expression and contributes its block result;
5. arm order is source order;
6. every accepted `match` is statically total;
7. guards are not part of Part 05.1;
8. match is elimination/control flow, never ordinary message dispatch.

A match used where its result is discarded remains an expression whose value is ignored.

# 6. Tokens and Lexical Grammar

Part 05.1 adds:

```rust
Token::Match
Token::FatArrow // =>
```

The lexer must recognize:

```text
match    keyword
=>       FatArrow
=>>      TypeLambdaArrow
```

Longest-match ordering is required around `=`:

```text
=>> before => before =

```

`Token::Underscore` already exists and becomes the wildcard token in pattern context.

`*` and `...` remain existing tokens. Their interpretation as whole-family and selector-gap pattern syntax is parser-contextual; no match-specific lexer token is required.

# 8. Pattern AST Upgrade

The pattern tree remains shared across destructuring/refutable consumers, but its variant syntax must stop being a string-only constructor node.

The recommended public AST is:

```rust
pub enum Pattern {
    Wildcard { range: SourceRange },
    Name { name: String, range: SourceRange },
    Tuple { elements: Vec<Pattern>, range: SourceRange },
    List { elements: Vec<Pattern>, rest: Option<Box<Pattern>>, range: SourceRange },
    Variant(VariantPattern),
    Or { alternatives: Vec<Pattern>, range: SourceRange },
    Record { entries: Vec<RecordPatternEntry>, range: SourceRange },
    Map { entries: Vec<MapPatternEntry>, range: SourceRange },
}
```

Conceptual variant syntax:

```rust
pub struct VariantPattern {

```

Exact field names may follow repository conventions, but the information content is mandatory.

# 9. Wildcard Pattern

`_` is a first-class recursive wildcard:

```phalcom
_
```

Semantics:

```text
matches every value in the expected subspace
binds no name
adds no equality relation between repeated positions
requires no payload projection when the entire corresponding payload is ignored
```

Examples:

```phalcom
match result {
    Result::Ok(_) => success()
    Result::Error(_, reason: _) => failure()
}
```

and:

```phalcom
match dynamicValue {
    Known::Case(_) => known()
    _ => fallback()
}
```

The final `_` is not a special fallback construct. It is the ordinary wildcard applied to the entire remaining scrutinee space.

# 10. Exact Variant Patterns

Exact variant patterns mirror exact variant selector identity.

Given:

```phalcom
enum Animal {
    @variant Dog
    @variant Dog()
    @variant Dog(_ name: String)
    @variant Dog(_ name: String, named age: Int)
}
```

these denote different exact `VariantId`s:

```phalcom
Animal::Dog
Animal::Dog()
Animal::Dog(name)
Animal::Dog(name, named: age)
```

The exact selector is computed from syntax shape, not bound variable names:

```text
Dog(name)
    selector = Dog(_)
    child pattern = bind name

Dog(_, named: age)
    selector = Dog(_, named:)
    child patterns = wildcard, bind age
```

Exact match syntax is resolved against `EnumSemanticTable` / associated family identity and must end in one exact `VariantId`.

---

# 11. Singleton and Nullary Constructor Distinction

The already-ratified distinction is preserved exactly:

```phalcom
Animal::Dog      // singleton getter-shaped variant
Animal::Dog()    // explicit zero-argument constructor variant
```

They are different selectors, different `VariantId`s, different exact-case types, and may coexist in one family.

Matching one never matches the other.

---

# 12. Labeled Payload Patterns

Variant payload patterns mirror constructor selector labels:

```phalcom
Result::Error(error, reason: message)
Result::Error(_, reason: _)
```

For a declared payload parameter with an external label, the pattern must use that external label.

The semantic analyzer resolves each explicit argument to one candidate-specific `VariantFieldId`.

Local declaration names are not selector identity and are not used to accept a mismatched external label.

---

# 13. Exact Payload Patterns Are Full-Arity

An exact callable variant pattern without `...` must represent every selector field exactly once.

Given:

```phalcom
@variant Error(_ error: Error, reason message: String)
```

valid:

```phalcom
Result::Error(error, reason: message)
Result::Error(_, reason: _)
```

invalid:

```phalcom
Result::Error(error)
```

`_` is the explicit way to state that a known field exists but its value is ignored.

The `...` selector-gap syntax intentionally changes this rule and is defined separately below.

---

# 14. Callable Selector-Pattern Syntax

A `...` inside a callable variant pattern denotes a selector-shape gap:

```phalcom
Animal::Dog(...)
Animal::Dog(x, ...)
Animal::Dog(..., named: y)
Animal::Dog(x, ..., named: y)
```

The gap consumes zero or more selector slots.

For:

```phalcom
Animal::Dog(x, ..., named: y)
```

semantic selector projection is conceptually:

```text
SelectorPattern {
    base = Dog
    kind = Method
    prefix = [Positional]
    suffix = [Label("named")]
    has_gap = true
}
```

while the explicit child pattern projection is:

```text
prefix field 0 -> bind x
suffix named field -> bind y
all gap-consumed payload fields -> ignored
```

Only one `...` gap is permitted in a selector pattern, matching the existing `SelectorPattern` invariant.

The existing `phalcom-common::selector::SelectorPattern` must be the authority for selector compatibility. Match analysis may wrap it with pattern-child metadata but must not implement a second slot-shape matcher.

---

# 15. `Dog(...)` Means Callable Members, Not the Singleton

For a family:

```text
Dog
Dog()
Dog(_)
Dog(named:)
```

this pattern:

```phalcom
Animal::Dog(...)
```

selects:

```text
Dog()
Dog(_)
Dog(named:)
```

and does not select:

```text
Dog
```

because `Dog(...)` is a method/callable selector pattern.

The gap may consume zero slots, therefore the nullary callable `Dog()` participates.

---

# 16. Whole-Family Pattern

The whole family uses match-specific compact syntax:

```phalcom
Animal::Dog*
```

It means:

> Every variant member whose `VariantFamilyId` has base `Dog`, including getter/singleton and callable members.

For:

```text
Dog
Dog()
Dog(_)
Dog(named:)
```

coverage relationships are:

```text
Dog        ⊂ Dog*
Dog()      ⊂ Dog(...)
Dog(_)     ⊂ Dog(...)
Dog(...)   ⊂ Dog*
```

`Dog*` is resolved from variant family membership, not by pretending that `*` is a `SelectorPattern` slot.

---

# 17. Qualified and Contextual Variant Syntax

Canonical explicit syntax includes the owner:

```phalcom
Option::Some(x)
Option::None
Animal::Dog(...)
Animal::Dog*
```

Contextual shorthand is supported when the expected pattern domain determines a unique semantic owner/family:

```phalcom
match option {
    Some(x) => ...
    None => ...
}
```

and recursively:

```phalcom
match value {
    Some(Ok(x)) => ...
    Some(Error(_, reason: message)) => ...
    None => ...
}
```

Contextual resolution is not global constructor lookup.

The algorithm is:

```text
expected pattern subspace
    -> enumerate eligible variant owners/families
    -> filter by base
    -> filter by exact selector / SelectorPattern / family mode
    -> filter by visibility
    -> filter by GADT/specialization compatibility where available
    -> require one semantic family/owner interpretation
```

If multiple owners remain, diagnose ambiguity and require qualification.

If no variant interpretation exists, ordinary binding-pattern semantics may apply only where the grammar position admits a binding pattern. The semantic analyzer must never silently reinterpret a syntactically explicit variant form such as `Some(...)`, `Dog*`, or `Owner::Case` as a binding.

At an arm root, `_` is the canonical irrefutable fallback. A failed contextual singleton lookup must produce a variant-resolution diagnostic rather than being silently accepted as a typo-shaped fallback.

# 18. Nested Patterns

Patterns are recursive and nested matching is required in Part 05.1:

```phalcom
match value {
    Some(Ok(x)) => x
    Some(Error(_, reason: message)) => recover(message)
    None => fallback()
}
```

Each child pattern is analyzed under the expected semantic payload space of its parent candidate.

Candidate-specific payload specialization occurs before nested analysis.

This is required for GADTs and contextual shorthand: the child expected domain may be more precise than the declared unspecialized field template.

---

# 19. Or-Patterns

Or-pattern syntax is:

```phalcom
A | B
```

Examples:

```phalcom
Color::Red | Color::Green => warm()
Result::Ok(x) | Result::Cached(x) => use(x)
Some(Ok(x) | Cached(x)) => use(x)
```

Or-patterns are recursive pattern nodes, not merely duplicate-arm parser sugar.

Coverage law:

```text
Coverage(A | B) = Coverage(A) ∪ Coverage(B)
```

Usefulness must also be checked between alternatives. These are errors:

```phalcom
Color::Red | Color::Red => ...
Animal::Dog* | Animal::Dog() => ...
```

when the latter alternative contributes no reachable values.

---

# 20. Or-Pattern Binding Rule

All successful alternatives must introduce the same binding names.

Valid:

```phalcom
Result::Ok(x) | Result::Cached(x) => use(x)
```

Valid:

```phalcom
Result::Ok(_) | Result::Error(_) => ...
```

Invalid:

```phalcom
Result::Ok(x) | Result::Error(e) => ...
```

The shared branch would not have one definite binding environment.

Binding types are joined rather than required to be identical:

```phalcom
Foo::IntValue(x) | Foo::StringValue(x) => {
    // x: Int | String
}
```

The type join uses existing `TypeKnowledge` / union normalization rules.

---

# 21. Duplicate Bindings Within One Alternative

A single alternative may not bind the same name more than once:

```phalcom
Pair::Pair(x, x) // invalid
```

Part 05.1 does not define repeated-name equality patterns.

The user must spell distinct names and compare explicitly in branch code if desired.

Across or-pattern alternatives, the same name is expected and required when it represents the shared branch binding:

```phalcom
A(x) | B(x) // valid
```

---

# 22. Guards Are Deferred

Part 05.1 does not parse or analyze guards such as:

```phalcom
Some(x) if x > 0 => ...
```

The reason is semantic, not merely schedule: guard coverage can require arbitrary predicate reasoning and changes the subtraction law because matching a constructor no longer consumes its whole structural space.

The Part 05.1 semantic product design must remain extensible to future guarded arms, but no guard field is required in the v1 AST.

---

# 23. Pattern Selection Reuses Selector/Family Architecture

Associated lookup and match have different operations over shared declaration identity.

Associated lookup asks:

```text
Which associated value/member/family is denoted or invokable?
```

Pattern resolution asks:

```text
Which reachable VariantIds satisfy this selector/family constraint?
```

Shared authorities:

```text
Selector
SelectorPattern
SelectorKind / SelectorKindPattern
VariantFamilyId
VariantId
Associated/enum owner resolution
visibility helpers
family member tables
```

Match-specific authorities:

```text
child patterns
payload projections
candidate-specific exact cases
coverage space
residual space
GADT branch proof
binding joins
exhaustiveness
```

Part 05.1 must not invoke runtime or first-class family reification to match a family. Family-pattern resolution is a static declaration-set operation.

# 25. Variant Pattern Resolution

Variant patterns must resolve to exact candidate identities.

Recommended model:

```rust
pub enum PatternResolution {
    Wildcard,
    Binding { binding: BindingId, knowledge: TypeKnowledge },
    Variant(ResolvedVariantPattern),
    Or(ResolvedOrPattern),
    Tuple(...),
    List(...),
    Record(...),
    Map(...),
}

pub struct ResolvedVariantPattern {
    pub owner: DeclarationId,
    pub family: VariantFamilyId,

pub enum VariantSelectorConstraint {
    Exact(Selector),
    Pattern(SelectorPattern),

}

pub struct ResolvedVariantCandidate {

```

`field_projections` contains only source-explicit prefix/suffix/exact fields. Gap-consumed fields and wildcard-only fields need not require runtime extraction in Part 05.2, though semantic coverage still knows they exist.

# 26. Candidate Set Formation

For an explicit exact selector:

```phalcom
Animal::Dog(x)
```

resolution should produce at most one exact variant declaration before GADT reachability filtering.

For a selector pattern:

```phalcom
Animal::Dog(x, ..., named: y)
```

candidate formation is:

```text
resolve owner
    -> resolve Dog variant family
    -> enumerate family variant members
    -> keep constructor/callable selectors
    -> apply SelectorPattern::matches
    -> enforce name visibility
    -> specialize each candidate against expected owner type
    -> solve GADT compatibility
    -> produce reachable candidates
```

For whole family:

```phalcom
Animal::Dog*
```

candidate formation starts from all variant family members, including getter/singleton variants.

# 27. Pattern Space Is Separate From `TypeId`

Part 05.1 requires an internal value-space representation richer than ordinary types.

Reason:

```phalcom
Some(Ok(_))
```

can leave a residual equivalent to:

```text
None | Some(Error(...))
```

The ordinary type `Option<Result<...>>` cannot encode that nested residual precisely, and widening to `Some | None` loses payload coverage.

Introduce an internal immutable/canonical or structurally comparable `PatternSpace`, conceptually:

```rust
pub enum PatternSpace {
    Empty,
    Opaque(TypeId),
    Union(Box<[PatternSpace]>),
    Variant(VariantSpace),
    Tuple(Box<[PatternSpace]>),
    List(ListSpace),
}

pub struct VariantSpace {
    pub variant: VariantId,
    pub exact_case: TypeId,
    pub fields: Box<[PatternSpace]>,
    pub proof: BranchProofEnvironment,
}
```

Records/maps may initially project to conservative `Opaque` spaces where complete algebra is not implemented.

`PatternSpace` is semantic proof machinery. It is not a user-visible type and does not enter runtime representation.

# 28. Initial Scrutinee Space

Build the initial reachable value space from canonical semantic type knowledge.

Rules:

## 28.1 Exact case

```text
ExactCase(V, E)
    -> one VariantSpace(V, E, specialized fields)
```

## 28.2 Closed enum root

```text
Enum<T...>
    -> union of specialization-compatible declared variants
```

Each declared variant is checked against the scrutinee specialization through the GADT compatibility solver.

## 28.3 Union

```text
Space(A | B | C) = normalize(Space(A) ∪ Space(B) ∪ Space(C))
```

## 28.4 Transparent alias

There is no alias-specific coverage rule after canonical type resolution. The resolved underlying `TypeId` is consumed directly.

## 28.5 Open / unsupported type

Use:

```text
Opaque(type)
```

until a supported structural pattern proves a partition.

A remaining `Opaque` space requires `_` for totality unless a supported analyzer proves it empty.

---

# 29. Union Types and Type Aliases Participate in Exhaustiveness

Given:

```phalcom
type State =
      Connection::Disconnected
    | Connection::Connecting
    | Connection::Failed<Error>
```

and:

```phalcom
const state: State = ...
```

this may be exhaustive:

```phalcom
match state {
    Connection::Disconnected => ...
    Connection::Connecting => ...
    Connection::Failed(error) => ...
}
```

Even if the enclosing `Connection` enum contains additional variants, they are outside the static `State` union.

Conversely:

```phalcom
type Things = Dog | Cat
```

does not declare that an `Animal` variable can only contain `Dog` or `Cat`. Closedness follows the scrutinee semantic type, not the existence of an alias.

---

# 30. Mixed Closed/Open Unions

Given:

```phalcom
type Value = Option<Int> | Object
```

matching:

```phalcom
match value {
    Option::Some(x) => ...
    Option::None => ...
}
```

is not exhaustive because the `Object` component remains.

This is exhaustive:

```phalcom
match value {
    Option::Some(x) => ...
    Option::None => ...
    _ => ...
}
```

Coverage composition must preserve opaque residual members instead of discarding them when finite ADT members are consumed.

# 31. GADT Case Compatibility Is Constraint Solving, Not Subtyping

This is a hard soundness requirement.

Given:

```phalcom
enum Expr<T> {
    @variant Int(_ value: Int) -> Expr<Int>
    @variant Bool(_ value: Bool) -> Expr<Bool>
}
```

For:

```phalcom
fn eval<T>(_ e: Expr<T>) -> T {
    match e {
        Expr::Int(x) => ...
        Expr::Bool(x) => ...
    }
}
```

both cases are reachable. Matching `Expr::Int` establishes `T = Int`; matching `Expr::Bool` establishes `T = Bool`.

An implementation that asks only:

```text
is Expr<Int> <: Expr<T> ?
```

before introducing case evidence is incorrect.

For:

```phalcom
const e: Expr<Int> = ...
```

`Expr::Bool` is impossible because:

```text
scrutinee gives T = Int
case requires  T = Bool
```

The compatibility operation must combine:

```text
scrutinee owner specialization
variant result specialization
variant CaseTypeEnvironment
existing branch type substitutions
```

and classify each candidate.

---

# 32. GADT Compatibility Result

Recommended semantic result:

```rust
pub enum CaseCompatibility {
    Reachable {
        exact_case: TypeId,
        substitution: TypeSubstitution,
        proof: BranchProofEnvironment,
    },
    Impossible {
        contradiction: GadtContradiction,
    },
    Blocked {
        reason: BlockReason,
    },
}
```

`Blocked` is distinct from `Impossible`.

A blocked proof cannot be silently treated as unreachable to make an incomplete match appear exhaustive.

If the checker cannot prove that a case is impossible, it remains part of the conservative reachable space or causes analysis to remain blocked according to the existing semantic status model.

---

# 33. Successful Case Proof

On successful exact candidate observation, the branch receives:

```text
scrutinee exact-case evidence
candidate-specialized payload field knowledge
candidate CaseTypeEnvironment equalities
any compatible substitution derived from the scrutinee
```

If the scrutinee is a stable source binding, its branch flow fact should narrow to the exact-case type or the precise reachable union represented by the successful pattern.

For an arbitrary expression:

```phalcom
match compute() {
    Some(x) => ...
    None => ...
}
```

there is no source binding to refine, but the match analyzer still owns an internal once-evaluated scrutinee semantic fact used to type the branch.

---

# 34. Family Patterns as Implicit Candidate Unions

A family/selector pattern may cover multiple exact variants:

```phalcom
Animal::Dog(x, ...)
```

Semantically, its successful space is the union of all compatible exact candidates satisfying the selector constraint.

This behaves like an implicit or-pattern for:

```text
coverage
binding joins
common proof joins
payload type joins
```

but the semantic product should preserve the compact family/selector origin and exact candidate list rather than synthetically expanding the source AST.

---

# 35. Common Proof Rule for Or/Family Alternatives

A branch that can be reached through several alternatives receives only proof facts valid in all successful alternatives.

Example:

```phalcom
Expr::Int(x) | Expr::Bool(x) => ...
```

Alternative-specific facts:

```text
Int path:  T = Int,  x: Int
Bool path: T = Bool, x: Bool
```

Shared branch:

```text
x: Int | Bool
```

but neither:

```text
T = Int
T = Bool
```

may be asserted globally in the shared branch.

Proof environment join is intersection/common consequence, while binding type join is value-type union/join.

This distinction is mandatory for GADT soundness.

---

# 36. Pattern Binding Semantics

A successful pattern produces a binding environment.

Each binding product records at least:

```rust
pub struct PatternBindingResolution {
    pub binding: BindingId,
    pub name: Box<str>,
    pub knowledge: TypeKnowledge,
    pub source: SourceRange,
}
```

Rules:

1. wildcard binds nothing;
2. ordinary binding patterns bind the full successful subspace;
3. nested field bindings use specialized candidate field types;
4. or-pattern alternatives must bind the same names;
5. family-pattern candidates join each shared binding type across reachable candidates;
6. duplicate names within one alternative are errors;
7. no binding becomes visible from a failed alternative.

The no-partial-binding execution rule is realized by Part 05.2; Part 05.1 provides the binding plan.

---

# 37. Visibility During Matching

Variant visibility axes remain independent:

```text
name
construct
payload
```

Rules:

1. construction visibility does not affect matching;
2. an explicitly named pattern requires name visibility;
3. inaccessible variants still participate in the exhaustiveness universe;
4. `_` may cover inaccessible variants;
5. payload bindings or nested payload tests require payload visibility;
6. a wildcard child `_` does not expose the payload value and therefore does not require user-visible payload projection;
7. selector/family patterns are filtered according to what may be explicitly named from the source context, but exhaustiveness still accounts for inaccessible reachable members outside the named set.

This prevents privacy from creating false exhaustiveness.

# 38. Coverage, Usefulness, and Residual Space

Ordered match analysis is conceptually:

```text
remaining = initial_scrutinee_space

for arm in source order:
    arm_space = resolve(pattern, expected = remaining-compatible domain)
    reachable = intersect(remaining, arm_space)

    if reachable is empty:
        diagnose redundant or impossible arm
    else:
        analyze branch under reachable proof/bindings

    remaining = subtract(remaining, arm_space)

require remaining == Empty
```

Nested patterns require structural subtraction rather than only top-level constructor-set subtraction.

The implementation should use a usefulness/pattern-matrix-inspired algorithm or equivalent normalized space algebra, but the observable contract is the value-space law above.

---

# 39. Impossible vs Redundant

Keep distinct semantic categories.

## 39.1 Impossible

The pattern denotes no values compatible with the scrutinee even before previous-arm coverage.

Example:

```phalcom
const e: Expr<Int> = ...
match e {
    Expr::Bool(x) => ... // specialization contradiction
    Expr::Int(x) => ...
}
```

## 39.2 Redundant

The pattern can denote values of the scrutinee type, but every such value has already been consumed by previous arms/alternatives.

Example:

```phalcom
match animal {
    Animal::Dog* => ...
    Animal::Dog(name) => ... // already covered
    _ => ...
}
```

Both are compile errors in Part 05.1.

---

# 40. Static Exhaustiveness

A `match` is accepted only if:

```text
final residual space == Empty
```

No ordinary partial match is permitted.

If the checker cannot prove the final residual empty, it emits a non-exhaustive error.

For an opaque/open space:

```phalcom
match object {
    Known::Case(x) => ...
    _ => ...
}
```

`_` consumes the opaque remainder.

A successfully compiled match has no user-level `MatchError` path.

---

# 41. Exhaustiveness Witnesses

The analyzer should produce compact witnesses for diagnostics where possible.

Examples:

```text
uncovered:
    Option::None
```

```text
uncovered:
    Animal::Dog()
    Animal::Dog(named:)
```

Nested witness:

```text
uncovered:
    Option::Some(Result::Error(...))
```

Opaque witness:

```text
remaining domain cannot be proven empty:
    Object
```

Witness generation is semantic presentation data and may be summarized; it does not need to enumerate an infinite domain.

# 42. Initial Structural Exhaustiveness Boundary

Part 05.1 guarantees complete reasoning for:

```text

GADT specialization-compatible constructor sets

unions of supported spaces
transparent aliases of supported spaces
nested ADT/GADT patterns

```

It should also support straightforward finite tuple decomposition where tuple structure is statically known.

Conservative handling never weakens the static-totality guarantee: unsupported residuals require `_`.

# 43. Match Result Typing

Since match is an expression, normally completing arms contribute to a result join.

Conceptually:

```text
result(match) = join(branch_result_i for each normally completing reachable arm)
```

Abrupt/diverging branches do not force a value type into the join.

Examples:

```text
Int + Int
    -> Int

Int + String
    -> Int | String

all branches abrupt
    -> Never
```

Use the existing `TypeKnowledge` join and canonical union normalization machinery rather than a match-specific union constructor.

Expected-type checking should be bidirectional: when a match appears under an expected type, each reachable branch may be checked against that expectation while the synthesized branch result remains available for explanations.

---

# 44. Branch Flow Semantics

Each reachable branch begins from:

```text
pre-match flow
+ successful pattern value-space refinement
+ candidate/common GADT proof environment
+ pattern bindings
```

Normally completing arm flows join after the match.

Coverage space and flow state are distinct abstractions:

```text
PatternSpace
    proves which values remain / are covered

FlowState
    tracks facts about program bindings and fields
```

When a `PatternSpace` can be represented faithfully as a `TypeId` or exact-case union, the analyzer should project that fact into `FlowState` for stable scrutinee bindings.

It must not widen a nested residual merely to force all coverage state into ordinary flow predicates.

---

# 45. Negative Knowledge Between Arms

A later arm is analyzed under failure knowledge from earlier arms.

For:

```phalcom
match option {
    Some(x) => ...
    None => ...
}
```

the second arm's reachable domain is already the residual `None` space.

For nested patterns:

```phalcom
match value {
    Some(Ok(x)) => ...
    Some(Error(e)) => ...
    None => ...
}
```

the second arm receives residual knowledge excluding `Some(Ok(_))`, not merely the unchanged `Option<Result<...>>` root.

This is why residual coverage state must not be represented only by current `FlowPredicate::IsNotInstance` facts.

---

# 46. Reuse Existing Flow Predicates Where Appropriate

Part 05.1 does not require a new `FlowPredicate::IsVariant` merely because runtime Part 04 has `IsVariant`.

Where exact-case type refinement can be represented by existing instance/type predicates, reuse those facts.

Add a variant-specific flow predicate only if concrete implementation evidence shows it is necessary for stable provenance or relation behavior.

Pattern coverage remains authoritative for match totality regardless of which flow predicate representation is chosen.

# 58. 5.1 Acceptance Criteria

Part 05.1 is complete only when all of the following are true:

1. `match` and `=>` lex/parse as dedicated syntax.
2. `Expr::Match` is preserved in the AST.
3. `_` is a dedicated recursive wildcard pattern.
4. or-patterns are recursive and parsed.
5. exact singleton/nullary/callable variant patterns preserve selector distinctions.
6. labeled payload patterns preserve external labels.
7. exact patterns require every payload selector slot.
8. `...` selector patterns reuse canonical `SelectorPattern` matching.
9. `Variant*` selects the whole variant family.
10. qualified and contextual variant syntax resolve to semantic family/variant identity.
11. nested patterns receive candidate-specialized expected domains.
12. union types and transparent alias unions participate in coverage.
13. GADT reachability uses constraint compatibility, not plain subtype filtering.
14. successful GADT patterns introduce branch-local declaration-owned equalities.
15. or/family branches retain only common proof facts.
16. shared binding types join soundly.
17. coverage preserves nested residual spaces.
18. redundant and impossible patterns are errors.
19. every accepted match is statically exhaustive.
20. opaque residuals require `_` unless proven empty.
21. match result types join normally completing reachable branches.
22. branch flows are joined using existing control-analysis machinery.
23. match-specific diagnostics are structured and machine-coded.
24. explanation DAG records proof/reachability/exhaustiveness reasoning.
25. `CallableAnalysis` publishes stable match resolution products.
26. no `phalcom-core` name-based execution changes are required for 5.1 completion.

# 60. Part 05.2 Forward Contract

Part 05.2 begins from these facts, not from source syntax:

```text
MatchResolution exists
all accepted matches are total
all variant syntax is resolved to exact VariantIds/candidate sets
all explicit payload positions are mapped to VariantFieldIds
all GADT compatibility is solved statically
all branch binding/proof joins are fixed
all redundancy/impossibility has already been diagnosed
```

Part 05.2 then realizes the match through Part 04's runtime contract:

```text
evaluate scrutinee once
IsVariant(exact candidate)
GetVariantPayload(resolved field index)
recursive tests
commit bindings only after pattern success
execute selected branch
join control flow
```

This split is intentional. Static elimination is a theorem produced by `phalcom-semantic`; execution is a projection of that theorem.

# 61. Final Architecture Statement

Part 05.1 establishes the following invariant:

> A Phalcom match arm never means “ask the runtime whether a name looks like this constructor.” It means “the semantic analyzer has resolved this pattern to a statically known value space, exact variant candidates, payload projections, and proof consequences.”

And the whole match establishes:

> The ordered union of useful arm spaces covers the complete reachable scrutinee space. Therefore a successfully analyzed match cannot fall through at runtime.

That is the semantic contract Part 05.2 must preserve exactly.
