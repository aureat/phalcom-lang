# Phalcom ADT/GADT + Associated Lookup
## Part 3.5 — G1 Boundary, Option-B-Ready Reification, and Family-Type Source Design

**Status:** Normative companion design specification  
**Series:** ADT/GADT + Associated Lookup, Part 3.5  
**Relationship to Part 3:** supplements Part 3; does not revise Part 3 documents  
**Precedence:** for G1 only, this document closes the unresolved Part 3 decision gate and is normative  
**Part 3 implementation target:** Option A — concrete/contextually specialized reification  
**Deferred capability:** Option B — declaration-polymorphic reification with universal value types  
**Deferred future syntax direction:** `forall<T, E> (T, E) -> Result<Box<T>, E>`  
**Candidate future family-type syntax:** `Family<#{ ... }>`  
**Repository baseline checked:** `feat/adts` at `2c8b5840fc5a864968cb2a832540fbcba868d9f8`

---

# 1. Purpose

Part 3 introduces the formal static semantics of associated lookup and invocation:

```phalcom
Owner::member
Owner::member::(_)
Owner::member::*
Owner::member(args)
```

It also introduces first-class family values and the formal structural family type required to type them.

One unresolved question — G1 — concerns what happens when an associated declaration depends on declaration-owned generic parameters and is reified before those parameters have been specialized.

For example:

```phalcom
enum Option<T> {
    @variant None
    @variant Some(_ value: T)
}

const some = Option::Some::(_)
const family = Option::Some::*
const none = Option::None
```

The declaration schema contains `T`, but none of these expressions supplies `T` by itself.

This document resolves G1 for Part 3 and constrains the architecture so the stronger future model remains possible without redesigning associated identity, family resolution, generic declaration schemas, or runtime lowering.

The central decision is:

> **Part 3 implements concrete/contextually specialized reification. A reified associated value may escape only after every residual generic binder that would otherwise appear free in its value type has been solved. This includes owner-declared parameters and member-local generic parameters when Phalcom has no already-existing first-class polymorphic representation for them. The implementation must nevertheless preserve the original generic schema and binder metadata so a later universal-type layer can expose the same declaration as a first-class polymorphic value.**

Part 3.5 does **not** implement `forall`, rank-N polymorphism, Hindley–Milner generalization, or source family-type annotations.

---

# 2. G1 Is Closed: Option A Is Normative for Part 3

## 2.1 Explicit specialization is valid

```phalcom
const some = Option<Int>::Some::(_)
```

The checker resolves the associated member against `Option<Int>` and produces a concrete callable value.

Conceptually:

```text
variant constructor schema:
    Some<T> : (T) -> ExactCase(Some(_), Option<T>)

owner specialization:
    T = Int

reified callable:
    (Int) -> ExactCase(Some(_), Option<Int>)
```

Likewise:

```phalcom
const family = Option<Int>::Some::*
```

produces a concrete family value whose exact members contain no escaping declaration metavariables.

## 2.2 Contextual specialization is valid

The user does not always need to spell the owner arguments.

```phalcom
const some: (Int) -> Option<Int> = Option::Some::(_)
```

The expected callable type may constrain `T = Int` before expression finalization.

A higher-order call may do the same:

```phalcom
transform(values, with: Option::Some::(_))
```

when the expected parameter type uniquely proves the specialization.

The same rule applies to family values when an expected family type is available internally or, in a future source revision, explicitly in source.

## 2.3 Unspecialized escaping reification is rejected

In Part 3:

```phalcom
const some = Option::Some::(_)
```

is underconstrained if no contextual evidence determines `T`.

Likewise:

```phalcom
const family = Option::Some::*
const none = Option::None
```

are underconstrained if their exact value/family type still depends on unsolved owner or member-local generic parameters.

The semantic state is not “unknown declaration.” The declaration is known exactly. The failure is that Part 3 has no value-level universal quantifier with which to publish the residual parameter.

Recommended diagnostic interpretation:

```text
associated generic value is underconstrained

`Option::Some::(_)` depends on declaration parameter `T`,
but no concrete specialization can be proven at this expression.

Provide an owner specialization or contextual type.
```

## 2.4 Underconstraint must not become Dynamic

The checker must not recover such an expression as:

```text
Dynamic
Object
Any
exists T. ...
```

nor as a callable/family containing a mutable unresolved `T?`.

The declaration schema is formally known. The lack of a Part 3 universal-value representation is a static underconstraint boundary, not a dynamic-runtime boundary.

## 2.5 First-use specialization is forbidden

This model is rejected:

```phalcom
const some = Option::Some::(_)

some(1)       # chooses T = Int
some("text")  # fails because an earlier call mutated the binding
```

A first-class value must never contain a shared inference variable whose solution changes as later uses are encountered.

Part 3 either proves a concrete reification at the reification site or rejects it.

Future Option B will solve the problem differently: every use will instantiate a declaration-owned universal scheme freshly.

# 3. Direct Invocation Is Not Reification

This distinction must remain explicit in the implementation.

```phalcom
Option::Some(42)
```

is not required to know `T` before invocation analysis begins.

The call already contains evidence capable of solving the declaration schema:

```text
instantiate schema
    T := fresh inference variable α

argument evidence
    Int <: α

owner / GADT / expected-result constraints
    ...

solve
    α = Int

publish
    ExactCase(Some(_), Option<Int>)
```

Therefore:

```phalcom
Option::Some(42)
```

may be valid while:

```phalcom
const some = Option::Some::(_)
```

is underconstrained.

The semantic principle is:

> **Invocation may temporarily introduce inference variables because the same semantic operation contains evidence that can solve them. Escaping reification may not publish such variables in Part 3.**

# 4. Deferred Option B: Declaration-Polymorphic Values

Option B is not part of Part 3 implementation, but its eventual semantics are defined sufficiently to constrain architecture.

## 4.1 Future universal type syntax

The preferred future syntax is:

```phalcom
forall<T> (T) -> T
```

and:

```phalcom
forall<T, E> (T, E) -> Result<Box<T>, E>
```

Explicit kinds may be permitted where necessary:

```phalcom
forall<F: Type -> Type, T: Type> (F<T>) -> F<T>
```

Ordinary `T` may default to kind `Type` when unambiguous.

`forall` describes a **polymorphic value type**, not a type lambda.

Phalcom type lambdas remain distinct:

```phalcom
<T> =>> Result<T, Error>
```

Conceptually:

```text
<T> =>> F<T>
    type-level function
    kind-level abstraction

forall<T> F<T>
    universally quantified value type
    each value use may instantiate T freshly
```

## 4.2 Future exact associated callable

A future revision could allow:

```phalcom
const some:
    forall<T> (T) -> Option<T>
    = Option::Some::(_)
```

More precisely, with exact case types available:

```phalcom
const some:
    forall<T> (T) -> Case<Option<T>::Some(_)>
    = Option::Some::(_)
```

Each use would instantiate a fresh `T`:

```phalcom
const a = some(1)
const b = some("text")
```

Conceptually:

```text
first use:
    fresh T₁
    T₁ = Int

second use:
    fresh T₂
    T₂ = String
```

No type state is shared between the calls.

## 4.3 Future generic singleton case value

A generic singleton variant is an important test of the model:

```phalcom
const none:
    forall<T> Case<Option<T>::None>
    = Option::None
```

This is a universal value, not a zero-argument callable.

That distinction is one reason Option B must be a general universal-type feature rather than special behavior hidden inside callable reification.

## 4.4 Declaration-provided polymorphism is narrower than automatic generalization

Future Option B should initially preserve quantification already owned by declarations.

It does not imply that every inferred expression with an unresolved type variable is automatically generalized.

These are different operations:

```text
reify generic declaration
    preserve known declaration binders

arbitrary expression inference
    unresolved metavariables do not automatically become forall binders
```

A future language revision may separately adopt broader let-generalization, but Option-B readiness must not depend on it.

# 5. Architectural Requirement: Preserve Schemas, Specialize Views

This is the most important implementation requirement for Part 3.

A declaration's generic schema must not be destroyed when a concrete associated value is produced.

Conceptually:

```text
AssociatedMemberSchema
    declaration identity
    declaration-owned binders
    binder kinds
    where constraints
    GADT equalities
    parameter/result templates

        specialize(owner/context)
                ↓

AssociatedMemberView
    concrete/substituted parameter types
    concrete/substituted result type
    exact invocation identity
```

Part 3 consumes the concrete view.

Future Option B can instead wrap the residual schema in a universal type scheme.

The architecture must therefore follow:

> **specialization is a projection over immutable declaration semantics, not mutation of declaration semantics.**

---

# 6. Required Separation of Generic Binder Classes

The implementation must preserve where each generic binder originated.

At minimum, distinguish:

```text
Declaration-owned parameter
    Result<T, E>

Callable-local parameter
    convert<U>(...)

GADT equality/index variable
    case-specific equalities

Inference variable
    fresh solver-local metavariable

Future universal binder
    value-level forall parameter
```

These concepts must never collapse into one anonymous `TypeId` category.

Example:

```phalcom
class Converter<T> {
    @class
    convert<U>(_ value: U) -> Pair<T, U>
}
```

A reified member schema depends on both:

```text
owner binder:
    T

callable binder:
    U
```

Part 3 may specialize `T` from:

```phalcom
Converter<Int>::convert::(_)
```

but `U` is a separate question. Under Option A, if the current first-class callable type cannot represent a polymorphic member-local binder, `U` must also be solved contextually before this callable value can escape. Direct invocation may still instantiate and infer `U` normally because the call supplies inference evidence.

Future Option B may instead preserve `U` as a universal member-local binder. The representation must retain the ownership distinction so that adding this later does not require reconstructing where the binder came from.

# 7. Required Separation of Family Identity, Family Type, and Captured Family Value

These are three different semantic entities.

## 7.1 Nominal associated family identity

```text
AssociatedFamilyId {
    owner,
    base
}
```

This answers:

> Which declaration-owned associated family is this?

## 7.2 Structural family type

The family type answers:

> Which selector-shaped operations does a value provide, and what are their member types?

It must not be represented as a union.

A union says:

```text
A | B
```

meaning one value may be A or B.

A family says:

```text
operation A is supported
AND
operation B is supported
```

It is therefore a structural capability row.

## 7.3 Captured associated family value/view

A captured family also needs semantic acquisition information:

```text
lookup owner
owner specialization
access-filtered member set
defining declaration for inherited members
exact target identities
specialized member types
```

That information must not be thrown away merely because two values happen to have the same structural `FamilyType`.

This is why captured denotation/resolution must remain richer than the family type itself.

---

# 8. Formal Family-Type Requirements

Part 3 needs a complete internal family type even though source annotations for that type are deferred.

Conceptually:

```text
FamilyType {
    members: [
        FamilyMember {
            operation: SelectorOperationShape,
            kind: Value | Callable,
            type: TypeId
        }
    ]
}
```

The operation identity must distinguish at least:

```text
Getter
Setter
Method(slots)
SubscriptGet(slots)
SubscriptSet(slots)
Operator method shapes through the ordinary selector model
```

A singleton variant contributes a value member.

A zero-argument constructor contributes a callable method-shaped member.

These are not interchangeable.

---

# 9. Candidate Source Syntax for Full Family Types

Part 3 does not implement this grammar. Part 3.5 records the preferred design direction so the formal representation is tested against realistic source expressiveness.

The preferred shape is:

```phalcom
Family<#{
    convert(_): (String) -> Bytes
    convert(_,or): (String, Error) -> Bytes
}>
```

The outer `Family<...>` establishes that the enclosed record-like body is not an ordinary record row. Inside it, each key is parsed as an **exact selector**, not as a record-field label.

The right side is the formal type of the exact member selected by that key.

## 9.1 Future polymorphic member schemes

Deferred Option B can compose naturally:

```phalcom
Family<#{
    convert(_): forall<T> (T) -> Box<T>
    convert(_,or): forall<T, E> (T, E) -> Result<Box<T>, E>
}>
```

This means the exact operations have independently quantified member schemes.

## 9.2 Why this syntax fits Phalcom

It reuses existing visual conventions:

```phalcom
#{ ... }
```

for a structural collection of named/shaped entries, while `Family<...>` changes the interpretation of keys from fields to exact selector capabilities.

It also keeps the type visually close to the declarations and associated syntax developers already use.

---

# 10. Exact Case Type Source Representation

Part 3 internally requires exact case types. A future source syntax should expose them without pretending each variant is an ordinary source class.

The recommended candidate syntax is:

```phalcom
Case<Option<Int>::Some(_)>
```

The payload is an enum owner type form plus an exact variant selector.

Examples:

```phalcom
Case<Option<Int>::None>
Case<Option<Int>::None()>
Case<Option<Int>::Some(_)>
```

These are three distinct exact case types when all three declarations exist.

The syntax intentionally reuses the exact associated selector grammar.

## 10.1 Enum root versus exact case

```phalcom
Option<Int>
```

means the enum/root type.

```phalcom
Case<Option<Int>::Some(_)>
```

means the exact `Some(_)` case under that owner specialization.

Formally:

```text
Case<Option<Int>::Some(_)> <: Option<Int>
```

but the reverse does not hold.

## 10.2 GADT cases

Given:

```phalcom
enum Expr<T> {
    @variant Int(_ value: Int) -> Expr<Int>
    @variant Bool(_ value: Bool) -> Expr<Bool>
}
```

source representation could be:

```phalcom
Case<Expr<Int>::Int(_)>
Case<Expr<Bool>::Bool(_)>
```

The following must be rejected as an inconsistent type form:

```phalcom
Case<Expr<String>::Int(_)>
```

because the exact variant result proves the enum index is `Int`.

This is not merely a naming failure; it is a GADT owner/index contradiction.

# 11. Family Source Representation Across Selector Kinds

The candidate syntax must be able to describe every family member kind.

## 11.1 Getter versus zero-argument method

```phalcom
Family<#{
    value: () -> Int
    value(): () -> String
}>
```

The left side preserves selector identity:

```text
value     => #value
value()   => #value()
```

The right side may use callable representation for behavioral getter references, while the selector key preserves the fact that acquisition refers to getter-shaped behavior rather than the zero-argument method lane.

## 11.2 Setter

```phalcom
Family<#{
    value=(put): (Int) -> Unit
}>
```

## 11.3 Subscript get and set

```phalcom
Family<#{
    [_]: (Key) -> Value
    [_]=(put): (Key, Value) -> Value
}>
```

The exact setter return type follows the language's canonical setter semantics; the syntax does not prescribe whether that is `Value` or `Unit`.

## 11.4 Operators

```phalcom
Family<#{
    +(_): (Number) -> Number
    -(_): (Number) -> Number
}>
```

Operators reuse exact selector syntax rather than adding a family-only encoding.

## 11.5 Singleton and constructor variants in one family

Given:

```phalcom
enum Option<T> {
    @variant None
    @variant None()
    @variant None(_ value: T)
}
```

for a concrete owner:

```phalcom
Family<#{
    None: Case<Option<Int>::None>
    None(): () -> Case<Option<Int>::None()>
    None(_): (Int) -> Case<Option<Int>::None(_)>
}>
```

The first row is a value member.

The second and third rows are callable variant constructors.

The type syntax therefore preserves the semantic distinction between singleton acquisition and construction.

# 12. Selector Base Names in Structural Family Types

The candidate syntax writes a selector base:

```phalcom
Family<#{
    convert(_): ...
    convert(_,or): ...
}>
```

Part 3's internal family type should not accidentally make a source spelling decision here.

There are two coherent future semantics.

## 12.1 Base-sensitive structural typing

Under this model, `convert(_)` and `build(_)` are different structural requirements.

This behaves most like a conventional structural interface/protocol: operation names are part of the contract.

Advantages:

- unsurprising when reading the source type;
- aliases correspond directly to named capabilities;
- family types resemble protocols closely.

Cost:

- two captured families invoked identically after capture cannot satisfy one another if their original associated base differs.

## 12.2 Base-erased family capability typing

Under this model, all entries in one `Family<#{...}>` must share one family base, but normalization erases that base and retains only relative operation shapes.

Then:

```phalcom
Family<#{
    convert(_): (String) -> Bytes
}>
```

and:

```phalcom
Family<#{
    build(_): (String) -> Bytes
}>
```

can be structurally equivalent because a captured family is invoked as a value:

```phalcom
f("text")
```

not as:

```phalcom
f.convert("text")
```

Advantages:

- maximizes higher-order composability;
- matches the fact that associated base name is provenance after capture;
- retains nominal family identity separately in denotation.

Cost:

- the written base becomes partly descriptive rather than structural, which requires explicit documentation.

## 12.3 Part 3.5 recommendation

Do **not** settle this through Part 3 implementation.

Internally, preserve both:

```text
AssociatedFamilyId.base
```

and a structural operation representation that can be compared independently.

For the eventual source syntax, the current recommendation is **base-erased structural capability typing**, because the family value's ordinary invocation protocol observes call shape rather than the associated source base. However, source syntax is deferred specifically so real higher-order API experience can validate this choice.

The implementation must therefore not key `FamilyType` interning solely by `AssociatedFamilyId` or source base name.

# 13. Family-Wide Versus Member-Local Future Quantification

The proposed syntax can express two different scopes.

Family-wide:

```phalcom
forall<T> Family<#{
    encode(_): (T) -> Bytes
    decode(_): (Bytes) -> T
}>
```

One universal `T` scopes over the entire family value instantiation.

Member-local:

```phalcom
Family<#{
    encode(_): forall<T> (T) -> Bytes
    decode(_): forall<T> (Bytes) -> T
}>
```

Each exact member owns an independent universal scheme.

Mixed scope is also meaningful:

```phalcom
forall<E> Family<#{
    ok(_): forall<T> (T) -> Result<T, E>
    error(_): (E) -> Result<Never, E>
}>
```

This is a strong architectural reason to preserve declaration binder ownership and member boundaries in Part 3.

Part 3 does not need to implement either form.

# 14. Option-B-Ready Requirements for Part 3 Implementation

The following are normative architectural constraints.

## R1 — Declaration schemas remain canonical

Associated resolution consumes generic declaration templates; it does not replace them with specialized signatures globally.

## R2 — Specialization produces a view

Applying `Option<Int>` to `Some(_)` creates a specialized member view. It does not mutate the `Option<T>::Some(_)` schema.

## R3 — Residual binders remain identifiable

When Part 3 rejects an escaping reification, it must still be possible to identify exactly which declaration-owned binders remain unresolved and what their kinds/constraints are.

## R4 — No first-use metavariable escapes

A binding may not store solver-local inference variables as a substitute for future universal polymorphism.

## R5 — Kinds are preserved

A future binder may be higher-kinded. Do not assume every residual declaration parameter has kind `Type`.

## R6 — Owner and callable binders stay distinct

Do not flatten declaration-owned and callable-local parameters into one positional generic list with lost ownership.

## R7 — GADT equalities remain attached to schemas/views

Exact case result equalities must survive specialization so future universal reification can instantiate them correctly.

## R8 — Family members remain individually identifiable

A family must retain exact member identities and member schemas; do not reduce it to only a list of final return types or a union.

## R9 — Family type is structural

`TypeData::Family` or its equivalent represents operation capabilities, not nominal family identity.

## R10 — Captured denotation is richer than structural type

Lookup owner, specialization, access-filtered members, defining declarations, and exact target identities remain available separately from structural type equivalence.

## R11 — Concrete Option A is enforced only at the escape/finalization boundary

The implementation may use fresh inference variables internally while solving contextual specialization. It must reject only if residual owner/member generic binders remain free in the reified value when the expression is finalized.

## R12 — Direct invocation keeps ordinary generic inference

Do not make Option A require explicit owner specialization for direct calls.

## R13 — No `forall` parser/type node is required in Part 3

Option-B readiness is architectural metadata preservation, not premature implementation of universal types.

## R14 — Part 4 must consume resolved products

Runtime lowering may choose compact/direct representations, but it must not rediscover generic associated semantics from syntax.

# 15. Relationship to Protocols and Interfaces

A family is not itself the language's protocol/interface declaration mechanism.

A useful distinction is:

```text
protocol/interface
    requirement about operations some receiver/value must support

Family value
    first-class captured set of exact operations

Family structural type
    protocol-like requirement describing which operations that family value supports
```

A family therefore resembles:

```text
overload set
+ first-class capability object
+ structural interface row
```

but is not reducible to any one of them.

At runtime an erased family may eventually resemble a witness table or operation table, but Part 3 resolves its static membership first. Dynamic representation must not imply dynamic semantic lookup.

# 16. Part 3 Concurrency Rule

Part 3 implementation may proceed while this document is being adopted.

This document is intentionally non-blocking except for G1 semantics.

An implementation agent should follow this rule:

```text
if Part 3 plan says G1 is undecided:
    Part 3.5 closes it as Option A

if Part 3 code already implements a compatible concrete reification model:
    keep it
    verify the Option-B-ready invariants

if Part 3 code introduces irreversible monomorphic assumptions:
    refactor those assumptions before treating the task as complete
```

The agent does **not** need to implement:

```text
forall syntax
universal TypeData
family source annotations
Case<...> source syntax
```

in order to satisfy Part 3.5.

# 17. Required Acceptance Scenarios

The Part 3 implementation should eventually demonstrate the following semantics.

## 17.1 Explicit generic owner reification

```phalcom
const some = Option<Int>::Some::(_)
```

Expected: concrete callable; no residual owner generic.

## 17.2 Contextually specialized reification

```phalcom
const some: (Int) -> Option<Int> = Option::Some::(_)
```

Expected: `T = Int` solved before publication.

## 17.3 Bare escaping generic reification

```phalcom
const some = Option::Some::(_)
```

Expected: underconstrained diagnostic, not Dynamic.

## 17.4 Bare generic family reification

```phalcom
const some = Option::Some::*
```

Expected: underconstrained when no contextual family type specializes `T`.

## 17.5 Generic singleton case

```phalcom
const none = Option::None
```

Expected: underconstrained if `T` remains unsolved.

## 17.6 Direct generic constructor invocation

```phalcom
const value = Option::Some(42)
```

Expected: inference solves `T = Int`; exact case result retained.

## 17.7 Expected-result constructor inference

For a constructor with a generic parameter not determined by arguments, expected result may complete inference.

## 17.8 No first-use specialization

There must be no accepted semantic path where a stored reified family/member contains a mutable solver metavariable later fixed by its first invocation.

## 17.9 Schema immutability

Specializing one reification to `Int` must not affect a later independent specialization to `String`.

## 17.10 Generic metadata survives specialization

Tests/debug assertions should be able to recover the original declaration binder identities and constraints from the schema used to produce a concrete view.

# 19. Non-Goals

Part 3.5 does not require implementation of:

- `forall` source grammar;
- universal type AST nodes;
- universal `TypeData` representation;
- rank-N polymorphism;
- impredicative polymorphism;
- automatic let-generalization;
- existential packaging;
- first-use monomorphization;
- source `Family<#{...}>` grammar;
- source `Case<...>` grammar;
- runtime generic dictionaries solely for `forall`;
- a protocol/interface declaration system;
- Part 4 lowering.

# 20. Normative Decision Register

**G1-A — Ratified for Part 3**  
Associated member/family reification must become concrete by expression finalization. Explicit owner arguments and contextual expected typing may solve owner and member-local generic binders; any binder that would otherwise remain free in the escaping value causes underconstraint in Part 3.

**G1-B — Deferred**  
Future declaration-polymorphic values may preserve declaration-owned generic binders as universal binders, with preferred syntax `forall<...> ...`.

**G1-C — Rejected**  
First-use specialization of a stored unresolved associated value.

**G1-D — Rejected as fallback**  
Dynamic/Object/Any recovery merely because declaration generic parameters remain unresolved.

**G1-E — Architectural requirement**  
Part 3 must preserve immutable declaration schemas, binder identity/kinds, specialization provenance, exact member identity, and captured family views so future universal reification can be layered on top.

**FT-1 — Required now**  
A formal structural family type exists internally.

**FT-2 — Deferred syntax**  
Source spelling for family types is not required by Part 3.

**FT-3 — Preferred future spelling**  
`Family<#{ selector: member-type ... }>`.

**CASE-1 — Preferred future spelling**  
`Case<OwnerType::ExactVariantSelector>`.

**POLY-1 — Preferred future spelling**  
`forall<T, ...> ValueType`.

---

# 21. Final Requirement

Part 3 should be implemented as though Phalcom does **not yet have universal first-class values**, while its semantic architecture should be built as though Phalcom **will eventually have them**.

That means concrete reification today must be a specialization of a richer declaration schema, not the only representation the compiler knows how to express.

If this boundary is preserved, future Option B becomes primarily:

```text
add universal type/scheme representation
+ define generalization/reification eligibility
+ instantiate schemes at use sites
+ add forall source syntax/presentation
```

rather than:

```text
redesign associated resolution
redesign family identity
redesign variant constructor identity
redesign GADT result semantics
redesign captured family values
```

That is the architectural objective of Part 3.5.
