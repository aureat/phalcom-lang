# 1. Executive Summary

Part 05.1 establishes Phalcom's formal pattern-elimination semantics. It parses `match`, resolves exact and contextual variant patterns, expands selector/family patterns, computes recursive pattern spaces, solves GADT case compatibility, joins or-pattern bindings/proofs, rejects impossible/redundant alternatives, proves static totality, and publishes immutable semantic match products.

Part 05.2 makes those already-proven meanings executable.

The architecture is:

```text
source program
    ↓
Part 05.1 semantic analysis
    ↓
MatchResolution / formal pattern resolutions
    exact VariantIds
    VariantFieldIds
    ordered alternatives
    binding identities
    reachability / totality proof
    GADT proof already discharged
    ↓
Part 05.2 semantic-to-backend projection
    ↓
MatchLoweringSpec / ExecutablePattern
    exact runtime-test targets
    physical payload slots
    executable alternative tree
    arm-local binding table
    ↓
AST compiler
    ↓
ordinary jumps + scratch locals
IsVariant
GetVariantPayload
    ↓
Part-04 VM/runtime primitives
```

The central Part 05.2 rule is:

> **Execution is a projection of the theorem produced by `phalcom-semantic`. `phalcom-core` must never become a second source-level pattern resolver.**

The compiler may decide how to order already-frozen candidate tests, where to store scratch values, and how to arrange jumps. It may not decide what `Some`, `Animal::Dog*`, `Dog(x, ..., named: y)`, a union alias, or a GADT case means.

The initial implementation deliberately uses straightforward ordered exact-case tests. Jump tables, decision-DAG factoring, shared-prefix factoring, payload-extraction reuse beyond the obvious local staging opportunities, and other match-specific optimizations remain backend backlog work. They must never require semantic reinterpretation.

Part 04 already provides the core runtime contract required here:

```text
Bytecode::IsVariant(u16)
Bytecode::GetVariantPayload(u16)

VM::runtime_variant_of(Value)
VM::value_is_variant(Value, RuntimeVariantId)
VM::case_payload_len(Value)
VM::case_payload_at(Value, usize)
```

Therefore Part 05.2 does not introduce a runtime pattern interpreter, runtime family-pattern object, or runtime GADT proof system.

# 5. Current Legacy Pattern Compiler

`phalcom-core/src/compiler/lib/patterns.rs` currently owns execution for destructuring and refutable patterns.

It already contains a valuable two-phase design:

```text
declare pattern locals
emit only tests
commit bindings only after complete success
```

This prevents a failed refutable pattern from partially mutating visible locals.

However the ADT portion is legacy and must be retired:

```text
Some -> send isSome
None -> send isNone
other variant -> compare value.class against global constructor/class
payload -> structural positional reads
```

Those operations do not represent the new ADT case identity model.

Part 05.2 preserves the no-partial-binding invariant and replaces ADT interpretation with formal semantic lowering products.

---

# 6. Current `if let` / `while let` Execution

The compiler currently has dedicated `compile_if_let` and `compile_while_let` paths.

Both already obey useful execution invariants:

```text
if let:
    evaluate RHS once
    store hidden value
    test pattern
    commit bindings on success
    execute then body inline
    failure -> else path

while let:
    reserve one hidden value slot
    each iteration evaluates RHS exactly once
    test pattern
    commit bindings on success
    failure exits loop
```

Part 05.2 should retain these control structures but migrate their pattern tests/bindings to the shared executable pattern engine.

`if let` and `while let` do not become syntax sugar for `match`.

# 7. Match Is Statically Total at Runtime Boundary

Part 05.1 establishes:

> Every accepted `match` is statically proven total.

Therefore Part 05.2 must not introduce normal runtime partial-match semantics.

There is no user-visible:

```text
MatchError
PatternMatchError for ordinary match
implicit default branch
```

The backend may retain an internal fallthrough trap for compiler/runtime consistency checking. Reaching it means a soundness/integration failure, not ordinary program control flow.

# 8. Match Arm Branch Semantics

The source permits:

```phalcom
pattern => expression
```

and:

```phalcom
pattern => {
    statements
    result
}
```

The connected compiler's ordinary `Expr::Block` lowering creates a closure value. That is not what a braced match arm means operationally.

The compiler already has a correct inline-body primitive:

```rust
compile_inline_block_body(BlockExpr)
```

It compiles a `BlockExpr` directly into the current function, creates no closure/call frame, preserves enclosing `return` behavior, opens an ordinary lexical scope, and leaves exactly one value on normal fallthrough.

Normative Part 05.2 rule:

> **A braced match arm is compiled as an inline branch body, not as an ordinary closure value.**

If Part 05.1 represents the arm branch as `Expr::Block`, the `match` compiler must recognize that AST position and call `compile_inline_block_body` on its `BlockExpr` payload. Non-block arm expressions use ordinary `compile_expr`.

This is branch-control lowering, not source semantic re-resolution.

# 9. Semantic-to-Backend Match Projection

Extend `ModuleLoweringSemantics` with compiler-facing match data.

Recommended shape:

```rust
pub enum LoweringSiteKind {
    AssociatedLookup,
    AssociatedInvoke,
    FamilyApplication,
    Match,
}

pub struct ModuleLoweringSemantics {
    pub module: ModuleId,
    pub enums: Box<[EnumLoweringSpec]>,
```

The exact map/key names may follow current implementation conventions.

One match expression should normally correspond to one `LoweringSiteKind::Match` entry using the full `MatchExpr` source range.

Nested pattern information belongs inside the match lowering spec rather than becoming separate `LoweringSite`s.

It is produced from formal Part 05.1 semantic products and consumed only by compiler lowering.

# 12. Exact Variant Candidate Projection

Every variant-capable executable leaf must eventually contain exact semantic case identities.

Conceptually:

```rust
pub struct ExecutableVariantCandidate {
    pub variant: VariantId,
    pub projections: Box<[ExecutableFieldProjection]>,
}
```

A selector/family source pattern may produce multiple candidates, but every candidate is exact.

For example:

```phalcom
Animal::Dog(...)
```

may become:

```text
VariantId(Dog())
VariantId(Dog(_))
VariantId(Dog(name:))
VariantId(Dog(_, age:))
```

The compiler never receives the instruction “find callable Dog family members.”

# 13. `VariantFieldId` to Physical Payload Slot

Part 05.1 correctly publishes semantic field identity:

```text
VariantFieldId
```

The VM bytecode correctly uses physical payload layout:

```text
GetVariantPayload(u16)
```

The semantic-to-backend projection is responsible for the conversion.

Part 04 already defines:

```rust
VariantFieldLoweringSpec {
    id: VariantFieldId,
    slot: u16,
    ...
}
```

Part 05.2 must resolve each candidate-specific field projection against the declaration's lowering layout and publish the physical `u16` slot in `ExecutablePattern`.

The AST compiler must not infer a slot from:

```text
field source name
external label
AST argument position
selector text
```

If a `VariantFieldId` cannot be projected, compilation fails with an internal lowering-contract error.

# 14. Cross-Module Field Projection

A match may consume a variant declared in another module.

Therefore field-slot projection must use the global semantic snapshot / enum semantics, not only `ModuleLoweringSemantics.enums` belonging to the current compiling module.

The projection algorithm conceptually performs:

```text
ResolvedFieldPattern.field: VariantFieldId
    ↓
SemanticSnapshot.enum_semantics.variant_info(field.variant)
    ↓
declaration-order field layout
    ↓
u16 physical slot
```

or an equivalent lookup derived from Part-04 enum lowering structures.

Cross-module tests are required.

# 15. Executable Binding Table

An arm's visible bindings should be frozen into a compact binding table.

Recommended conceptual entry:

```rust
pub struct ExecutableBindingSpec {
    pub semantic: BindingId,
    pub name: Box<str>,
    pub range: SourceRange,
}
```

The executable pattern tree refers to entries through small local indices or stable references.

This is especially useful for or-patterns:

```phalcom
A(x) | B(x) => use(x)
```

Both alternatives stage into the same arm-level binding destination.

There must be one visible `x` in the arm body, not one compiler local per alternative.

# 16. Staged Binding Execution

Part 05.2 strengthens the existing “test then commit” pattern into:

```text
test + stage hidden binding values
    ↓
complete pattern/alternative succeeds
    ↓
commit hidden values to user-visible locals
```

This is the preferred execution architecture for all refutable patterns.

Why it is required:

1. failed nested tests cannot leak user bindings;
2. failed or-pattern alternatives cannot leak values;
3. selector/family candidates may project the same binding from different physical payload slots;
4. commit does not need to re-traverse/re-extract the source value;
5. candidate-specific extraction knowledge stays local to the successful test path.

Scratch-stage values are not semantically valid until the full pattern succeeds.

A failed alternative may leave stale hidden scratch content because no user-visible commit occurs; later alternatives overwrite all binding slots required by their success path.

---

# 17. Visible Binding Locals

The compiler should declare one visible local for every arm binding before compiling the arm body.

The binding table defines the authoritative set.

For:

```phalcom
A(x) | B(x) => use(x)
```

both alternatives stage into:

```text
$stage_x
```

and shared success commits:

```text
$stage_x -> visible x
```

5.1's binding-type join has no runtime representation. The runtime only stores the actual `Value` selected by the successful alternative.

---

# 18. Wildcard Lowering

`_` requires:

```text
no runtime predicate
no source binding
no staging slot
```

A wildcard payload need not be extracted.

For:

```phalcom
Result::Error(_, reason: _)
```

if neither payload is otherwise required by nested tests, code generation may omit both `GetVariantPayload` operations entirely after the case identity is established.

Wildcard semantics are static; the executable effect is absence of work.

---

# 19. Binding Pattern Lowering

An ordinary binding pattern is irrefutable over its expected position.

Its executable effect is:

```text
stage current value -> binding scratch
```

No runtime predicate is needed.

The binding is committed only when the containing full pattern succeeds.

---

# 20. Exact ADT Candidate Test

For one exact candidate:

```text
value_slot
    ↓
GetLocal(value_slot)
IsVariant(candidate_variant_index)
JumpIfFalse -> candidate failure
```

`candidate_variant_index` comes from:

```text
chunk.executable_semantics.add_variant_target(&candidate.variant)
```

No ordinary dispatch occurs.

No `.class` comparison occurs.

No `doesNotUnderstand` path occurs.

---

# 21. Payload Extraction

For an explicit candidate projection:

```text
GetLocal(candidate_value_slot)
GetVariantPayload(physical_slot)
```

If the child pattern requires further tests, store the payload into a hidden scratch value slot before recursively testing it.

If the child is only a binding, the compiler may stage directly into the binding scratch slot.

If the child is `_`, do not extract it.

---

# 22. Nested ADT Patterns

For:

```phalcom
Some(Ok(x))
```

general source-defined ADT execution is:

```text
IsVariant(Some)
GetVariantPayload(Some.value) -> $nested
IsVariant(Ok) on $nested
GetVariantPayload(Ok.value) -> $stage_x
complete success
commit x
```

The runtime never resolves the textual names `Some` or `Ok`.

# 23. Selector/Family Pattern Execution

Patterns such as:

```phalcom
Animal::Dog(...)
Animal::Dog(x, ..., named: age)
Animal::Dog*
```

have already been expanded by Part 05.1 to exact candidates.

Runtime lowering performs only candidate tests.

There is no:

```text
runtime SelectorPattern matching
runtime family capture
runtime associated-family invocation
runtime family member discovery
```

The existing first-class `AssociatedFamily` runtime object is unrelated to pattern-family execution.

# 24. Candidate-Specific Payload Layouts

A partial selector pattern may bind the same source names from different physical slots in different candidate variants.

Example conceptual family:

```text
Dog(_, named:)
Dog(_, _, named:)
Dog(_, mode:, named:)
```

Pattern:

```phalcom
Dog(x, ..., named: y)
```

may project:

```text
candidate 1: x <- slot 0, y <- slot 1
candidate 2: x <- slot 0, y <- slot 2
candidate 3: x <- slot 0, y <- slot 2
```

Each candidate stages into the same arm-level `$stage_x` / `$stage_y` locations.

This is why candidate-specific field projection is mandatory in the 5.1→5.2 handoff.

---

# 25. Or-Pattern Execution

Preserve or-pattern source alternative structure.

For:

```phalcom
A(x) | B(x) => branch(x)
```

lower conceptually as:

```text
try alternative A
    if complete success -> shared arm success

try alternative B
    if complete success -> shared arm success

all alternatives fail -> containing pattern failure

shared arm success:
    commit x
    execute branch
```

Do not flatten an arbitrary or-pattern into only a top-level `VariantId` set.

These two alternatives may share a top-level case but differ recursively:

```phalcom
Some(Ok(x)) | Some(Cached(x))
```

Preserving the alternative tree is required for correctness.

---

# 26. Or-Pattern Shared Prefixes

The initial implementation may repeat common tests.

For:

```phalcom
Some(Ok(x)) | Some(Cached(x))
```

it is acceptable initially to execute the `Some` test separately for each alternative.

Factoring the common `Some` prefix is a backend optimization, not required semantics.

The semantic/backend boundary must be correct before such optimization.

# 27. Structural Patterns

Tuple/list/record/map execution may continue to use current structural operations where those operations remain language-correct.

Examples include:

```text
Tuple/List class or shape tests
size tests
at(_)
map/record get

```

Part 05.2 does not require replacing every structural pattern primitive with new bytecodes.

However structural patterns must use the same staging/commit execution discipline and support the richer recursive nodes (`_`, `|`, nested ADTs).

# 28. Unified Executable Pattern Engine

The compiler should have one core recursive emitter conceptually equivalent to:

```text
emit_pattern(
    executable_pattern,
    current_value_slot,
    staging_frame,
    failure_continuation
)
```

The failure continuation differs by context:

```text
match arm      -> next arm
or alternative -> next alternative
if let         -> else path
while let      -> loop exit
required bind  -> pattern mismatch raise
for pattern    -> required per-item mismatch path
```

This shared emitter is the primary mechanism for eliminating semantic drift between pattern contexts.

# 29. Pattern Execution Frame

The compiler should introduce an explicit internal pattern execution frame rather than scattering scratch ranges across call sites.

Recommended conceptual state:

```rust
struct PatternExecutionFrame {
    value_slot: u16,
    binding_slots: Box<[u16]>,
    staging_slots: Box<[u16]>,
    temp_start: u16,
    ...
}
```

Exact shape may differ.

It must support:

```text
reserve visible binding locals
reserve hidden stage locals
reserve nested value temporaries
emit runtime cleanup on success path
emit equivalent cleanup on failure path
close captured visible bindings correctly
truncate compiler-local metadata exactly once after codegen
```

This is the most delicate compiler-lifetime portion of Part 05.2.

---

# 30. Scratch and Scope Discipline

Compiler locals are stack-backed. Runtime failure jumps can bypass code emitted on the success path.

Therefore Part 05.2 must deliberately separate:

```text
compile-time scope metadata mutation
runtime cleanup bytecode emitted on each control edge
```

The existing `compile_if_let` already manually emits scratch releases on both success and failure paths. Reuse that design principle in a generalized helper.

A failed arm must not leave live hidden locals at the next arm's entry.

A successful arm must close any captured user-visible pattern binding before its scope is left.

---

# 31. Match Expression Lowering

Recommended v1 lowering:

```text
begin match outer scope

reserve $match_scrutinee
evaluate scrutinee exactly once
store $match_scrutinee

reserve $match_result

for arm in source order:
    begin arm compile scope
    reserve visible bindings + staging
    emit arm pattern

    failure edge:
        runtime cleanup arm scratch
        continue to next arm

    success edge:
        commit bindings
        compile branch body/expression
        store result in $match_result
        clean arm runtime state
        jump match_join

exhaustive_fallthrough:
    MatchInvariantFailure

match_join:
    load $match_result
    release match scratch
end match outer scope
```

The exact scratch arrangement may avoid a result slot in provably safe cases, but a single hidden result local is the required-correctness baseline.

---

# 32. Scrutinee Exactly Once

This is a hard execution rule.

For:

```phalcom
match nextEvent() {
    Event::Started => ...
    Event::Stopped => ...
}
```

`nextEvent()` executes exactly once.

All candidate tests and payload projections operate on the stored value.

This rule applies even when:

```text
there are many arms
one arm expands to many selector-family candidates
or-pattern alternatives repeat candidate prefixes
nested payloads are extracted
```

---

# 33. Arm Source Order

Arms execute in source order.

Part 05.1 has already rejected useless/redundant arms, but source order remains an observable control-flow property for patterns whose runtime tests may involve structural operations.

The compiler must not reorder source arms merely because variant identities could be sorted differently.

---

# 34. Candidate Order

For exact candidates generated from one family/selector pattern, Part 05.2 should preserve the deterministic candidate order published by Part 05.1.

Exact ADT candidate tests are pure and mutually exclusive, so several orders could be semantically equivalent. Preserving semantic order nevertheless gives:

```text
deterministic bytecode
deterministic disassembly
stable tests
future optimization reproducibility
```

Do not rebuild candidate order from an unordered map.

---

# 35. Match Result Value

Every normally completing match expression leaves exactly one result value.

A hidden `$match_result` local is the v1 baseline.

Each normally completing branch stores its branch value into this slot and jumps to one join point.

The join point loads the result once.

If the surrounding statement discards the match value, ordinary compiler pop behavior may discard it after expression lowering. Match remains a value-producing expression.

---

# 36. Abrupt Branches

A branch may contain abrupt control such as:

```text
return
throw
break / continue where lexically valid
```

Part 05.1 already excludes non-normally-completing arms from static result joining.

Part 05.2 compiles abrupt control using the existing enclosing compiler context.

A braced arm is inline specifically so `return` targets the enclosing callable rather than a synthetic closure frame.

No artificial match-specific exception/control object is introduced.

---

# 37. Internal Exhaustive-Fallthrough Trap

Even though Part 05.1 proves totality, initial code generation should retain candidate tests for every source arm and an explicit internal fallthrough endpoint.

Recommended bytecode:

```rust
Bytecode::MatchInvariantFailure
```

or an equivalent clearly internal compiler/runtime trap if the repository introduces a common invariant opcode before implementation.

VM behavior:

```text
raise RuntimeError::Internal(
    "statically exhaustive match reached runtime fallthrough"
)
```

This is not a language-level `MatchError`.

It exists to expose semantic/runtime representation bugs during development.

A later backend optimization may prove the final branch safe to emit without a test, but that is outside initial Part 05.2.

# 38. No Runtime GADT Solver

For:

```phalcom
enum Expr<T> {
    @variant Int(_ value: Int) -> Expr<Int>
    @variant Bool(_ value: Bool) -> Expr<Bool>
}
```

execution of:

```phalcom
match expr {
    Expr::Int(x) => ...
    Expr::Bool(x) => ...
}
```

uses only:

```text
IsVariant(Int)
GetVariantPayload(...)
IsVariant(Bool)
GetVariantPayload(...)
```

There is no runtime:

```text
T lookup
Int/Bool type-object comparison
GADT equality check
case proof allocation
generic specialization object
```

The theorem has already been proved statically.

# 39. Generic ADT Erasure

The bytecode VM continues to erase generic specialization in physical ADT case representation.

`VariantId` identifies the declaration case, not one runtime case descriptor per generic application.

The same executable pattern test handles values whose static types may be different specializations when the checker has proven the candidate reachable.

# 40. `if let` Migration

Part 05.2 must migrate `compile_if_let` to the shared executable pattern engine.

Retain existing control semantics:

```text
RHS exactly once
success bindings only in then scope
failure cannot see bindings
then body inline
else body inline
one expression result
```

Change only pattern authority/execution:

```text
legacy Pattern AST interpretation
    ↓ remove
formal semantic pattern resolution
    ↓
ExecutablePattern
    ↓
shared staged emitter
```

`if let` remains refutable control flow, not a statically total match.

---

# 41. `while let` Migration

Part 05.2 must migrate `compile_while_let` similarly.

Retain:

```text
RHS exactly once per iteration
failure exits loop
success commits current iteration bindings
loop body executes inline
break / continue behavior
captured binding close semantics
```

A failed iteration must not expose partial values from a candidate that failed after some nested tests.

# 42. Required Pattern Contexts

The existing pattern compiler is also used by required/destructuring contexts such as local bindings and loop bindings.

Part 05.2 should converge these contexts on the same executable pattern emitter where the source grammar permits the same pattern forms.

The semantic pattern is shared; only failure behavior differs.

```text
        ↓

```

```text

```

and keeps Part 05.2 on one case-test bytecode path.
