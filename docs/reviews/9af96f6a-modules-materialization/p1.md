# Release-blocking findings

## 1. High — Imported binding/local declaration collision creates two different meanings for one name

This is the nastiest semantic bug I found.

`InterfaceBuilder` maintains imported names separately in `local_import_bindings`; it catches import/import collisions. Body declarations are subsequently accumulated into `declarations`, but there is no cross-check between a declaration and an existing import binding.

The linker then independently puts both namespaces into the binding layout:

- declarations → `local_globals`
- imports → `imports`

Again, no cross-namespace collision check.

That alone would be bad enough. The compiler and exporter then resolve the ambiguity differently.

Compiler bare-name resolution is:

```text
local
→ upvalue
→ linked import
→ global
→ implicit self
```

so the imported name wins over a module global.

But `resolve_export()` does the opposite: for `export x`, it checks `interface.declarations` before `import_symbols`. Therefore the declaration wins.

So this source can acquire contradictory semantics:

```phalcom
from .a import value

let value = 2

value        # resolves to imported a.value
export value # resolves to this module's global value
```

The same lexical name means one binding inside the module and another binding to consumers.

This is not merely confusing shadowing. It violates the fundamental “one statically resolved binding identity per reference” property that the rest of this design is trying to establish.

### Fix

Reject the collision during interface construction, before the linker ever sees it.

Conceptually, build a single module-scope declaration namespace:

```rust
enum ModuleLocalOrigin {
    Declaration(SourceRange),
    Import(SourceRange),
}
```

Every import binding and every top-level declaration claims a name from that one table. A second claimant is an error.

Do not fix this by deciding “imports win” or “locals win.” With a static preamble, silent shadowing is the wrong rule. Make it illegal.

Add fixtures for both ordering-independent forms even though imports syntactically precede body declarations.

## 2. High — Whole-module exports are specified, represented at runtime, but impossible to link

This is a particularly revealing half-implementation.

The parser/interface layer accepts:

```phalcom
import foo.bar as bar
export bar
```

because a whole-module import contributes to `local_import_bindings`, and `export` accepts either declarations or imported bindings.

The runtime is also explicitly prepared for it:

```rust
pub enum RuntimeExportRef {
    Binding(BindingRef),
    Module(ObjRef),
}
```

and the Part III design explicitly specifies whole-module exports.

But the linker canonicalizes every `LinkedExport` to:

```rust
LinkedExport {
    symbol: SymbolId,
    ...
}
```

There is no module-valued export target. Whole-module imports deliberately enter `import_symbols` with `None`, while selective imports receive `Some(SymbolId)`. Later, `resolve_export()` can only resolve a declaration or an imported `SymbolId`; a module import therefore falls into `MissingBinding`.

The correct model is not difficult. `LinkedExport` itself needs to distinguish value bindings from module objects:

```rust
pub enum LinkedExportTarget {
    Binding(SymbolId),
    Module(ModuleId),
}

pub struct LinkedExport {
    pub public_name: Box<str>,
    pub target: LinkedExportTarget,
    pub range: SourceRange,
}
```

Then materialization maps them naturally to the already-existing `RuntimeExportRef`.

This should not remain as an exception encoded through `Option<SymbolId>`. The type system is telling you that there are actually two kinds of export.

## 3. High — Re-running a `CompiledProgram` destroys sticky module state

The runtime lifecycle design is sound on paper:

```text
Prepared
Initializing
Initialized
Failed
```

with `ModuleFailure` retained by `ModuleRegistry`.

But `VM::run_compiled()` always begins with:

```rust
self.materialize_program(program)?;
```



And `materialize_program()` allocates a new object for every module and then calls:

```rust
self.module_registry.insert(id.clone(), ModuleRecord::prepared(obj_ref));
```

for every identity.

`ModuleRegistry::insert()` is plain `HashMap::insert`, replacing an existing record without complaint.

Consequently:

```text
run_compiled(program)
    B fails
    B = Failed

run_compiled(program) again
    materialize_program()
    B replaced with a brand-new Prepared record
    B initializer executes again
```

That contradicts the explicit sticky-failure rationale in the runtime specification, which mentions “repeated entry attempts in one VM” as one of the reasons the state exists.

It also undermines canonical runtime module identity. One semantic `ModuleId` should correspond to one module object within a runtime program/session.

### Fix

There are two legitimate models; choose explicitly.

For the current design I recommend:

```rust
materialize_program(program):
    if registry contains ModuleId:
        verify it belongs to the same RuntimeProgram
        reuse it
    else:
        allocate
```

Better still, introduce an explicit `RuntimeProgram` object as the specification originally suggested and make lifecycle ownership obvious.

`ModuleRegistry::insert()` should not silently replace a module. Give it something like:

```rust
register_new(...) -> Result<(), DuplicateModuleIdentity>
```

If you want a fresh execution universe, create a fresh VM/session or expose an explicit reset operation. Do not make ordinary execution implicitly reset sticky state.

## 4. High — Project/package CLI execution is currently unreachable

This one is straightforward.

`cmd_run()` does this before entry classification:

```rust
let source = match read_source(cli.path.clone(), cli.source.clone()) {
    ...
};
```

Only later does it canonicalize the path and distinguish:

```rust
if canonical.is_dir() {
    if canonical.join("project.toml").is_file() {
        EntrySelection::Project(canonical)
    } else {
        EntrySelection::Package(canonical)
    }
}
```



But `read_source()` is:

```rust
(Some(p), None) => fs::read_to_string(&p)
```



So:

```console
phalcom ./my-project
```

attempts `read_to_string("./my-project")` and exits with the I/O path before `EntrySelection::Project` can be constructed.

The project/package classification code exists but directory entry cannot reach it.

### Fix

Classify first.

Something like:

```rust
let selection = classify_entry(cli.path.as_deref(), cli.source.as_deref())?;
```

Only inline source should be read directly by this CLI layer. `ProgramCompiler` should own file/project/package source acquisition.

This also removes the strange duplication where the CLI reads a module file once and `ProgramCompiler` then reads it again through `FilesystemSourceProvider`.

Add actual executable CLI tests for:

```text
phalcom project-dir/
phalcom package-dir/
phalcom module.ph
phalcom --source ...
```

The project-directory case would have caught this immediately.

## 5. High — The LSP’s authoritative module resolver is implemented but not integrated into the normal analysis path

This is the largest architecture gap outside runtime.

The new LSP seam is directionally correct. `DocumentModuleMap` explicitly distinguishes document URI identity from semantic `phalcom_modules::ModuleId`.

And `SharedModuleResolver` correctly wraps the compiler's real `phalcom_modules::ModuleResolver`.

There is even:

```rust
ModuleGraph::update_with_shared_resolver(...)
```

which uses it.

But repository search finds no production caller of that method. The normal `SemanticEngine` still does:

```rust
self.state.documents.ensure_lsp_for_uri(uri);
...
self.state.graph.update(...)
```



And that `ModuleGraph::update()` still uses its own old physical URI/path inference. The source contains the admission directly:

```rust
// TODO(module-path-common): extract this VM-free normalization ...
```

and more importantly:

```rust
if dot_count == 0 {
    // Absolute logical roots need ProjectUniverse context.
    // ...
    return Vec::new();
}
```



Therefore the compiler and LSP still do not have one module-resolution truth.

An absolute project import or dependency alias can successfully resolve in the compiler while the ordinary LSP graph fails to connect the edge at all.

That affects much more than diagnostics. It contaminates:

- dependent invalidation;
- provider repair;
- navigation;
- completion provenance;
- cross-module semantic analysis;
- future type propagation.

This is exactly the kind of split-brain module implementation the shared `phalcom-modules` crate was supposed to eliminate.

### Fix

Do not teach `SemanticEngine` filesystem/project resolution itself.

The ingestion worker should produce something like:

```rust
ResolvedDocument {
    uri,
    semantic_module_id,
    parsed_program,
    resolved_import_edges,
}
```

using `ProjectUniverse + ModuleResolver`.

Then the semantic engine consumes resolved identities only.

Keep URI heuristic resolution exclusively for genuinely standalone unsaved/unprojected documents, explicitly marked as such.

Once this lands, delete as much duplicate `import_candidates()` normalization as possible.

## 6. High — Export invocation discards Phalcom selector shape

The export-first dispatch rule itself is correct. `send_dynamic()` tries module exports before ordinary `Module` methods, which is exactly what you wanted to allow exports named `name`, `class`, `inspect`, etc.

The implementation below that point, however, collapses Phalcom's selector semantics.

Both export dispatch functions decode:

```rust
let (name, _labels, _kind) = decode_selector(...)
```

and immediately throw away `labels` and `kind`.

For a binding export:

```rust
if arity == 0 {
    return value;
} else {
    synthesize call(_, _, ...)
}
```

That conflates:

```phalcom
module.foo    # getter
module.foo()  # zero-argument method invocation
```

even though Phalcom deliberately has distinct `SignatureKind::Getter` and `SignatureKind::Method(0)`.

For arguments, it synthesizes:

```rust
vec![None; arity]
```

which converts every call to positional arguments. A call such as conceptually:

```phalcom
module.render format: "json"
```

cannot preserve its label shape when forwarded to the exported callable.

And `RuntimeExportRef::Module(target)` simply returns the target module regardless of `arity`, which will become observably wrong as soon as the currently-broken module-export linker is fixed.

### Fix

Export lookup should consume the whole decoded selector shape:

```text
Getter
    → read export

Method(shape)
    → read export
    → invoke exported value's call with identical positional/labeled shape

Setter / subscript
    → explicitly define or reject according to module export semantics
```

Never reduce a selector to `(base name, total arity)` at this boundary.

This needs selector-shape tests, not just “sending Config returns an object.”

# Important incompleteness

## 7. `EntrySelection::ModuleId` is broken as a standalone entry API

`compile_entry_selection(EntrySelection::ModuleId(id))` constructs:

```rust
let universe = Arc::new(ProjectUniverse::new());
...
discover_and_link(universe, ..., entry_id)
```



But `ProjectUniverse::new()` contains no projects, while `ModuleResolver::load_interface()` immediately requires:

```rust
universe.get_project(module_id.project)
```



So an ordinary semantic `ModuleId` cannot be discovered from this arm.

The separate API:

```rust
ProgramCompiler::new(linked)
    .compile_entry(EntrySelection::ModuleId(...))
```

makes sense because that compiler owns a linked universe. The standalone variant does not.

I would remove `ModuleId` from `compile_entry_selection()` rather than invent missing context.

## 8. `CompiledProgram` and `ModuleArtifact` are still mostly names for a future architecture

This deserves attention because it makes the implementation look further along than it is.

`compile_module()` does:

```rust
let artifact = ModuleArtifact::empty(module);
```

for every linked module.

So the artifact has:

- no global declaration blueprints;
- no class blueprints;
- no initializer.

Materialization acknowledges this directly:

```rust
// Phase 2: Global layouts are populated dynamically by top-level execution.
```

and the class blueprint arm is currently:

```rust
RuntimeDeclarationBlueprint::Class(_class_bp) => {}
```



Then `run_compiled()` compiles each retained source string into bytecode after runtime materialization.

That is materially different from the Part III model:

```text
compile closed program
→ reserve static layouts
→ materialize declaration blueprints
→ install already-compiled initializer artifacts
→ initialize
```

The current model is closer to:

```text
discover + parse interfaces + link
→ allocate runtime module objects
→ create slots demanded by cross-module bindings
→ compile all source into this VM
→ execute
```

That may be an entirely valid implementation strategy for a VM whose bytecode constants contain heap handles.

But then the abstractions should tell the truth.

Either finish `ModuleArtifact`, or rename the phase boundaries so that `CompiledProgram` does not imply a VM-independent executable artifact that does not actually exist.

---

## 9. `ModuleArtifact` claims VM independence while storing `ObjRef`

The file literally describes itself as:

> “VM-independent compiled module metadata.”

Yet:

```rust
pub initializer: Option<ObjRef>
```

is a VM heap handle.

Those concepts cannot coexist cleanly.

Currently the field remains `None` through `ProgramCompiler`, which is why this has not caused trouble.

Long term choose one:

- artifact is VM-independent → store bytecode/IR/closure blueprint, never `ObjRef`;
- artifact is materialized runtime state → move it under `RuntimeProgram` and permit heap handles.

I strongly prefer the former because it makes caching, incremental compilation, tooling and eventually native/AOT compilation much cleaner.

---

## 10. Static module metadata never reaches `ModuleObject`

`LinkedModuleInterface` correctly retains `ModuleMetadata`.

But `ModuleObject` contains no metadata field at all.

The runtime specification explicitly called for immutable metadata retention on module/package objects.

On the positive side, you did correctly remove ordinary runtime attribute attachment from modules: `_$attach`, `_$attributes`, and `_$freezeAttributes` now accept only classes/methods.

So the separation principle is right; the immutable metadata storage half is simply unfinished.

There is also a stale documentation comment in `primitive/attribute.rs` that still says module objects participate in the three-receiver attribute mechanism even though the implementation no longer does.

# Runtime initialization quality

The initialization machinery has good ingredients but is more complicated than necessary.

`CompiledProgram` already supplies a dependency-first topological order. `initialize_program()` iterates that order. Good.

But `initialize_single_module()` then recursively initializes `Prepared` dependencies anyway.

You therefore have both:

```text
topological iteration
```

and:

```text
recursive dependency traversal
```

performing the same scheduling job.

Pick one.

Given your static DAG design, topological iteration is superior:

```rust
for id in initialization_order {
    assert all runtime_dependencies are Initialized;
    initialize_exactly_this_module(id);
}
```

Then `Initializing` means genuine invariant corruption/re-entry rather than part of a recursive traversal.

There is also an error-discipline issue here. After recursively initializing a dependency:

```rust
if initialize_single_module(...).is_err() {
    let dep_failure = dep_record.failure.clone()
        .expect("failed dependency has failure recorded");
}
```

An internal invariant error can return `Err` without transitioning that dependency to `Failed`. The subsequent `expect()` can therefore panic.

The runtime specification specifically called for malformed synthetic `CompiledProgram` tests to exercise impossible runtime ordering. Those cases should produce `InternalModuleOrderViolation`, not panic.

The `chain` argument is also effectively vestigial: it is passed around and pushed/popped, but `build_initialization_error()` ignores its `_chain` argument and reconstructs the chain from nested `ModuleFailure`.

That is a useful signal to simplify this subsystem now.

# LSP identity code has a smaller structural smell

`DocumentModuleMap` is a sensible transitional seam, but it currently maintains:

```text
URI → SemanticModuleId
SemanticModuleId → URI
URI → legacy LSP ModuleId
```

without enforcing bijection updates.

If an existing URI is remapped to another semantic module identity, the previous `by_module` entry is not removed. Likewise, remapping a semantic identity to another URI can leave the old URI mapping behind.

Also:

```rust
semantic_for_lsp()
uri_for_lsp()
```

perform linear scans over `lsp_by_uri`.

Neither is catastrophic today, but this type is becoming foundational. Make it a proper invariant-owning bidirectional map before project moves/renames and workspace changes start hammering it.

More fundamentally, once the LSP finishes migrating, the local:

```rust
struct ModuleId(String)
```

should disappear from semantic internals. Semantic entities should ultimately be keyed by `phalcom_modules::ModuleId`; URIs belong at the document/UI boundary.

# What is particularly good

There is a lot here worth preserving.

### The graph model is excellent

`ReferenceGraph`, `SemanticGraph`, and `RuntimeDependencyGraph` are explicitly different types rather than one generic “dependency graph.”

That is exactly right.

It leaves room for:

```text
reference cycle     possibly legal
semantic/type SCC   possibly legal and fixed-point analyzed
runtime init cycle  illegal
```

without later having to untangle one graph whose edges accidentally acquired several meanings.

The iterative Kosaraju SCC implementation is also a good choice: deterministic, no recursive stack hazard, and reusable for future type/protocol dependency analysis.

The deterministic dependency-first topological order using ordered collections is also clean. You correctly achieve reproducibility without semantically promising sibling ordering.

### Semantic identity moved to the correct layer

The use of:

```rust
ModuleId {
    project: ResolvedProjectId,
    path: ModulePath,
}
```

instead of physical path strings is an important architectural win.

This is the foundation that makes:

- symlink/path spelling irrelevant to identity;
- dependency aliases separate from target identity;
- LSP/compiler/runtime agreement possible;
- future package providers feasible.

### Filesystem resolution has good defensive semantics

`FilesystemSourceProvider` explicitly handles:

- kebab/snake ambiguity;
- module-file versus package-directory ambiguity;
- nested project boundaries;
- canonical confinement under source root.



Those are exactly the boring edge cases that become irreversible DX problems if a language silently guesses.

### Live imported bindings are implemented the right way

`BindingRef { module, slot }` and indexed `GetLinked` are much better than copied imported values.

That gives re-exports and selective imports canonical live-cell semantics without runtime path resolution.

The focused compiler test also verifies that a linked import lowers to `GetLinked` and does not fall back to `GetGlobal`.

This abstraction should stay.

### GC treatment is very strong

Both VM root enumeration and heap outgoing-edge tracing follow exhaustive patterns.

`ModuleRegistry` and runtime roots are explicitly rooted, while a `ModuleObject` traces:

- closure;
- globals;
- binding-export target modules;
- module exports;
- linked binding/module reads.



This is stronger than the walkthrough claim because the implementation makes the invariants mechanically hard to forget.

The comment in `trace.rs` acknowledging that exhaustive enum matching does not protect newly added fields is also excellent engineering documentation.

### Export namespace versus internal globals is conceptually correct

The runtime has a separate `exports` table rather than exposing `name_to_slot`.

That preserves private-by-default module globals.

Likewise, checking exports before ordinary Module methods is exactly the right decision for avoiding future namespace capture by kernel API growth.

Those are good long-term language decisions.

# Test coverage review

This is where the “100% tests passed” statement can be misleading.

A green workspace tells you the existing expectations agree with the implementation. It does not tell you the modules implementation is well specified.

The dedicated core runtime file currently has five tests.

They cover:

- diamond project runs without error;
- a failure becomes a `ModuleInitializationError`;
- inline import rejection;
- one exported object can be fetched;
- `core_new.ph` runs.

The dedicated linked-compiler tests add two very useful cases:

- linked import emits `GetLinked`;
- linked import is immutable.



The problem is that most tests establish only “does not error,” not the semantic invariants that matter.

For example, the diamond test does not verify exact initialization ordering or one-time initialization. The sticky-failure test calls `initialize_single_module()` again directly, which preserves the existing registry and therefore completely misses the `run_compiled()` rematerialization bug.

I would add these before calling Modules v1 finished:

1. `import/local` same-name rejection.
2. Whole-module import exported as a module object.
3. Multi-hop re-export retains one canonical binding cell.
4. Getter export versus zero-argument callable export.
5. Exported callable with labeled arguments preserves exact selector shape.
6. Export name colliding with `Module` methods (`name`, `class`, `hash`, `inspect`).
7. Private module global cannot be reached through external send.
8. Re-running a successfully initialized program does not rerun initializers.
9. Re-running a failed program preserves the original sticky failure.
10. Synthetic invalid initialization order returns invariant error without panic.
11. Three-hop dependency failure preserves the full provenance chain.
12. GC forced after materialization keeps linked reads and re-export targets alive.
13. Package runtime value has `Package < Module`.
14. Importing a deep leaf does not implicitly initialize ancestor `package.ph`.
15. Project-directory CLI invocation.
16. Package-directory CLI invocation.
17. `EntrySelection::ModuleId` behavior.
18. Absolute project-root import LSP edge.
19. Dependency-alias import LSP edge.
20. File rename/remap repairs `DocumentModuleMap` without stale reverse entries.

I would also make the diamond fixture assert observable initialization effects, not merely `res.is_ok()`.

# Code-smell assessment

The code is not generally messy. Most smells come from transitional architecture that was left in place after the feature was declared complete.

The recurring smell is **duplicate authority**:

```text
declarations namespace + import namespace
topological initializer + recursive initializer
semantic ModuleId + URI ModuleId
shared ModuleResolver + LSP heuristic resolver
ModuleArtifact initializer + ModuleObject initializer
CompiledProgram + runtime compilation
```

Each duplication independently seems reasonable during migration. Collectively, they are exactly where the bugs are appearing.

The next cleanup should therefore not be a generic refactor. It should enforce a rule:

> For every module-system fact, identify exactly one authoritative representation and make every downstream representation a derived/indexed form.

Concretely:

```text
Module identity       → phalcom_modules::ModuleId
Local binding name    → one interface namespace table
Import resolution     → ModuleResolver
Canonical export      → LinkedExportTarget
Dependency semantics  → ModuleGraphs
Initialization plan   → initialization_order
Runtime identity      → ModuleRegistry
Runtime public API    → export table
Document location     → DocumentModuleMap boundary only
```

That would eliminate most of the identified defects at the architectural level rather than patching them one at a time.

# Recommended repair order

I would not undertake a broad rewrite. The architecture is good enough that a fairly surgical stabilization pass should work.

**P0 / before declaring v1 complete:** fix the CLI directory-entry bug; unify import/declaration namespace collision checking; introduce `LinkedExportTarget::{Binding, Module}`; preserve exact selector shape in export dispatch; make materialization idempotent/canonical so sticky state survives repeated runs; route project-backed LSP graph construction through the actual module resolver.

**P1 / immediately afterward:** eliminate recursive initialization in favor of the precomputed DAG order; finish or deliberately remove declaration/class-blueprint scaffolding; decide whether `CompiledProgram` is genuinely compiled or a linked source program and rename/refactor accordingly; retain `ModuleMetadata` on runtime modules; fix/remove the standalone `EntrySelection::ModuleId` API.

**P2 / quality hardening:** collapse legacy LSP `ModuleId`; make `DocumentModuleMap` enforce bidirectional consistency; encapsulate registry state transitions instead of exposing mutable records; replace impossible-path `unwrap`/`expect` in module initialization with typed invariant errors; clean stale module-attribute documentation.

The most important conclusion is that I **would not rethink the modules architecture**. The decision to use static declarations, semantic identities, separate graph layers, closed linking, indexed live bindings, a runtime registry and a distinct export namespace was good.

What needs work is the final 15–20% where transitional seams are still competing with those abstractions. That last portion is exactly where language module systems tend to accumulate permanent irregularities, so I would fix these now rather than preserve them as “v1 behavior.”
