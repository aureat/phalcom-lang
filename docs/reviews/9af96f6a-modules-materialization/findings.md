# Findings

## P1 — Directory project/package entries fail before module selection

The new CLI branch correctly classifies a directory as either `EntrySelection::Project` or `EntrySelection::Package` at [`phalcom-core/bin/phalcom/cli.rs:194-203`](../../../phalcom-core/bin/phalcom/cli.rs:194), but `cmd_run` calls `read_source(cli.path.clone(), cli.source.clone())` at line 178 before reaching that branch. `read_source` treats every path as a file and calls `fs::read_to_string` at [`phalcom-core/bin/phalcom/cli.rs:373-376`](../../../phalcom-core/bin/phalcom/cli.rs:373). Consequently, passing a project or package directory never reaches `ProgramCompiler::compile_entry_selection`; it exits with the file-read error for the directory. This is a direct regression in the newly introduced project/package entry workflow, not a malformed-input case: the same `diamond_app` directory is accepted by the module integration test when passed directly as `EntrySelection::Project`.

The failure is reproducible with the built binary:

```text
$ target/debug/phalcom phalcom-core/tests/fixtures/modules_v1/diamond_app
Error: Failed to read file phalcom-core/tests/fixtures/modules_v1/diamond_app
exit 74
```

The fix should make source loading lazy: inline input should become `EntrySelection::Inline`, a regular file should be read only when diagnostics need its text, and a directory should go directly to `EntrySelection::Project` or `EntrySelection::Package`. The error-rendering path must still preserve source text for parse diagnostics after compilation has selected a file entry. Add CLI integration coverage for both a `project.toml` directory and a `package.ph`/`main.ph` directory; the existing runtime fixture test does not exercise the CLI boundary.

## P1 — Whole-module re-exports cannot be linked

The runtime model adds [`RuntimeExportRef::Module`](../../../phalcom-core/src/heap/module.rs:25) and dispatch branches for it, but the new materializer converts every `LinkedExport` into `RuntimeExportRef::Binding` at [`phalcom-core/src/modules/materialize.rs:89-108`](../../../phalcom-core/src/modules/materialize.rs:89). More importantly, the current linker representation cannot produce the required module export in the first place. A whole-module import is recorded by [`phalcom-modules/src/linker.rs:341-375`](../../../phalcom-modules/src/linker.rs:341) with `LinkedReadSpec::Module(target)` and `import_symbols[(module, local)] = None`; the interface builder permits `export m` because `m` is a local import binding at [`phalcom-modules/src/interface.rs:99-131`](../../../phalcom-modules/src/interface.rs:99). During `resolve_export`, however, the local-export branch accepts only a declaration or `Some(Some(symbol))` at [`phalcom-modules/src/linker.rs:518-536`](../../../phalcom-modules/src/linker.rs:518), so the `Some(None)` entry for `m` becomes `LinkError::MissingBinding`.

This contradicts the runtime contract in [`phalcom-modules-v1-part-3-runtime-initialization-execution.md:341-353`](../../work/pending/modules/phalcom-modules-v1-part-3-runtime-initialization-execution.md:341), which requires `import M as m; export m` to materialize as `RuntimeExportRef::Module(target module ObjRef)`. The result is a missing language feature at the linker boundary and a dead runtime enum branch: module objects can be imported for reads, but cannot be publicly re-exported through the documented surface. The implementation needs an explicit linked-export target kind (or equivalent module-target metadata) so the linker preserves `Module(target)` through `LinkedModuleInterface`, and the materializer must map that target to the registered module object. Add an integration fixture that imports a child module under an alias, exports the alias, and verifies both getter access and downstream chained access.

## P1 — Invalid runtime cycles panic during dependency-failure propagation

`initialize_single_module` detects a dependency in `ModuleState::Initializing` and returns an internal `InternalModuleOrderViolation` error at [`phalcom-core/src/modules/initialize.rs:47-51`](../../../phalcom-core/src/modules/initialize.rs:47). When that error is returned from the recursive call made for a `Prepared` dependency, the caller immediately reads the dependency record's failure with `.expect("failed dependency has failure recorded")` at [`phalcom-core/src/modules/initialize.rs:53-60`](../../../phalcom-core/src/modules/initialize.rs:53). The recursive cycle path leaves that dependency in `Initializing`; it has no `ModuleFailure`, so the invariant error is replaced by a Rust panic. The same state mismatch exists in the `Failed` propagation assumptions at lines 67-72, although the cycle path reaches the first `expect`.

This is reachable by constructing the invalid synthetic `CompiledProgram` explicitly called out by the runtime specification, not by a legal source graph: [`phalcom-modules-v1-part-3-runtime-initialization-execution.md:731-745`](../../work/pending/modules/phalcom-modules-v1-part-3-runtime-initialization-execution.md:731) requires an internal invariant error, with a test that constructs an invalid program. The implementation should propagate the original error when recursive initialization returns while the dependency remains `Initializing`, or classify that state as an invariant failure without reading `failure`. Add a synthetic two-node runtime dependency cycle test and assert an error, no panic, and no partial module exposure.

## P2 — `EntrySelection::ModuleId` discovers against an empty universe

The new static entry API documents `EntrySelection::ModuleId` as “Compile an already linked module ID,” but its implementation creates a fresh empty `ProjectUniverse` and a filesystem provider before calling `discover_and_link` at [`phalcom-core/src/modules/compile.rs:106-113`](../../../phalcom-core/src/modules/compile.rs:106). A `ModuleId` contains only a resolved project identity and logical path; it does not carry the project manifest or source root needed to populate that new universe. For any project-backed ID, discovery therefore has no loaded project to resolve and read. The linked-program-aware constructor already stores an `Arc<LinkedProgram>` in `ProgramCompiler`, but the static branch does not use that context.

This makes the public selection variant fail for the very identity form it claims to accept, while the CLI and fixtures avoid the branch by selecting paths. The API should either remove `ModuleId` from the context-free static function, require a linked plan/universe as an argument, or route `ModuleId` through `ProgramCompiler::new(linked).compile_entry` with source-backed compilation data. Add a test using a loaded fixture project and its real `ModuleId` that compiles and executes through the selected API, plus a negative test that distinguishes missing entry from missing project context.

## P2 — Static module-export calls bypass rest-family dispatch

The compiler-emitted send path calls `try_module_export_send` from [`phalcom-core/src/vm/dispatch.rs:978`](../../../phalcom-core/src/vm/dispatch.rs:978). For an exported callable and nonzero arity, the new implementation constructs a `call(...)` selector, performs exact `lookup_method`, and invokes `call_method_with_selector_as` directly at [`phalcom-core/src/vm/send.rs:1217-1225`](../../../phalcom-core/src/vm/send.rs:1217). It never performs the ordinary rest-family lookup/activation sequence. The normal send path explicitly checks a cached method's rest layout and otherwise calls `lookup_rest_method` followed by `activate_rest_method` at [`phalcom-core/src/vm/dispatch.rs:982-1027`](../../../phalcom-core/src/vm/dispatch.rs:982). The dynamic module-export path does use `send_dynamic`, which includes that rest fallback, at [`phalcom-core/src/vm/send.rs:1259-1264`](../../../phalcom-core/src/vm/send.rs:1259).

Therefore the same exported callable can accept a variable-arity call through `VM::send_dynamic` but miss or report `doesNotUnderstand` when the compiler emits the ordinary static send. This is a dispatch-semantics divergence introduced with module export interception. Reuse the shared shape/rest dispatch helper for the exported value, preserving caller authority and source range, and add a fixture with an exported rest callable invoked once through compiled syntax and once through `send_dynamic`; both calls must capture identical positional and labeled arguments.

## P2 — Module-object export references ignore incoming arguments

Both new `RuntimeExportRef::Module` branches return the target module object without inspecting the call shape: the static path truncates the stack and pushes the module at [`phalcom-core/src/vm/send.rs:1198-1203`](../../../phalcom-core/src/vm/send.rs:1198), while the dynamic path returns `Some(Value::Obj(target_mod))` at [`phalcom-core/src/vm/send.rs:1249-1250`](../../../phalcom-core/src/vm/send.rs:1249). The specification requires an export send with arguments to read the exported value and invoke its normal `call(...)` protocol at [`phalcom-modules-v1-part-3-runtime-initialization-execution.md:413-423`](../../work/pending/modules/phalcom-modules-v1-part-3-runtime-initialization-execution.md:413). A module-object export with arguments would therefore silently discard arguments and return a module object rather than applying the specified call behavior. This branch is currently blocked by the P1 linker/materialization defect, but it is still an incorrect implementation of the newly added runtime variant and will become user-visible as soon as module re-exports are wired.

The dispatch code should distinguish getter-shaped sends from argument-bearing sends before returning a module object, then route the latter through the same callable protocol used for all exported values, or produce the specified ordinary miss/error if module objects are not callable. Add a direct runtime test that installs a `RuntimeExportRef::Module`, sends zero and nonzero arity selectors through both static and dynamic paths, and asserts that arguments are not discarded.

## P2 — `Interpreter::run_entry` erases structured compile errors

The new high-level interpreter method maps every `ProgramCompileError` into `PhError::StringError(e.to_string())` at [`phalcom-core/src/interpret.rs:54-57`](../../../phalcom-core/src/interpret.rs:54). The compiler facade has deliberately separated variants for link, project, resolution, source, missing entry, package/project executability, and context-free REPL import errors at [`phalcom-core/src/modules/compile.rs:63-93`](../../../phalcom-core/src/modules/compile.rs:63). Converting those variants to an untyped string prevents callers from selecting the correct exit class, rendering source-aware diagnostics, or matching recovery behavior. It also makes the new public API less informative than the underlying compiler API.

Preserve the structured error by adding an appropriate `PhError` variant/conversion or return `Result<(), ProgramCompileError>` from a compile-facing method and convert only at the CLI boundary. Add tests that call the interpreter with a missing project entry, an unresolved import, and a context-free inline import, asserting that the error category remains distinguishable.
