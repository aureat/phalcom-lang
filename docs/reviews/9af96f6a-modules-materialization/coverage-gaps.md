# Coverage gaps and residual risks

The new runtime integration tests establish a useful happy-path diamond and sticky-failure baseline, but their assertions are weaker than the invariants the implementation claims to provide. [`phalcom-core/tests/modules_runtime.rs:15-16`](../../../phalcom-core/tests/modules_runtime.rs:15) checks only that the module count and initialization order are at least four, so a missing module or extra unintended module can pass. The export test at lines 74-83 checks only that `Config` returns some object; it does not assert the exported object identity, its value, the exporting module's namespace isolation, or static/dynamic parity. Tighten these to exact module identities/order where deterministic, and assert the actual exported value or target object.

No committed test covers project/package directory invocation through the binary, whole-module alias re-export, package exposure boundaries, private/unexported name fallback, cyclic re-export diagnostics, invalid synthetic runtime cycles, `EntrySelection::ModuleId`, repeated `materialize_program`/`run_compiled` calls, module registry replacement and garbage collection, or argument-bearing module-object exports. These are not merely aspirational cases: the first four P1/P2 findings arise specifically in those untested seams. The minimum regression set should include a CLI process test, a linker fixture for `import M as m; export m`, a synthetic invalid `CompiledProgram` test, and one API test for a linked `ModuleId`.

The static and dynamic dispatch paths also need a shared behavioral matrix. For each exported value, cover getter access, fixed-arity call, positional rest call, labeled rest call, missing export fallback, and module-object export. The compiler-emitted path enters `invoke_at`, while the public dynamic API enters `send_dynamic`; passing one lane does not establish parity for the other. Include a test that compares their returned value, captured arguments, error kind, and stack/frame cleanup.

The materialization API deserves lifecycle tests beyond successful initialization. A failed materialization currently may have inserted some module records before returning, and repeated materialization replaces registry records while allocating fresh heap objects. Even if the registry roots make old objects collectible, the intended reuse/rollback behavior should be made explicit and tested under a forced missing linked target. Likewise, `CompiledProgram` contains `ObjRef` in `ModuleArtifact::initializer` despite being described as VM-independent; cross-VM reuse should either be prohibited by type/API or tested and made safe.

The full clippy command is not a useful clean signal for this commit without baseline filtering: the workspace already carries broad `clippy::result-large-err` debt around `PhError`, along with older style lints. Keep changed-file lint output separate from the baseline, and add a focused lint/benchmark lane for materialization allocation count, repeated registry insertion, source-text retention, and export-table lookup cost once runtime semantics are complete.
