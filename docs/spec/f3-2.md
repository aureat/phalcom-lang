Yes. Three real loose ends:

1. LSP still encodes U9 rest selectors.

   [selectors.rs](/Users/altunhasanli/dev/phalcom/phalcom/phalcom-lsp/src/selectors.rs:25) only recognizes final `*rest` as `name(*)`; `**rest`, `***rest`, split layout, and fixed prefixes are indexed incorrectly. Go-to-definition, references, and workspace symbols can disagree with runtime selector identity.

2. Native-rest rejection is not defensive at installation.

   F.3 source declarations only create closures, so current behavior is safe. But [the method-install opcode](/Users/altunhasanli/dev/phalcom/phalcom/phalcom-core/src/vm/dispatch.rs:1310) would accept a future/reflection-created primitive with `Signature.rest`, then call it with the bytecode rest ABI. F.3 says this must reject unless ABI is ratified.

3. Constructor rest remains explicitly rejected by old transition code.

   [class_decl.rs](/Users/altunhasanli/dev/phalcom/phalcom/phalcom-core/src/compiler/lib/class_decl.rs:60) still rejects rest on constructors with `RestModeNotYetSupported`. This is either correct scope narrowing or an F.3 gap; amended F.3 does not explicitly exempt constructors, so needs a decision.
