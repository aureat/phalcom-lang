# 010 — three A/Bs, built and pre-registered, not yet timed

**Status: NOT MEASURED.** Every binary named here is built, verified
behavior-invariant, and waiting on a quiet box. No wall-clock exists for any of
them, and none may be inferred from what is written below.

**Base SHA: `4c6c83f`.** All six timing binaries are built at `4c6c83f` (one is
at its parent `c82c8bf`, deliberately — see §5). Counting builds are separate
binaries and are never timed ([instruments.md](instruments.md) two-build
protocol).

This document exists because three open holes ([H16](SCOREBOARD.md#6-open-holes--what-is-empty-and-how-to-fill-it),
[H17](SCOREBOARD.md#6-open-holes--what-is-empty-and-how-to-fill-it),
[H13](SCOREBOARD.md#6-open-holes--what-is-empty-and-how-to-fill-it)'s body half)
all bottleneck on the same scarce resource — a machine quiet enough for
`ab-guarded.py` to consent to time it ([F22](findings.md#f22--call_016s-one-live-thread-is-dead-the-opcodes-were-never-its-mechanism)).
Builds do not care about load; timing is the only thing that does. So every
build is done up front, and the quiet window is spent entirely on measurement.

The predictions in §2–§5 are recorded **before** any number exists, so that a
result cannot be rationalised after the fact. That is the discipline
[F18](findings.md#f18--presizing-the-fiber-vecs-is-negative-and-f3h9s-memmove-lever-is-spent-206--30)
(an estimate with the wrong sign) and
[F21](findings.md#f21--an-arms-code-is-paid-by-every-program-not-the-ones-that-execute-it)
(a ceiling that was right and still insufficient) both argue for.

## 1. Why the base moved, and why `e66af34`'s pair was retired

[H17](SCOREBOARD.md#6-open-holes--what-is-empty-and-how-to-fill-it) recorded a
prepared A/B pair at `e66af34` (`/tmp/ph-base`, `/tmp/ph-probe`) ready for a
quiet box. **That pair is not used here.** Between `e66af34` and HEAD, commit
`4c6c83f` (`wip(U-CTOR)`) edited `phalcom-core/src/vm/dispatch.rs` at line 887 —
which is **inside `run_until_inner`** (the function begins at line 477). It
rewrote the super-construct fallback in the `SuperSend` arm, replacing a
selector re-encode with a kind-filtered lookup.

Measured, that commit **shrank the dispatch loop by 248 bytes**:

| symbol | `c82c8bf` (prev) | `4c6c83f` (HEAD) | Δ |
|---|---|---|---|
| `run_until_inner` | 16,544 | 16,296 | **−248 B** |
| `invoke_at` | 1,536 | 1,584 | +48 B |
| `call_method` | 1,136 | 1,136 | +0 |

Under [F21](findings.md#f21--an-arms-code-is-paid-by-every-program-not-the-ones-that-execute-it)
that is not a neutral event: F21's whole claim is that `run_until_inner`'s **code
footprint** is paid by every program, including ones that never execute the
changed arm. A base binary five commits stale, on the wrong side of a
loop-footprint change, cannot serve as the base for a measurement whose effect
size is ~5%. Everything is therefore rebuilt at one common SHA.

`e66af34`'s pair is left on disk untouched as a cross-check, not as an input.

## 2. H16 — does the dispatch loop's *layout* cost ~5%?

**Hole:** [H16](SCOREBOARD.md#6-open-holes--what-is-empty-and-how-to-fill-it).
**Binary:** `ph-A-h16`. **Base:** `ph-A-base`.

### The hypothesis

[F21](findings.md#f21--an-arms-code-is-paid-by-every-program-not-the-ones-that-execute-it)
established, by probe rather than inference, that an arm's **code in
`run_until_inner`** is paid by programs that never execute it: a 38th variant
with an `unreachable!()` body (which LLVM erases) is free at −0.6%, while the
same variant with a **real** body that is **never emitted** costs **+6.1%**. F21
established the *sign and mechanism* of that effect. It never established
whether the effect runs the *other* way.

**H16's hypothesis: the loop is on a layout cliff, and it is currently on the
wrong side of it.** If adding ~5% of arm code costs ~5%, then removing a quarter
of the loop's footprint should *pay*, and by more than any remaining fusion —
whose best ceiling is ~5.1%, and which F21 has anyway gated.

### The probe

Outline the five **cold** arms — `Class`, `Import`, `MakeFamily`,
`FinalizeClass`, `Method` — into `#[inline(never)]` methods on `VM`, leaving each
arm a single call. These five run at class-definition and load time, never in a
hot loop, so no benchmark row executes them more than a handful of times. This
is the move H16 itself prescribes.

Cut 004/007's hoisted `Rc<Callable>` is what makes this cheap: the arms take
`&Rc<Callable>` out of a local, not a borrow of `self.heap`, so an outlined
method keeps full `&mut self` with no lifetime fight and no `unsafe`.

### What the probe verifiably does (measured, load-independent)

| symbol | `ph-A-base` | `ph-A-h16` | Δ |
|---|---|---|---|
| **`run_until_inner`** | **16,296** | **12,088** | **−4,208 B (−25.8%)** |
| `call_method` | 1,136 | 1,136 | **+0** |
| `invoke_at` | 1,584 | 1,584 | **+0** |
| `op_class` | — | 1,040 | outlined |
| `op_import` | — | 856 | outlined |
| `op_make_family` | — | 1,496 | outlined |
| `op_finalize_class` | — | 268 | outlined |
| `op_method` | — | 1,452 | outlined |

5,112 B of arm code left the loop; 4,208 B of footprint went with it. The two
neighbouring hot functions are **byte-identical in size**, so this is a clean
single-variable perturbation of exactly the quantity F21 indicted.

### Prediction, recorded before measurement

- **If F21's mechanism is footprint-proportional and monotone**, every
  execution-bound row improves, including `for`, `fib` and `string_equals`, which
  execute these five opcodes ~never. A −25.8% footprint cut against F21's
  measured ~+5–6% per duplication event predicts a **multi-percent, uniform,
  same-sign win**.
- **The falsifier is a split sign.** If some rows gain and others lose, the
  effect is not "footprint" but something narrower — I-cache set conflicts,
  branch-predictor table pressure, or code alignment of a specific hot arm — and
  H16's framing ("the loop is on a layout cliff") is wrong even if the numbers
  are large. That distinction matters more than the magnitude, because it decides
  whether *any* future cut can control this variable deliberately.
- **A null result (< ~1%, no consistent sign) refutes H16** and, read together
  with F21's +6.1%, would mean the tax is asymmetric: adding code hurts, removing
  it does not help. That is a strange but survivable world, and it would mean
  the fusion work list is gated permanently rather than pending a layout fix.

### What it does not decide

Nothing here re-prices cut 008. That needs its own A/B against a layout-matched
base (H16's second half), and it is out of scope for this round.

## 3. H17 — the `core.ph` cursor protocol, finally timeable

**Hole:** [H17](SCOREBOARD.md#6-open-holes--what-is-empty-and-how-to-fill-it).
**Binary:** `ph-A-h17`. **Base:** `ph-A-base`.
**Finding:** [F23](findings.md#f23--fors-cost-is-a-ph-call-chain-and-a-coreph-cut-is-immune-to-f21s-arm-tax).

### The hypothesis

`for (x in list)` pushes **four `.ph` frames per element**, two of which are pure
forwarding wrappers over a floor primitive. `for` is the suite's worst row at
**10.7× Wren**. Deleting the two wrapper frames should show up in wall-clock.

### The probe

Give `List` its own cursor protocol that calls the primitives directly —
`self.length_` inside `iterate`, `self.at_` in `iteratorValue` — skipping
`List.size` and `List.at`. **`core.ph` only; no Rust.** Map/Set/Tuple/Range
already do exactly this; `List` is the sole `.ph` hop, so this half is a
consistency fix with four precedents in the same file.

### Two claims verified before timing

**(a) F23's counts reproduce at HEAD.** F23 counted at `e66af34`, *before*
`c82c8bf` renamed the native `raw*` selectors to a trailing underscore. The probe
is now spelled `at_`/`length_` rather than `rawAt`/`rawLength`, so the count was
re-derived at `4c6c83f` with fresh counting builds:

| metric | base `4c6c83f` | probe `4c6c83f` | Δ | F23 @ `e66af34` |
|---|---|---|---|---|
| instructions retired (`for.ph`) | 59,000,705 | 53,000,704 | **−6,000,001 (−10.2%)** | −6,000,001 (−10.2%) |
| `Return` (= `.ph` frames pushed) | 5,000,004 | 3,000,003 | **−2,000,001** | −2,000,001 |
| stdout | `499999500000` | `499999500000` | identical | identical |

Identical across the rename. The selector spelling is orthogonal to the
mechanism, as it should be, and **−2,000,001 is exactly 2 frames per element over
1M elements** — the prediction met to the digit for the second time.

**(b) F23's "immune to F21" claim is now verified, not asserted.** F23 argues a
`core.ph` cut leaves the dispatch loop byte-identical and therefore cannot pay
the arm tax. Measured:

| symbol | `ph-A-base` | `ph-A-h17` | Δ |
|---|---|---|---|
| `run_until_inner` | 16,296 | 16,296 | **+0** |
| `call_method` | 1,136 | 1,136 | **+0** |

**H16 does not gate H17.** That is now a measurement, not an argument.

### Prediction, recorded before measurement

- **Do not derive the wall-clock from the instruction count.** The deleted
  instructions are `CallFrame` pushes (96 B each,
  [F15](findings.md#f15--value-is-2-wrens-and-objref-blocks-nan-boxing)), not
  dispatches, so [F19](findings.md#f19--a-dispatch-costs-33-ns-and-that-is-what-a-fusion-buys-h13)'s
  3.3 ns dispatch price does **not** size this. An un-re-derived estimate here is
  precisely F18's sign error waiting to recur. **No number is predicted.**
- **Direction is predicted:** `for` improves; every other row is flat, since none
  of them iterate a `List`. A row *other* than `for` moving materially would mean
  the probe is not what it claims to be, and would need explaining before the
  `for` number is trusted at all.

### The landing blocker, unchanged by any of this

The probe is **not behavior-invariant** under class reopening
([ADR-0026](../../adr/accepted/0026-class-hierarchy-mutability.md)): a user
reopening `List` to override `size` or `at` would no longer see `for` honor it.
The golden corpus's 46 green tests are **not** evidence of invariance — they are
evidence the corpus does not reopen `List`. Landing needs kernel-collection
sealing (the `8d401f4` `Option` precedent) or its own ADR. **Timing it decides
whether that sealing work is worth starting — nothing more.**

## 4. H13 (body half) — what does the 128 B argument-buffer init cost?

**Hole:** [H13](SCOREBOARD.md#6-open-holes--what-is-empty-and-how-to-fill-it),
the open body half.
**Binaries:** `ph-A-h13b` (primary), `ph-A-h13` (secondary). **Base:** `ph-A-base`.

### The hypothesis

`call_method`'s primitive fast path opens with `let mut args = [Value::Nil;
INLINE_ARGS];` — 8 × 16 B = **128 B initialized on every primitive send**, of
which the first `arity` are immediately overwritten by the copy. `arity` is a
runtime operand from the bytecode, so LLVM cannot statically shrink the init to
the live prefix, and the dead stores cannot be eliminated across the opaque
`native_fn` function-pointer call. The dead init should therefore be real.

This is the question an `INLINE_ARGS` A/B was built for and **had voided by
machine load** ([F22](findings.md#f22--call_016s-one-live-thread-is-dead-the-opcodes-were-never-its-mechanism)).
**No result from that void round is carried forward here, in either direction.**

### Two probes, because the obvious one is confounded

The first attempt (`ph-A-h13`) replaced the array with `MaybeUninit` and wrote
the elements in a `for i in 0..arity` loop. It **grew `call_method` by 96 B** —
because it also replaced a bulk `copy_from_slice` (a memcpy) with an elementwise
loop. That probe measures *init-removal ⊕ memcpy→loop*, which is two variables.

`ph-A-h13b` is the clean probe: `MaybeUninit` storage, init removed, and the copy
left as a **single bulk `copy_from_slice`**, exactly as the base does it. It
isolates the init.

| symbol | `ph-A-base` | `ph-A-h13b` (clean) | `ph-A-h13` (confounded) |
|---|---|---|---|
| `call_method` | 1,136 | **1,112 (−24 B)** | 1,232 (**+96 B**) |
| `run_until_inner` | 16,296 | 16,296 (+0) | 16,296 (+0) |

h13b gets *smaller*, which is what removing dead stores should do. Both leave
`run_until_inner` untouched, so **F21's loop tax does not apply to either** —
though h13's +96 B in `call_method` is its own footprint change, and is exactly
why it is demoted to secondary.

### Prediction, recorded before measurement

- **Expect a small effect, and expect it on the primitive-heavy rows.**
  `Value::Nil` is a cheap immediate; 128 B of stack stores is on the order of a
  nanosecond or two against a send that F19 prices at ~3.3 ns of dispatch alone.
  `arith_send` and `bare_send` are where it would show; `for` and `fib` should
  barely move.
- **A null result is a real answer and closes the hole.** H13's body half exists
  because nobody knows this number. "It is under the noise floor" retires it.
- **`ph-A-h13` vs `ph-A-h13b`** is a free second question — memcpy vs elementwise
  loop at small `arity`. Time it only if the window allows; it is not the hole.
- **Do not fit per-opcode prices from this.** Least-squares over the
  execution-bound rows is underdetermined at 37 opcodes; H13's standing
  instruction is to pivot one known quantity at a time, not to regress.

## 5. The natural experiment nobody designed — `prev` vs `base`

**Binaries:** `ph-A-prev` (`c82c8bf`) vs `ph-A-base` (`4c6c83f`).

F21 and H16 rest on **deliberate** probes: code added or removed by someone
trying to measure it. `4c6c83f` is different. A concurrent session, working on
constructor semantics with no performance intent whatsoever, shrank
`run_until_inner` by 248 B (§1). It is an *unintentional* perturbation of exactly
F21's variable — which makes it the closest thing to a natural experiment this
log has.

### Prediction, recorded before measurement

- **If F21 generalises, `4c6c83f` is faster than `c82c8bf` on rows that never
  execute `SuperSend`** — the changed arm — by a fraction of F21's ~5%, scaled
  to a −1.5% footprint change rather than a duplication event.
- **This is confounded and must be reported as such.** The two SHAs differ by
  more than the loop: `invoke_at` grew 48 B, `c82c8bf` renamed selectors across
  17 files, and interned selector strings changed length. It is a canary, not a
  clean measurement. Report it as one.
- **Its real value is a warning.** If unrelated work moves the suite by several
  percent through nothing but layout, then **every cut in this log carries an
  uncontrolled layout term**, and SCOREBOARD §1's history is noisier than its
  numbers claim. That would be the largest finding of the round, and it comes
  free with binaries that already exist.

## 7. The quiet window — one run, six arms

### Run this

```sh
~/phalcom-perf-phaseA/run-phase-b.sh
```

It verifies the manifest, **waits for the box to go quiet by itself**, runs the
batch, and saves everything to `~/phalcom-perf-phaseA/results/phase-b-<stamp>.txt`.
That results directory is the handoff: the next session reads it from there.

### Why one invocation and not five

`ab-guarded.py`'s `--bin` **appends** — it takes N arms, times them all against
`arms[0]`, and **alternates arm order every rep**. So a single six-arm run is
strictly better than five pairwise runs: the shared base is timed **once**
instead of four times (600 runs, not 960), and every arm sees the same machine
conditions, so any residual drift hits them equally rather than landing on
whichever pair happened to run during it.

```sh
benchmarks/vm/ab-guarded.py 15 full \
    --bin base=$B/ph-A-base \
    --bin h16=$B/ph-A-h16 \
    --bin h17=$B/ph-A-h17 \
    --bin h13b=$B/ph-A-h13b \
    --bin h13=$B/ph-A-h13 \
    --bin prev=$B/ph-A-prev
```

8 rows × 15 reps × 6 arms ≈ **12–20 min**. Every `d%` column is that arm against
`base`; note `prev`'s sign is therefore inverted from §5's "prev → base" framing
— same information, read it in the right direction.

The harness aborts the **whole** run if any two arms disagree on stdout. All six
agree on all 8 rows ([§6](#6-binary-manifest)), so that check should never fire —
if it does, something rotted and no number from the run is usable.

### The guard, and the trap in front of it

`ab-guarded.py` exits 3 and prints nothing if `load1 > 1.5` or a
`rustc`/`cargo`/`cc`/`ld` is running. It rescans **per rep**, because
`getloadavg()` lags ~1 min and misses bursts. It aborts rather than pausing; a
contaminated run is discarded whole.

**The lag is the trap.** `load1` is a ~1-minute moving average, so quitting Chrome
does not drop it for another 2–3 minutes — quit your apps, run immediately, and
you get exit 3 anyway despite having done everything right. `run-phase-b.sh`
polls and waits for this rather than failing on it. At the time of writing load
was **10.92**, and it was **not** `rustc` — it was desktop load (WindowServer,
Finder, Chrome).

**Serialize against the U-CTOR/U-BINDINGS track.** That work runs `rustc`, which
is F22's exact hazard and will abort the run mid-flight.

Exit 0 = numbers valid. Exit 3 = machine not quiet, **nothing to salvage** — a
refusal is not a null result. Never set `LOAD_MAX` to bypass the guard for a real
number; it exists to smoke-test the harness, and it labels its own output invalid
when used.

## 8. What Phase A deliberately did not do

- **No timing.** Not one wall-clock number was taken, at load 10.9–12.0. Under
  F22 that would be void, and a void number in a doc outlives the caveat next to
  it.
- **No landing.** Every probe is a probe. H17's ADR-0026 blocker (§3) is
  untouched, and H16's outlining is written to be measured, not merged.
- **Nothing committed to the main tree.** All work is in detached worktrees under
  the session scratchpad; `phalcom-core/src` on `main` is untouched, because the
  U-CTOR sessions are live in it.
